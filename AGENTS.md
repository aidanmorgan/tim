## Delivery speed rules (owner, 24 October 2026; these take precedence over conflicting wording below)

- **One loop, one review system.** Every slice runs the `bmad-build-auto` workflow. Its step-04 review layers (Blind Hunter, Edge Case Hunter, Verification Gap, Intent Alignment) are the independent adversarial review. No separate reviewer agent repeats them. After publication, a small verifier runs only the terminal checks (CI on the exact SHA, Pages artifact, deployment).
- **One slice at a time.** Start the next slice from the published main, so a slice merges main at most once. Parallel work is limited to read-only drafting of the next spec.
- **Builds.** Use incremental builds. Run the full solution suite once per round, at the end. Do not run the local Release worker build or web publish; CI owns them.
- **Mutations once.** A small set of mutants covers each new test's key behaviour. The review's verification layer checks them; the implementer does not repeat them.
- **Light evidence.**
  - Identities are commit SHAs, CI run IDs and test totals.
  - No staged-tree or diff hashing, and no duplicated manifests.
  - SnapshotApproval is the review Pass on a committed SHA.
  - Terminal receipts are a short section in the review record.
- **Fresh agents.** Each slice gets a fresh implementer, and review fixes go back to it. Do not carry long-lived agents across slices.
- **Stable rules.** A new rule applies from the next slice unless the owner says otherwise. A slice already in review finishes under the rules it started with.

## Delivery slices and independent review

Implement one small functional slice: one behavior, defect or invariant plus its necessary callers, content, tests and documentation. Select its bounded [INVEST scope](docs/planning/invest-index.md), then read the exact source acceptance and technical prerequisites; card summaries cannot waive them. Use a dedicated implementation subagent and a different independent adversarial review subagent; the coordinator delegates, reconciles results and reports status. Keep that pair through debugging and forward fixes. Self-review never qualifies.

Related design, implementation, cleanup, tests, UI proof, evidence and status updates are criteria inside that slice, not separate assignments or terminal administrative gates. Preserve every requirement ID and acceptance criterion. Do not combine several new puzzle elements. Genuine technical prerequisites and necessary design decisions must pass their required stage before dependent work; historical row order alone is not a dependency. Apply [REQ-14 and the slice workflow](docs/delivery-workflow.md#paired-subagent-workflow).

The reviewer independently inspects the actual diff and requirements, derives expected outcomes, investigates direct/transitive impacts and runs affected positive, negative/control and boundary checks. Retain a justified criterion/impact matrix, distinct actual identities, raw commands/results, findings and a terminal verdict. Runtime changes need one matching build of the affected closure and fast positive/control/boundary checks; reuse that build for tests with `--no-build --no-restore` until relevant source, generated inputs, dependencies or configuration change. Tests must execute the real production C# simulation for intended interactions, negative/boundary cases, tick progression and supported Reset/save/load; declaration-only or mocked checks are insufficient. Actual Chrome/Playwright behavior and ordinary UI lifecycle proof are queued for the post-catalogue E2E phase, with browser qualification explicitly pending; detailed performance stays at its named qualification phase; documentation/research need source, link, preservation, dependency and consistency checks. Unknown coverage or missing/stale proof is Incomplete; a known violation is Fail. Only zero unresolved unintended regressions within the justified required-now scope permits implementation Pass. A fully implemented element may proceed on native/unit proof and independent review while browser qualification remains explicitly pending until post-catalogue E2E; this is not browser/release qualification.

Return findings to the same implementation owner and independently re-review affected fixes. A reviewer who changes a deliverable becomes an implementer and needs another independent reviewer. The verdict and review-only evidence do not create a recursive work item.

## Engineering and gameplay requirements

- Sole design authority: [element package isolation](docs/architecture/element-package-isolation.md) (target invariants and current status).
- Current numeric/execution authority: [canonical IEEE-754 f32 game values and WASM SIMD physics](docs/gpu-f32-physics.md). Use standard 32-bit single-precision floating point (`f32` / `float`) across authoring, solver, and presentation, with WebAssembly 128-bit SIMD (`wasm-simd128`) vectorization on a dedicated Web Worker. Lock-free zero-copy triple-buffered pose ring in `SharedArrayBuffer` eliminates GPU-to-CPU readback stalls. Universal rendering on both WebGL 2 and WebGPU via instanced draw batches. Integers and declared external adapters retain their correct types. No hidden legacy game models or CPU fallback paths.

- Engine first: deliver **ENGINE-CORE-1** then **ENGINE-CORE-2** in the [ordered roadmap](docs/planning/invest/vertical-delivery.md#rolling-playable-roadmap) before new elements; then one element per slice in roadmap order. Existing parts deliver the engine through thin playable Workshop slices; their required authoring/solver/worker/presentation criteria are grouped inside each outcome, not a whole-subsystem prerequisite queue. [Standing requirements](docs/delivery-workflow.md#standing-requirements) and [stage gates](docs/delivery-workflow.md#stage-gates) remain mandatory; full supported-device/workload qualification stays at its named release-checklist gate.
- Tri-Graph compile-to-state architecture: Decouple into three distinct graphs:
  1. **Logical Scene / Machine Graph:** Hierarchical authoring, typed sockets, connections, serialization, and UI selection on the main thread.
  2. **Physics Graph:** Compiled at Run into flat contiguous SIMD-aligned Structure-of-Arrays (SoA) tables, Dynamic AABB BVH with velocity fattening, Disjoint Set Union (DSU) island graph, and Box2D v3 Temporal Gauss-Seidel (TGS) Soft solver, advanced on a dedicated WASM SIMD worker at 120 Hz (480 Hz substeps). Scaled to handle hundreds of concurrent puzzle elements with sub-millisecond execution times.
  3. **Rendering Graph:** GPU instanced draw batches (`gl.drawElementsInstanced` in WebGL 2, `renderPass.drawIndexed` in WebGPU) driven by the zero-copy pose ring and secondary cosmetic animation evaluators (60 Hz) on an independent Animation worker.
  Rates: physics (120 Hz) > animation (60 Hz) ≥ renderer (30–60 FPS, display-paced). Data flows one-way: physics → animation → renderer and physics → renderer; nothing flows back ([compilation model](docs/gpu-f32-physics.md#compilation-model)). No element has its own solver, kernel branch or update loop; a new element is declaration data, art and bindings only.
- Implement every named puzzle element/variant, not one representative per family. Component coverage precedes exhaustive difficulty/nudging and campaign sweeps. Preserve existing difficulty evidence and the target of **150 progressively taught levels**.
- Every existing/new catalogue part, fixture and supported mode needs identifiable actual Chrome/Playwright UI construction, verified placed configuration and typed connections, intended behavior, a meaningful negative/control, applicable integration and exact Run/Reset restoration plus save/load where supported. Use actual UI controls, never setters, imported solutions or numeric placement menus. Retain recipes, revision/bundle identity, assertions, logs, motion/screenshots and failed attempts. Native/reference/fake-page checks supplement this proof. Accumulate affected cases across the batch, including infrastructure changes, and run necessary affected/integration/regression E2E after all named puzzle elements are implemented. Until then label browser qualification pending; preserve older proof without claiming it covers changed inputs. No element counter is needed. Missing/stale proof remains incomplete at the enforcing batch or release gate.
- Prove relevant boundaries, production build and ordinary lifecycle/resource ownership; qualify detailed resource stress and affected performance at their named gates. Commit and push each independently reviewed fully implemented element before the next, recording pending post-catalogue browser qualification; preserve individual evidence/publication when administrative stages share a slice.
- Refactor forward: one current path, no fallback, compatibility shim, legacy mode, old-name alias or automatic migration. Never create backwards compatibility shims, helpers, or bridges. Every slice names the legacy it deletes; the programme ends with zero legacy physics/animation code in the tree (git history is the archive). Update current callers, authored content, tools, tests and active docs together; reject unsupported inputs explicitly and atomically. Puzzle elements must be refactored into the new declarative data schema, never removed. Historical artifacts remain unchanged evidence, not supported current input.
  - **Review gate (owner, 25 October 2026):** a reviewer treats as a **Fail** any change that adds or keeps any of the following:
    - a fallback;
    - backwards compatibility: a compatibility shim, helper, bridge, adapter for an old format or caller, legacy mode, old-name alias or re-export, migration or upgrade path, or version branch;
    - a retained deprecated field, member or file kept so old inputs keep working;
    - a second rule or code path for the same behaviour, chosen by condition, flag, mode or environment.

    Two things are not compatibility:
    - Refusing unsupported input with a typed, visible reason. Detection only names the refusal and never reads or uses the old content.
    - A numerical recovery inside one algorithm, such as a singular-matrix per-row solve. It applies the same rule as the main path.

    Every bmad-build-auto review runs the Forward-Only Auditor layer (`_bmad/custom/bmad-build-auto.toml`). Triage grades each confirmed finding `high`, never rejects it as low or out of scope, and a slice cannot reach `done` with one unresolved.
- **Hard rule — no skipped tests (owner, 24 October 2026).**
  - Every test of the game system runs and passes in every required run: local verification, hooks and CI. Every reported result has `Skipped: 0`.
  - The game system's tests are the C# solution's test projects and the node harnesses for game runtime code.
  - **Scope (owner, 24 October 2026):** browser/E2E suites and the vendored BMAD tooling tests are not part of proving the system works. Required runs do not include them, and they are not provisioned or gated.
  - The following are forbidden: `Skip`, `[Fact(Explicit = true)]`, conditional/ignored tests, `.skip`/`.todo`, and test-runner filters or categories that exclude tests from a required run.
  - Selecting tests for a scoped local check is allowed, but the full required run must still include them.
  - **Browser exception (owner, 24 October 2026):** browser/E2E tests (Chrome/Playwright suites and the tests of their toolchain) are deferred, explicitly disabled or removed, until the post-catalogue browser phase, which re-enables them. That phase starts only when **every named puzzle element is implemented and passing its unit and integration tests** (owner, 24 October 2026). Before then, no slice runs, writes as a gate or depends on browser tests. Disabling must be explicit and listed in one place, with the re-enable gate and owner. Silent filters are not allowed. Native C# and non-browser tests have no exception.
- **Hard rule — unit tests follow [docs/testing-guidance.md](docs/testing-guidance.md) (owner, 24 October 2026).** Tests prove behaviour through defined interfaces, run the real production code, and derive their expectations and tolerances independently. They cover positive, control and boundary cases, are proven to fail against a plausible defect, and are deterministic. Architecture guards are a small, named category. Reviewers apply the guidance's checklist, and any failure is a finding.
- **Hard rule — tests assert behaviour, not hashes (owner, 24 October 2026).**
  - Committed tests must not assert hashes, digests or byte-identity of simulation, trace, event, render or save output, including "unchanged bytes" and golden-hash pins.
  - Assert the observable behaviour explicitly: counts, kinds, ticks, owners, states and positions or speeds within a derived tolerance.
  - Refactor byte-identity remains welcome as one-off review evidence. It is not a committed test.
  - Allowed:
    - integrity checks of vendored or third-party files;
    - fixed test inputs kept as committed fixture files. Do not pin them by hash.
  - A reviewer treats a new output-hash assertion as a Fail.
  - A test that cannot run in an environment is a defect to fix (provision the dependency, or move the behaviour into a test that can run). It must not be skipped.
  - Delete a test only when its behaviour is removed or provably covered elsewhere, and record which.
  - A reviewer treats any skipped or excluded test as a Fail.
- Game-grade tolerances: follow the envelope in [docs/gpu-f32-physics.md](docs/gpu-f32-physics.md#game-grade-envelope); numerical residuals clamp or continue, never fault the tick; proof-grade certificates are not acceptance criteria.
- **TypeScript, not JavaScript (owner, 24 October 2026).**
  - Code that cannot be C# (browser and worker glue, client runtime, node harnesses, tooling) is written in strict TypeScript (`strict: true`, no `any` escapes).
  - Shipped JS is only the output of a pinned `tsc` build that runs inside the normal build, publish and CI. No hand-written `.js` is committed in runtime or tool sources.
  - Tests run against the compiled output that ships.
  - Existing hand-written JS is converted by a dedicated slice. New or changed runtime and tool code from then on is TypeScript.
- Use C# wherever possible. Closed sets are enums end-to-end in production, configuration, tests and automation: API parameters/returns, collections/keys, comparisons and control flow retain enum types. Named string constants, ToString, nameof, interpolation or parsing in domain logic do not substitute for typing. Extensible identities use strongly typed IDs and resource/external strings use named boundaries. Convert/validate strings only at genuine UI/serialization/external boundaries; reject unknown/undefined values. Compile affected callers and test changed canonical mappings/rejection. Existing violations remain required refactoring; no repository-wide compliance claim before the verified audit.
- Preserve the approved palette; follow [DESIGN.md](DESIGN.md) for form, composition, lighting and motion.
- Use **Chrome through the available Playwright connector**. Check that connection directly before reporting it missing; an empty in-app Browser discovery does not establish unavailability. Do not substitute another browser.

Keep the current brief short: outcome, blocker/owner/retry condition, next acceptance check and authoritative evidence links. Update it when a result, blocker or candidate changes. Track verified delivery, blocked time, test duration and unnecessary repeats from existing records; unknown measurements stay unknown. Detailed [current requirements](docs/planning/requirements.md) remain required, without turning each administrative row into a new project.
