## Game fidelity — owner policy, 28 October 2026

This is a physics-based puzzle game. Correct puzzle outcomes, meaningful causal event order, plausible motion, stable resting behaviour and reliable lifecycle are the acceptance targets. This policy applies immediately, including the current slice, and supersedes older instructions that preserve historical simulation ticks, substep ordinals, trajectories or migration-era position deltas without a current gameplay requirement.

- Every strict numerical assertion must name the gameplay failure or defined-interface invariant it excludes. Choose tolerances by quantity, functional clearance and observation duration; floating-point ULPs, solver residuals and fractions of slop alone do not establish gameplay significance. Tight local mathematical tests remain valid when they test that mathematical contract.
- Use the [float comparison and effort rules](docs/testing-guidance.md#float-comparison-and-effort-rules) in every spec, implementation handoff and review. Reuse quantity-specific tolerances; do not invent a universal epsilon or tighter per-test margins. No extra precision checks or reruns without a concrete uncovered gameplay or interface failure.
- Lesson deadlines are finite, generous stall guards. Preserve intended timers/delays/cadence, but do not equate incidental arrival timing with a timing feature. Verify causal order and required occurrences, not every incidental contact or every-tick monotonic trajectory.
- Assert decoded semantic outputs. No simulation/event/trace/render/save hash or byte-identity acceptance, including one-off proof used to block a slice. Exact IDs, counts where specified, typed refusals, authored Reset state and canonical serialized field values remain valid; identical whole buffers are not their substitute.
- Before a second attempt to repair a numerical-only test failure, state the observable gameplay defect. If none is established, inspect and correct the test contract under this policy rather than escalating solver complexity or preserving obsolete goldens. Do not widen a bound to fit observed output; justify the revised behavioural test independently.
- Implementers and reviewers must flag unnecessarily precise tests. Historical evidence is not a source of new acceptance obligations. See [testing guidance](docs/testing-guidance.md) and [delivery rules](docs/delivery-workflow.md#game-fidelity).

## Delivery speed rules (owner, 24 October 2026; these take precedence over conflicting wording below)

- **One loop, one review system.** Every slice runs the `bmad-build-auto` workflow. Its step-04 review layers (Blind Hunter, Edge Case Hunter, Verification Gap, Intent Alignment, Forward-Only Auditor and Element-Free Engine Auditor) are the independent adversarial review; which of them a pass launches follows **Review tiers** below. No separate reviewer agent repeats them. After publication, a small verifier runs only the terminal checks (CI production build on the exact SHA, Pages artifact, deployment).
- **One slice at a time.** Start the next slice from the published main, so a slice merges main at most once. Parallel work is limited to read-only drafting of the next spec and to an **Early level proof** slice (below).
- **Local test authority (owner, 26 October 2026; effective immediately, including pending publication).** The full local solution test round is authoritative: zero failures and zero skipped game tests, with only the explicit browser deferral. Supplemental normal hook checks are separately required; their scoped test selection does not replace the full round. Follow the [local verification commands](docs/delivery-workflow.md#local-test-authority), including matching compiler logs. GitHub performs production compilation/publish, artifact checks and deployment, without game/tool test execution or test-only provisioning. Terminal verification records the exact SHA, build run, Pages artifact and deployment; remote test totals are not required. Independent Auto review and compiler warnings-as-errors remain required.
- **Builds.** Use incremental builds. Run the full solution suite once per round, at the end. Do not run the local Release worker build or web publish; CI owns them.
- **No mutation testing until the E2E phase (owner, 25 October 2026).** No implementer or reviewer creates, builds or runs mutants or mutated copies of the tree. Reviewers judge whether a test would catch a plausible defect by reading its assertions. Mutation testing returns with the post-catalogue browser/E2E phase.
- **Light evidence.**
  - Identities are commit SHAs, CI run IDs and test totals.
  - No staged-tree or diff hashing, and no duplicated manifests.
  - SnapshotApproval is the review Pass on a committed SHA.
  - Terminal receipts are a short section in the review record.
- **Fresh agents.** Each slice gets a fresh implementer, and review fixes go back to it. Do not carry long-lived agents across slices.
- **First-pass rules (21 November 2026 review).** Follow the [loop protocol](_bmad/custom/bmad-loop-protocol.md): policy is read from the checkout being worked on, never from another checkout; each child reads its [role card](_bmad/custom/role-cards.md); planning runs the [capability probe](_bmad/custom/bmad-loop-protocol.md#capability-probe), and a missing solver, ABI, wire or shared-presentation capability is its own engine slice first (amending REQ-12), with open owner decisions raised together; handoff follows the protocol's order, including the [new-package registration check](docs/delivery-workflow.md#new-package-registration-check), with a second full round only if the candidate changed after handoff; a missing or weak test is a patch, not `bad_spec`; the slice record is the native spec as a short contract plus a run log; completion is one candidate commit and one approval.
- **Stable rules.** A new rule applies from the next slice unless the owner says otherwise. A slice already in review finishes under the rules it started with.

## Delivery slices and independent review

Implement one small functional slice: one behavior, defect or invariant plus its necessary callers, content, tests and documentation. Select its bounded [INVEST scope](docs/planning/invest-index.md), then read the exact source acceptance and technical prerequisites; card summaries cannot waive them. Use a dedicated implementation subagent and a different independent adversarial review subagent; the coordinator delegates, reconciles results and reports status. Keep that pair through debugging and forward fixes. Self-review never qualifies.

Related design, implementation, cleanup, tests, UI proof, evidence and status updates are criteria inside that slice, not separate assignments or terminal administrative gates. Preserve every requirement ID and acceptance criterion. Do not combine several new puzzle elements, except as a **Family slice** below. Genuine technical prerequisites and necessary design decisions must pass their required stage before dependent work; historical row order alone is not a dependency. Apply [REQ-14 and the slice workflow](docs/delivery-workflow.md#paired-subagent-workflow).

Slice shapes and review tiers (owner, 21 November 2026). They apply from the next slice that starts; Bellows 12.4 and the registration-derivation slice, in flight on that date, finish under their starting rules. The [loop protocol](_bmad/custom/bmad-loop-protocol.md#slice-shapes) defines each precisely.

- **Family slice.** Several named variants of one family may be delivered in one slice when the capability probe shows that none needs a new engine, abstraction, wire or shared-presentation capability. Each identity still gets its own acceptance rows and tests.
- **Duplicate closure.** An identity that duplicates another part is closed by a recorded check in that part's slice or in one closure review, with the ledger row citing it. It gets no package or slice of its own and then counts as implemented.
- **Early level proof.** Planned puzzles that use only delivered parts may be authored and proven natively in parallel with element slices, in their own worktree, with publication serialised one publisher at a time. This is not browser qualification.
- **Review tiers.** A data-only slice, as the loop protocol's [Review tiers](_bmad/custom/bmad-loop-protocol.md#review-tiers) defines it, is reviewed by Verification Gap, the Forward-Only Auditor and the Element-Free Engine Auditor. Every other slice runs all six layers. The two auditors and Verification Gap run on every pass. Intent Alignment runs on the slice's first review pass only (restarted by `bad_spec`). A slice found to be mis-tiered is reviewed again at the engine tier.

The reviewer independently inspects the actual diff and requirements and derives expected outcomes; tests execute the real production C# simulation; unknown coverage or missing or stale proof is Incomplete and a known violation is Fail; browser proof stays queued for the post-catalogue E2E phase. The full rule is unchanged in [reviewer proof and verdicts](docs/delivery-workflow.md#agents-reviewer-proof).

Return findings to the same implementation owner and independently re-review affected fixes. A reviewer who changes a deliverable becomes an implementer and needs another independent reviewer. The verdict and review-only evidence do not create a recursive work item.

## Engineering and gameplay requirements

- **Review repair policy — owner, 4 November 2026 (effective immediately):** confirmed review findings must be fixed and independently re-reviewed before acceptance, including pre-existing issues. Origin, an initially narrow diff or low severity is not permission to defer a confirmed defect. This supersedes older unrelated-debt acceptance wording. Re-review exception (owner decision, 21 November 2026): from a slice's third review pass, a new finding outside the repair diff and what it directly affects, which breaks no hard rule, required-now criterion or gameplay behaviour, is recorded in deferred work instead of blocking, under the loop protocol's Re-review scope. Follow the [BMAD loop protocol](_bmad/custom/bmad-loop-protocol.md) for controlled repair scope, blocked recovery, progress checks and independent dispatch; preserve deferred qualification stages and unrelated dirty work.

- **BMAD customization entry check:** before approving work affected by the project engineering rules, resolve the invoked skill's project customization and verify that it loads [the project engineering extension](_bmad/custom/project-engineering-contract.md), the two engine guides where applicable, and its native planning/review hooks. If resolution fails, recover the documented base → team → user merge or report Incomplete; installed defaults alone cannot approve the work. Build/Auto must halt on renderer failure as their SKILL.md requires. Use the native spec/story/readiness/triage artifacts for evidence; do not substitute a separate rule checklist for the workflow gates.

- **Element-free engine gate — owner, 4 November 2026 (effective immediately):** no new or changed engine behavior may depend on puzzle-element-specific code or assumptions. The [design guide](_bmad/custom/element-free-engine-design.md) defines the required contracts; the [review policy](_bmad/custom/element-free-engine-review.md) defines scope, phase evidence, blocking verdicts and handoff duties. Apply both before engine-affecting planning approval and implementation acceptance, including context-free reviewers. A backlog repair may describe the violation it removes; it may not approve it as the solution.

- Sole design authority: [element package isolation](docs/architecture/element-package-isolation.md) (target invariants and current status).
- Current numeric/execution authority: [canonical IEEE-754 f32 game values and WASM SIMD physics](docs/gpu-f32-physics.md). Use standard 32-bit single-precision floating point (`f32` / `float`) across authoring, solver, and presentation, with WebAssembly 128-bit SIMD (`wasm-simd128`) vectorization on a dedicated Web Worker. Lock-free zero-copy triple-buffered pose ring in `SharedArrayBuffer` eliminates GPU-to-CPU readback stalls. Universal rendering on both WebGL 2 and WebGPU via instanced draw batches. Integers and declared external adapters retain their correct types. No hidden legacy game models or CPU fallback paths.

- Engine first: deliver **ENGINE-CORE-1** then **ENGINE-CORE-2** in the [ordered roadmap](docs/planning/invest/vertical-delivery.md#rolling-playable-roadmap) before new elements; then one element, or one Family slice, per slice in roadmap order. Existing parts deliver the engine through thin playable Workshop slices; their required authoring/solver/worker/presentation criteria are grouped inside each outcome, not a whole-subsystem prerequisite queue. [Standing requirements](docs/delivery-workflow.md#standing-requirements) and [stage gates](docs/delivery-workflow.md#stage-gates) remain mandatory; full supported-device/workload qualification stays at its named release-checklist gate.
- Tri-Graph compile-to-state architecture: a logical scene and machine graph on the main thread is compiled at Run into a physics graph advanced on a dedicated WASM SIMD worker at 120 Hz, which drives a rendering graph of GPU instanced batches; data flows one way and nothing flows back. No element has its own solver, kernel branch or update loop; a new element is declaration data, art and bindings only. The full statement is unchanged in [Tri-Graph architecture](docs/delivery-workflow.md#agents-tri-graph).
- Implement every named puzzle element/variant, not one representative per family; a Family slice or a Duplicate closure still accounts for each identity by name. Component coverage precedes exhaustive difficulty/nudging and campaign sweeps. Preserve existing difficulty evidence and the target of **150 progressively taught levels**.
- Every existing/new catalogue part, fixture and supported mode needs actual Chrome/Playwright UI proof through real UI controls, accumulated across the batch and run in the post-catalogue E2E phase; until then label browser qualification pending, and missing or stale proof is incomplete at the enforcing batch or release gate. The full rule is unchanged in [browser proof for every part](docs/delivery-workflow.md#agents-browser-proof).
- Prove relevant boundaries, production build and ordinary lifecycle/resource ownership; qualify detailed resource stress and affected performance at their named gates. Commit and push each independently reviewed fully implemented element or Family slice before the next, recording pending post-catalogue browser qualification; preserve individual evidence/publication when administrative stages share a slice.
- Refactor forward: one current path, no fallback, compatibility shim, legacy mode, old-name alias or automatic migration. Never create backwards compatibility shims, helpers, or bridges. Every slice names the legacy it deletes; the programme ends with zero legacy physics/animation code in the tree (git history is the archive). Update current callers, authored content, tools, tests and active docs together; reject unsupported inputs explicitly and atomically. Puzzle elements must be refactored into the new declarative data schema, never removed. Historical artifacts remain unchanged evidence, not supported current input.
  - **Review gate (owner, 25 October 2026):** a reviewer treats as a **Fail** any change that adds or keeps any of the following:
    - a fallback;
    - backwards compatibility: a compatibility shim, helper, bridge, adapter for an old format or caller, legacy mode, old-name alias or re-export, migration or upgrade path, or version branch;
    - a retained deprecated field, member or file kept so old inputs keep working;
    - a second rule or code path for the same behaviour, chosen by condition, flag, mode or environment.

    Two things are not compatibility:
    - Refusing unsupported input with a typed, visible reason. Detection only names the refusal and never reads or uses the old content.
    - A numerical recovery inside one algorithm, such as a singular-matrix per-row solve. It applies the same rule as the main path.

    Every bmad-build-auto review runs the Forward-Only Auditor layer (`_bmad/custom/bmad-build-auto.toml`). Triage grades each confirmed finding `high`, never rejects it as low or out of scope, and a slice cannot reach `done` with one unresolved.
- **Hard rule — no skipped tests (owner, 24 October 2026).**
  - Every test of the game system runs and passes in the required full local solution round. Normal hooks additionally run their scoped checks; they do not run or replace the full suite. GitHub builds and deploys; it does not repeat the tests. Every reported result has `Skipped: 0`.
  - The game system's tests are the C# solution's test projects and the node harnesses for game runtime code.
  - **Scope (owner, 24 October 2026):** browser/E2E suites and the vendored BMAD tooling tests are not part of proving the system works. Required runs do not include them, and they are not provisioned or gated.
  - The following are forbidden: `Skip`, `[Fact(Explicit = true)]`, conditional/ignored tests, `.skip`/`.todo`, and test-runner filters or categories that exclude tests from a required run.
  - Selecting tests for a scoped local check is allowed, but the full required run must still include them.
  - **Browser exception (owner, 24 October 2026):** browser/E2E tests (Chrome/Playwright suites and the tests of their toolchain) are deferred, explicitly disabled or removed, until the post-catalogue browser phase, which re-enables them. That phase starts only when **every named puzzle element is implemented and passing its unit and integration tests** (owner, 24 October 2026). Before then, no slice runs, writes as a gate or depends on browser tests. Disabling must be explicit and listed in one place, with the re-enable gate and owner. Silent filters are not allowed. Native C# and non-browser tests have no exception.
- **Hard rule — unit tests follow [docs/testing-guidance.md](docs/testing-guidance.md) (owner, 24 October 2026).** Tests prove behaviour through defined interfaces, run the real production code, and derive their expectations and tolerances independently. They cover positive, control and boundary cases, assert the changed result directly so that a plausible defect would fail them, and are deterministic. Mutation runs are deferred to the post-catalogue E2E phase. Architecture guards are a small, named category. Reviewers apply the guidance's checklist, and any failure is a finding.
- **Hard rule — tests assert behaviour, not hashes (owner, 24 October 2026).**
  - Committed tests must not assert hashes, digests or byte-identity of simulation, trace, event, render or save output, including "unchanged bytes" and golden-hash pins.
  - Assert the observable behaviour explicitly: counts, kinds, owners, states, feature-defined timing and positions or speeds within a gameplay-justified tolerance.
  - Refactor byte-identity is not gameplay acceptance or a publication prerequisite. Use decoded semantic behaviour; existing historical byte comparisons remain historical evidence only.
  - Allowed:
    - integrity checks of vendored or third-party files;
    - fixed test inputs kept as committed fixture files. Do not pin them by hash.
  - A reviewer treats a new output-hash assertion as a Fail.
  - A test that cannot run in an environment is a defect to fix (provision the dependency, or move the behaviour into a test that can run). It must not be skipped.
  - Delete a test only when its behaviour is removed or provably covered elsewhere, and record which.
  - A reviewer treats any skipped or excluded test as a Fail.
- Game-grade tolerances: follow the envelope in [docs/gpu-f32-physics.md](docs/gpu-f32-physics.md#game-grade-envelope); numerical residuals clamp or continue, never fault the tick; proof-grade certificates are not acceptance criteria.
- **TypeScript, not JavaScript (owner, 24 October 2026).**
  - Code that cannot be C# (browser and worker glue, client runtime, node harnesses, tooling) is written in strict TypeScript (`strict: true`, no `any` escapes).
  - Shipped JS is only the output of a pinned `tsc` build that runs inside the normal build, publish and CI. No hand-written `.js` is committed in runtime or tool sources.
  - Tests run against the compiled output that ships.
  - Existing hand-written JS is converted by a dedicated slice. New or changed runtime and tool code from then on is TypeScript.
- Use C# wherever possible. Closed sets are enums end-to-end in production, configuration, tests and automation: API parameters/returns, collections/keys, comparisons and control flow retain enum types. Named string constants, ToString, nameof, interpolation or parsing in domain logic do not substitute for typing. Extensible identities use strongly typed IDs and resource/external strings use named boundaries. Convert/validate strings only at genuine UI/serialization/external boundaries; reject unknown/undefined values. Compile affected callers and test changed canonical mappings/rejection. Existing violations remain required refactoring; no repository-wide compliance claim before the verified audit.
- Preserve the approved palette; follow [DESIGN.md](DESIGN.md) for form, composition, lighting and motion.
- Use **Chrome through the available Playwright connector**. Check that connection directly before reporting it missing; an empty in-app Browser discovery does not establish unavailability. Do not substitute another browser.

Keep the current brief short: outcome, blocker/owner/retry condition, next acceptance check and authoritative evidence links. Update it when a result, blocker or candidate changes. Track verified delivery, blocked time, test duration and unnecessary repeats from existing records; unknown measurements stay unknown. Detailed [current requirements](docs/planning/requirements.md) remain required, without turning each administrative row into a new project.
