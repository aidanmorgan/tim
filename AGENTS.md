# Project rules

- Current priority: implement the outstanding puzzle-component families first. Defer exhaustive difficulty/nudging sweeps and the full campaign playtest matrix until the component set is implemented. Continue focused correctness, build, Reset and real-UI Playwright behavioural proof for each individual puzzle element; preserve all existing difficulty evidence. Expand/rework the 75-level campaign to teach the components, without letting difficulty testing delay component coverage.

- Goal: implement all different puzzle elements tracked in TODO.md and its linked component research, not merely one representative of each family. Track each element separately through implementation, sufficient verification, commit and push; do not silently drop or defer an element out of scope.
- Every part must be proven working through real-UI Playwright tests. This applies to all existing catalogue parts, fixtures and new additions—not just one representative per family. No part is complete without its own identifiable evidence; previously shipped parts are not exempt.
- For each part, construct or exercise it using actual UI controls, verify intended behaviour and a meaningful negative/control case, demonstrate applicable connections/integration, and confirm exact construction restoration after Run/Reset. Verify the actual placed configuration and typed connections; a successful lifecycle or a part appearing on screen is not behavioural proof. Cover distinct supported modes where relevant (for example each logic operation or optical channel).
- Record reproducible Playwright recipes/actions, tested revision, assertions/observations, result logs, relevant screenshots/motion captures and retained failures per part. Native tests, compilation, builds, reference solutions and fake-page adapter tests supplement but never replace real-browser proof. Re-run affected part proofs when implementation changes invalidate earlier evidence; keep missing/stale evidence explicitly incomplete.
- Also prove relevant boundary cases, Reset/save restoration and a production build. Deferring the exhaustive campaign/difficulty matrix never defers the mandatory focused Playwright proof for each part.
- Commit and push each individually verified new element before moving on to the next. Keep unfinished requirements and failed verification evidence explicit; do not batch several new elements into a later commit or wait for the entire 75-level goal to finish before publishing verified progress.
- Always refactor forward. Never add fallback paths, backwards compatibility, legacy modes, compatibility shims, old-name aliases or automatic format migration.
- Update current implementations, callers, authored content, tooling and tests together. Reject unsupported inputs explicitly; do not silently substitute another implementation, infer obsolete fields or downgrade behaviour.
- Preserve historical playtest artifacts unchanged as evidence, not as supported current input.
- Use C# wherever possible. Use enums for closed sets and typed identities or centralized constants for extensible names; avoid magic-string protocols.
- Preserve the current colour scheme. Follow DESIGN.md for Monument Valley-inspired form, composition, lighting and motion without replacing the approved palette.
- The current campaign target is 75 progressively taught levels. Track actual implementation and verification status in TODO.md; do not equate passing reference solutions with completed repeated difficulty testing.
- Browser playtests must use real UI actions, not game-state setters, imported solutions or numeric placement menus. Retain failed attempts.
