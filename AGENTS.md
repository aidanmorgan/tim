## Focused execution

Apply the [focused engineering rules and role prompts](docs/delivery-workflow.md#focused-agentic-engineering): state material assumptions, choose the simplest complete design, limit changes to the affected dependency closure, and define observable success before implementation. For an authorised backlog goal, finish and verify the current slice, complete required publication, then continue to the next ready TODO-linked outcome. A request confined to one change does not authorise executing the backlog. Reassess stalled work using the workflow's progress trigger; do not weaken gates or turn supporting administration into a new project.

## Delivery slices and independent review

Implement one small functional slice: one behavior, defect or invariant plus its necessary callers, content, tests and documentation. Select its bounded [INVEST scope](docs/planning/invest-index.md), then read the exact source acceptance and technical prerequisites; card summaries cannot waive them. Use a dedicated implementation subagent and a different independent adversarial review subagent; the coordinator delegates, reconciles results and reports status. Keep that pair through debugging and forward fixes. Self-review never qualifies.

Related design, implementation, cleanup, tests, UI proof, evidence and status updates are criteria inside that slice, not separate assignments or terminal administrative gates. Preserve every requirement ID and acceptance criterion. Do not combine several new puzzle elements. Genuine technical prerequisites and necessary design decisions must pass their required stage before dependent work; historical row order alone is not a dependency. Apply [REQ-14 and the slice workflow](docs/delivery-workflow.md#paired-subagent-workflow).

The reviewer independently inspects the actual diff and requirements, derives expected outcomes, investigates direct/transitive impacts and runs affected positive, negative/control and boundary checks. Retain a justified criterion/impact matrix, distinct actual identities, raw commands/results, findings and a terminal verdict. Runtime changes need the applicable builds, actual Chrome/Playwright behavior, lifecycle and performance proof; documentation/research need source, link, preservation, dependency and consistency checks. Unknown coverage or missing/stale proof is Incomplete; a known violation is Fail. Only zero unresolved unintended regressions within the justified scope permits Pass.

Return findings to the same implementation owner and independently re-review affected fixes. A reviewer who changes a deliverable becomes an implementer and needs another independent reviewer. The verdict and review-only evidence do not create a recursive work item.

## Scoped evidence and publication

Track drift during edits. At a coherent frozen review boundary, refresh applicable current views and run required schema, membership and deletion audits. Keep one immutable scoped snapshot for that candidate, exact source/relevant input and artifact identities, one review record and references to original raw evidence. Do not repackage after every edit, duplicate manifests, self-hash records, or make future receipts inputs to their own approval. Follow [evidence identity and hashing](docs/delivery-workflow.md#evidence-identity-and-hashing): reuse established exact identities; compute scoped hashes at acceptance boundaries or when relevant inputs change, not on every read, status edit or test.

Select checks by actual impact: callers/consumers, shared state, content/serialization, builds/tools, lifecycle/resources and worker clocks. Shared or unknown impact broadens scope. Reuse unchanged independently reviewed proof only after the reviewer establishes its original identity and current relevant-input/contract/environment applicability. Unrelated HEAD or whole-workspace diff changes alone do not invalidate it. Repeat checks only for changed relevant inputs, findings or unresolved concerns. Required global audits remain required; keep unrelated failures explicit with owner and justification. Never claim global or runtime qualification from a scoped Pass.

Mandatory Anvil validation runs before each write; normal pre-commit protections remain. Do not introduce a generator, schema, cache or metrics platform as a prerequisite to this workflow.

For required publication, independent SnapshotApproval first verifies every pre-publication criterion for the exact candidate and enumerates genuinely publication-dependent checks. Only then may the implementer commit/push/deploy that snapshot. Completion and dependent slices remain blocked until the reviewer verifies remote/deployed identities and all required production-origin behavior/performance and records terminal Pass. Changed relevant inputs invalidate affected approval. Receipts do not replace deployed checks. Non-publication work proceeds directly to terminal review.

Update current callers, authored content, tools, tests and active docs together; reject unsupported inputs explicitly and atomically. Historical artifacts remain unchanged evidence, not supported current input.

Named string constants, ToString, nameof, interpolation or parsing in domain logic do not substitute for typing. Convert/validate strings only at genuine UI/serialization/external boundaries; reject unknown/undefined values. Compile affected callers and test changed canonical mappings/rejection. Existing violations remain required refactoring; no repository-wide compliance claim before the verified audit.
