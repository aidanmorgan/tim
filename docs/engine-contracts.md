## Ownership and assemblies

The browser owns construction interaction, Scene Graph authoring, input, and final property application. A portable typed compiler validates immutable construction and transforms the Scene Graph into flat, value-only declaration tables for the Physics Graph. The independent simulation worker owns discrete commands, controllers, transactions, reliable publication, and the unified physics engine: a high-performance C# WebAssembly runtime leveraging 128-bit SIMD (`wasm-simd128`) to execute numerical motion, forces, dynamic AABB BVH spatial queries with velocity fattening, contacts, Disjoint Set Union (DSU) simulation islands, Box2D v3 Temporal Gauss-Seidel (TGS) Soft constraints, multi-domain networks (electrical supply over compiled routes today; optical rays and acoustics as their stories land), and finite energy stores. All physics advances at a fixed 120 Hz tick with 480 Hz substeps on the dedicated WASM SIMD worker with strictly zero element-specific solvers, zero per-part update loops, and zero element-selected kernel branches. It publishes committed poses directly into a lock-free zero-copy triple-buffered ring in `SharedArrayBuffer` using atomic sequence counters, eliminating GPU-to-CPU readback stalls. Every mutation reaches it as a typed, sequenced command with a receipt; every read is the committed read model, the pose ring or a typed query; one-shot occurrences travel only on the event ring. The independent animation worker owns cosmetic phase and procedural effects, running at 60 Hz completely decoupled from physical truth, fed one-way by committed physics results. Animation is entirely data-driven: cosmetic curves, squash-and-stretch, motor spin, indicator/UI easing, and particle effects evaluate declarative bindings to committed physical poses, committed level states and one-shot ring occurrences, with strictly zero per-element animation scripts or callbacks in the animation host. Browser rendering follows the display clock (30–60 FPS), issuing instanced draw calls (`gl.drawElementsInstanced` in WebGL 2, `renderPass.drawIndexed` in WebGPU) reading directly from the shared pose ring.

Every mutable field, map, cache, buffer and property has one writer and an explicit lifetime. No Godot object/reference or live scene read enters worker contracts. Preserve full authored affine geometry/material semantics; a convex affine transform cannot silently become a normalized rigid pose. Validate singular/unsupported transforms and numeric local-coordinate bounds before installation. Queries, broadphase, colliders, support footprints, swept corrections and presentation all bind the same typed geometry identity/revision. Replace collider geometry/material/participation and query metadata atomically; restore old metadata with its snapshot.

Retain specialized timer/controller arrays, animation slots/versions/free lists, spatial hierarchies and transaction participants inside their correct owners. No ECS or new storage platform is a prerequisite. Every current component override, internal body, fixture, material, shape and direct/transitive query consumer participates; a representative part cannot close the owner audit. Compiler, host, solver, animation and presenter cutovers update current callers/content/tools together and remove obsolete routes. Never create backwards compatibility shims, helpers, or bridges; all refactoring is forward-only.

## General data-driven physics and animation engines

The [general-engine execution design](general-engine-design.md) specifies declaration records, compiler admission, WASM SIMD128 dispatch, shared animation, and presentation. Its [complete source composition map](planning/general-engine-element-map.md) retains every planned source and explicitly owned model gap; a mapping is not runtime qualification.

**Tri-Graph Architecture and Compile-to-State.** The engine decouples into three independent graphs with clear responsibilities and one-way synchronization:
1. **Logical Scene / Machine Graph:** Main-thread authoring model. Represents hierarchical puzzle elements, typed sockets, logical connections (wires, belts, pipes, axles), UI selection, and serialization. It handles user interactions, drag-and-drop placement, rotation, and connection wiring without knowing solver internals or GPU vertex formats.
2. **Physics Graph:** Compiled at Run from the Scene Graph into flat, contiguous Structure-of-Arrays (SoA) SIMD-aligned memory tables. Represents rigid bodies (mass, inertia, velocities, transforms), colliders, Box2D v3 TGS Soft constraints, force regions, finite energy stores, sensors, and multi-domain network nodes across mechanical, electrical, optical, acoustic, and pneumatic domains. All physics is simulated through a unified, generalised, data-driven engine on a dedicated WASM SIMD Web Worker advancing at a fixed 120 Hz tick with 480 Hz substeps. Strictly zero element-specific solvers, zero per-part update loops, and zero element-selected kernel branches exist in the physics engine. Broadphase collision detection uses a Dynamic AABB BVH with velocity fattening; island partitioning uses Disjoint Set Union (DSU); narrowphase collision detection uses generic analytic manifolds (Sphere, Box, Plane, Capsule, Compound Cylinder) and signed distance fields (SDF); and multi-domain physical fields execute through shared capability kernels. Designed to support hundreds of concurrent puzzle elements with sub-millisecond execution times.
3. **Rendering Graph:** GPU-instanced draw batches on the browser main thread. Groups static and dynamic meshes by material and geometry into instanced arrays. Consumes interpolated transforms from the zero-copy `SharedArrayBuffer` pose ring and cosmetic secondary animation offsets from the Animation worker. Fully compatible with both WebGL 2 and WebGPU.

**One-Way Data Flow and Decoupled Animation.** Data flows strictly one-way: physics → animation → renderer and physics → renderer; nothing flows back into physics. Rates are ordered: physics (120 Hz with 480 Hz substeps) > animation (60 Hz) ≥ renderer (30–60 FPS, display-paced). Physics always updates faster than rendering, and rendering never influences physical results. All animation executes on an independent Animation Web Worker at 60 Hz, completely decoupled from physical truth. Animation is entirely data-driven and event-driven: cosmetic curves, squash-and-stretch, motor spin, indicator/UI easing, and particle effects evaluate declarative bindings to committed physical poses, committed level states and one-shot event-ring occurrences. Strictly zero per-element animation scripts or callbacks exist in the animation host.

<a id="zero-element-assumptions-contract"></a>

### Zero Element Assumptions & Generic Combination Contract

All subsystems across authoring, compilation, simulation, animation, and presentation must strictly comply with the following non-negotiable architectural invariant:

1. **Zero Element Assumptions:** The engine runtime makes strictly zero assumptions regarding which puzzle elements exist, have been loaded, or will be instantiated. No part is designated as "built-in" or "special"; all parts are discovered dynamically from data declarations.
2. **Universal Combination Support:** The engine must support ANY arbitrary combination of puzzle elements without special-case handling, part-checking conditionals, or hardcoded couplings. Any element may interact, collide, or connect with any other element provided their shapes, materials, and typed port contracts match.
3. **Homogeneous Mathematical Execution:** All physical simulation (rigid body dynamics, narrowphase analytic manifolds, TGS Soft joints), multi-domain networks (compiled electrical supply routes, discrete activation DAGs), animation tracks, and GPU draw batches operate exclusively on homogeneous mathematical tables and generic capability structures.
4. **Absolute Prohibition of Identity Branching:** No subsystem (including the physics compiler, solver kernels, animation host, and UI interaction router) may branch, switch, or execute conditional logic based on a part's identity, class name, or perceived purpose. When two parts collide or connect, the interaction is governed 100% by universal physics manifolds, contact materials, and declared port contracts.

<a id="element-bundle-loading-contract"></a>

### Element Bundle Loading Contract

The element bundle is the only declaration source the game loads ([invariant 2](architecture/element-package-isolation.md#target-invariants)):

1. **Packages:** Each puzzle element is declared only in its own `elements/<Name>/` project, which references only `CuriousContraptions.Abstractions` and the domain Abstractions it needs. Adding an element adds a package and nothing in the engine, the workers or the UI.
2. **Build-time discovery:** An MSBuild target runs `tools/BundleElements` before the Godot export and before publish. It discovers packages by globbing `elements/*/*.csproj` and reflecting over `IPuzzleElementDeclaration` implementations; there is no hand list. Generation fails the build, naming the package and field, for a duplicate id, a non-finite value, an undefined enum value or a body without a collider.
3. **Start-up loading:** `PartRegistry` loads only the bundle. Each definition is a plain runtime record built from one bundle entry, and its scene loads from its package path (`res://elements/<Name>/…`). A missing or structurally invalid bundle stops start-up with an explicit message naming the problem; nothing is loaded from elsewhere.
4. **Identity:** Each element's identity is the typed id the bundle issues. Saves and messages carry that id. There are no named element constants, numeric id switches or closed element enums.
5. **Palette:** The Free Workshop palette lists every bundle element, grouped by its declared category, with no static inventory list.
6. **No versioning:** The bundle has one schema and carries no version field, generation timestamp or version check (owner, 21 Oct 2026). Structural validation is the only admission rule.

<a id="element-bundle-schema-contract"></a>

### Element Bundle Schema Contract

Every bundle entry is typed, and every field is written bit-exactly and read back bit-exactly (a round-trip test proves each package's declaration equals its deserialised entry, f32 bit for bit):

1. **Encodings:** f32 game values are IEEE-754 single precision, written in shortest round-trip form. Vectors are `[x, y, z]`; quaternions are `[x, y, z, w]`. Enums are written by name; an unknown name, or a number in place of a name, is rejected. Integers and ids keep their integer types.
2. **Metadata:** a unique canonical element id, an enum category (the palette's Motion, Goals, Power, Control or Structure), a display-name key, the icon path (null until the element ships its icon) and the element's `.tscn` scene path.
3. **Typed parameter schema:** each parameter declares its key, its unit enum, an enum kind (Real, WholeNumber, Boolean or Choice), and an f32 minimum, maximum and default; a Choice also lists its option names, and its bounds and default are option indices. Instance values are validated against this schema; there is no property bag.
4. **Footprint:** the bodies, moving bodies and prismatic constraints one placed instance adds to the compiled scene.
5. **Ports:** typed socket id (the socket's name), domain, direction, the signal kind of a signal port (Pulse or Level), local position, normal and the `Loc_Port_<Id>` locator node.
6. **Colliders:** shape kind enum, half-extents (a sphere's radius on every axis), local offset, local rotation and material (restitution, friction, rolling resistance $C_{rr}$, bounce threshold).
7. **Mechanical payload:** body motion kind, mass, principal inertia, material, and joint and prismatic anchors.
8. **Electrical payload:** source, consumer and switch nodes and their supply parameters.
9. **Signal payload:** contact triggers, latch, counter and timer declarations.
10. **Events and bindings:** the capability-named event kinds the element can produce, and its presentation bindings (target node, property, from/to, curve and driving source: a committed level state or a one-shot ring occurrence).

Admission rejects explicitly a missing or duplicate required field, an unknown field, an undefined enum value, a non-finite or out-of-range value, a duplicate id and a dangling reference.

<a id="locator-anchored-sockets-contract"></a>

### Locator-Anchored Mesh Sockets Contract

1. **Locator Naming Convention:** All connection socket anchors in an element's `.tscn` scene follow the canonical naming convention `Loc_Port_<Id>`, named exactly by the declared typed socket.
2. **Runtime Resolution in `MachinePart`:** Sockets resolve their local transforms from the locator nodes. No hardcoded vector tables or static position switch statements are permitted.
3. **Secondary Body Transform Tracking:** Locators attached to secondary moving components (such as rotating motor shafts or pivoting lever arms) inherit the dynamic transform of that sub-mesh during runtime/preview. Connected cables, belts, and links update their endpoint anchors without per-element scripts.

<a id="element-scene-contract"></a>

### Element Scene Contract (`.tscn`)

The authored element asset is the element's own Godot `.tscn` scene in its package (owner decision, 18 Oct 2026):

1. **Visual nodes:** PBR surface meshes (base color, roughness, metallic) adhering to the palette and sculptural aesthetic in [DESIGN.md](../DESIGN.md).
2. **Collision proxy nodes:** separate, non-rendered analytic proxies named by prefix: `col_box` (half-extents), `col_sphere` (radius), `col_capsule` (radius and half-height), `col_cylinder` (radius and height) and `col_hull` (convex hull).
3. **Locators:** empty `Loc_Port_<Id>` nodes for every declared socket.
4. **Articulated sub-trees:** moving sub-components (motor shafts, springboard plates, lever arms) are child branches carrying their own visual, collision and locator nodes.
5. **No code-defined geometry:** procedural mesh construction and hardcoded coordinate or collider tables in C# are forbidden.
6. **Extraction:** collider and locator extraction reads only the dedicated proxy and locator nodes, with no element branching. Under Story 9A.16 it runs at build time and its output is baked into the bundle, which is then the compiler's only collider source.

<a id="multi-domain-port-contract"></a>

### Multi-Domain Port Compatibility & Validation Contract

Connections between ports are validated by the compiler under strict mathematical and physical invariants:

1. **Domain Equality:** A connection is valid if and only if both endpoints share identical domains:
   $$\text{Domain}(P_{\text{source}}) == \text{Domain}(P_{\text{target}})$$
2. **Directional Pairing:** Exactly one Exposed (`Output`) port must connect to an Accepted (`Input`) port. Connecting two outputs or two inputs rejects at admission with an explicit validation error.
3. **Cardinality Rules by Domain:**
   - **`Electrical` Domain:** Multi-drop branching permitted. One power source may feed multiple parallel inputs; at Run the compiler builds one supply route per consumer over the reachability graph (direct, or switched through a committed contact), and the shared allocation debits finite supply. Modified Nodal Analysis (node potentials and branch currents) is a named later capability, added as a generic kernel by the first element story that needs it.
   - **`Activation` Domain:** Fan-out permitted (one trigger output can signal multiple inputs). Inputs receive discrete activation events at the start of the simulation tick.
   - **`Mechanical` Domain:** Bilateral 1-to-1 constraint pairs (e.g. shafts/belts). Solved via Box2D v3 TGS Soft kinematic ratio constraints.
4. **DAG Cycle Prevention for Instantaneous Signals:** For direct, unbuffered activation or logic signals, cyclic graph topologies without a stateful delay (e.g. `CAT-045 Delay` or finite-time buffer) are rejected during graph compilation to prevent infinite recursion within a single tick.

**Never implement a per-element solver or animation evaluator.** Elements supply typed declarations: geometry, bodies, materials, constraints, stores, sources, sensors, controller operations, animation curves/tracks, transitions, and target bindings. Shared physical laws and shared animation evaluators consume those values. Catalogue/part names, IDs, or concrete classes must not select equations, collision responses, sensor algorithms, or cosmetic update loops; instance IDs identify state and bindings, not bespoke behavior. Adding a new puzzle element means adding its declaration data (the physics capabilities it instantiates, parameters, art, and animation bindings) and nothing in the solver or the animation engine.

When a required element exposes a missing capability, extend the reusable engine law, sensor/controller primitive, or animation evaluator with explicit typed parameters and independent acceptance. Deliver that extension with the current consuming slice; each later physical domain is added as a generic capability inside the slice that first needs it, never as an element-specific path, and no universal framework is built first. Domain-specialised capability kernels selected by declared data are valid; element-selected kernels are not. Capability-named `ActivationNodeKind` values selected by declared data are valid; element-named event kinds (such as `CounterReached` or `LatchSet`) are not, and event kinds name capabilities (such as `ThresholdReached` or `MemoryChanged`). Element-specific assets, shapes, parameter values, and declarative compositions remain valid; hidden executable callbacks or element-keyed branches do not become data merely by being registered.

Animation definitions use reusable typed curves, tracks, state, and transitions driven by admitted commands, committed level states read from the committed read model, one-shot occurrences read from the event ring with the consumer's own cursor, and the shared clock. A level state is never relayed as an event, and a one-shot occurrence is never inferred by diffing published reads on the main thread. The Animation worker evaluates them; the browser binds and applies results to element-specific art. Physical/contact-bearing motion remains Simulation-owned. No per-element worker switch, private cosmetic scheduler, or presentation feedback into physics is permitted. Preserve canonical IEEE-754 `f32` values, WASM SIMD128 physical authority, separate workers, lifecycle, and single-property ownership.

For each affected capability, inspect the declaration-to-execution path and prove it with varied parameters/instances or an unfamiliar declaration composition, plus a meaningful negative/control and unsupported-input rejection. Within an already supported capability, a differently named element must need only declarations/bindings/assets and its proof, with no solver/evaluator source edit. A genuinely new capability needs its general engine extension and proof first. Retain every named element's actual UI, Reset/save, lifecycle, performance, and publication criteria; reuse proof only under the existing applicability rules. All refactoring is forward-only; zero backwards compatibility shims are permitted.

## Stable identities and construction

A construction owns a nonzero 128-bit DocumentId and monotonically allocated nonzero U64 identities. Typed entity, body, collider, joint, connection, capability, observable, target and goal IDs share the document allocator; deleted values are never reissued. Allocation is transactional and exhaustion rejects. A failed unpublished candidate restores the allocator exactly, with no escaped ID.

Definitions declare explicit stable U32 member keys, never array ordinals. Persist typed child IDs by member key/kind; movement, save/load, recompilation and storage compaction preserve them. Matching key/type may survive a definition replacement; absent members retire and new members receive new IDs. Slots, tree traversal, Godot instance IDs, runtime handles and hashes of display names cannot become public identity.

Definition, geometry and puzzle registries use typed U64 IDs with exact registry SHA256 handshakes; adding entries cannot renumber existing ones. Worker session is 128 nonzero bits. Positive signed-I64 world/query generation (at most I64.MaxValue) qualifies installed IDs; Reset/Load retain authored IDs but invalidate old-generation references. Animation has separate positive U64 generations and independent standalone-UI registrations. No counter wraps.

Compile in explicit stable order: entity/member, connection, capability, observable, target/property. Contact order uses ordered body/collider pair then declared feature identity, including equal-time events; broadphase/packing order must not select numerical reduction order. Preserve replay within the qualified same environment; cross-device numerical outcomes use declared IEEE-754 f32 bounds and exact discrete order.

Construction includes document/registry/allocator/puzzle identity, precision/mode/environment, every entity/definition/locked state/pose and declared initial root/internal-body motion, typed parameters/member maps, assistance knots, typed connections and goal predicates. All floating game quantities store standard IEEE-754 f32 floats (single-precision 32-bit floating point). Every required field appears exactly once; reject missing/duplicate/unknown fields, undefined enum values, invalid identities and collapsed numeric controls. No arbitrary property bag, inferred default or old-format migration.

A construction has no fixed entity, connection, goal or placement-target count: every table is sized from the scene and memory is the only bound (owner, 20 Oct 2026; Story 9R.5b). A fixed count exists only where a written requirement states it; content is never dropped. Exact field layouts are reviewed P0-008/P0-016 decisions before a variant is admitted. Formats carry no version numbers (owner, 21 Oct 2026); the retired F64 byte layouts are not a current schema.

Parameter declarations retain every named field/unit and mode: ball radius/mass/restitution/buoyancy/drag/rolling resistance; wall dimensions; ramp dimensions; pipe length; receiver threshold; clock interval; counter integer target; pressure minimum mass; Hold/Delay duration; weight mass; spring stiffness/damping/precompression; trampoline tension/damping; clutch close duration; cannon capacity/charge power; motor speed/torque; wound-spring stiffness/stroke/lead; battery enabled; pusher stroke/speed/acceleration/force; conveyor dimensions/surface-per-radian; bumper strength; fan supply/force/reach/width; bellows force/reach/width; windmill response; lever mass/initial angle. ## Wire and admission

Use little-endian exact U8/U16/U32/U64 and signed I64 where declared, strict Boolean 0/1 and explicit enum tags. JS uses exact BigInt/DataView operations for 64-bit identities/ticks, never Number or JSON numeric conversion. External diagnostic U64 is exactly sixteen lowercase hex digits; session text is thirty-two; I64 decimal has no plus, padding, leading zero or negative zero. Domain logic never parses these external forms.

All physical/game-value payloads carry standard IEEE-754 f32 floats; validate finite values and preserve canonical admitted representations. Do not normalize rotations or reconstruct wide hidden state in a codec. Platform clock readings retain declared integer nanosecond adapters. Resource/presentation UTF-8 is strict, NUL-free and bounded to 4096 bytes; strings do not select domain behavior.

Each envelope identifies message kind, total length, actual sender/recipient role, outbound/return leg, session, world generation, edge sequence, commit tick/revision, topology revision and BufferId. No pointer, closure, heap view, scene object, local slot or executable declaration crosses the boundary. Validate checked lengths before allocation, then schema/route/session/generation/discriminants/intrinsic values/identity before mutation; reject truncation, trailing bytes, unsupported flags, unknown tags and conflicting duplicates.

Required message families are Hello/Ready/Fault/Credit/Acknowledge; simulation commands/results; complete physical samples, occurrences and topology; query/results; construction/transfer seal/save; animation definitions/commands/results/samples; clock probe/reply; diagnostics. Hello/Ready match build/schema/registry hashes and actual role. A physical sample is complete coherent state, never a partially installed delta. Cold topology/construction transfers install only after contiguous exact chunks, bounded complete length and digest seal; failed decode preserves the installed world.

Admission, application commit, recipient application and durable save are separate outcomes. Requests retain original generation/sequence, target identity, required revision/dependency, application tick/phase/order and exact immutable payload. Duplicate pending/terminal/already-acknowledged inputs preserve their original meaning; conflicting duplicate, gap, stale generation, late/far-ahead target and capacity shortage reject explicitly. No automatic retry turns a lost reply into a second effect. ExactTick requires committedTick < T ≤ committedTick + 1200, with no silent rescheduling; future pending commands cannot block due controls. DependencySequence names a lower admitted same-generation command and must have Applied before execution; retain dependency satisfaction before result acknowledgement. Failed/cancelled or unresolved-at-exact-tick dependency yields DependencyFailed. Same-tick inputs compare one common pre-tick revision and commit one tick/revision/result transaction. Replay is bounded to the admitted 30-second Run (1800/3600/7200 ticks at 60/120/240 Hz); its recording is sized from that Run, and a recording that cannot be completed is explicit incomplete evidence and cannot alter physics.

A current codec requires a complete field/width/unit/route/length table for every admitted variant, canonical enum mappings, exact command/query/animation result and cancellation rules, independent malformed/extreme/2^53-neighbour/stale-slot fixtures and current caller compilation. P0-016 owns this forward ABI work; unadmitted variants remain explicitly unsupported. The Workshop command/response wire, its cadence settings record and the construction save carry no format version (owner decision, 21 Oct 2026: the browser and its workers ship in one bundle with one schema); input that is not structurally valid for that schema (FlatBuffers verifier, widths, zero padding, enum ranges, construction validation) rejects with the typed refusal rather than supplying defaults. No other envelope, record, ring, trace line or handshake carries a version either (Story 9A.1): where a version word once stood, the bytes are zero padding that rejects when set.

## Reliable storage and leases

**Superseded counts (owner, 20 Oct 2026; Story 9R.5b).** No transport table has a fixed capacity: lease pools, retained requests, results, queries, occurrences and batches are sized from the scene and the admitted workload, and memory is the only bound. The specific counts and byte budgets in this section are void unless a written requirement restates them. The ownership, return, charging and ordering rules below stay current.

Every edge direction has separate caps of 56 data leases/504 KiB and 8 control leases/8 KiB; a control allocation is at most 1024 bytes. Categories cannot borrow. The lease ledger records original edge/session/nonreused BufferId/sequence/bytes/category and ownership phase. Transfer detaches the buffer; exactly one context or transport owns it.

Return the same allocation as Credit, with validated identity, original charged length and explicit zero padding. Return consumes no reverse-edge credit and receives no further Credit. The original edge stays charged through the whole round trip. Reuse allocates a fresh identity; stale returns cannot release it. Free pooled and leased allocations both count. Fan-out charges each copy.

Process returns before new outbound messages. A receiver must return a request without waiting for a reverse response lease; reserve reliable result/event storage before physical commit and send retained semantic responses when capacity exists. Control saturation must still permit returns/acks. Fault is a bounded sticky typed record with exact repeated-fault count, not an unlimited queue. Reliable occurrences/results do not coalesce; monotonic acknowledgement watermarks may.

Six 512 KiB edge pools, three 1 MiB transfer staging buffers and 2 MiB aggregate retained wire copies/packing scratch give the 8 MiB transport budget. That last 2 MiB is Simulation 1 MiB, Animation 768 KiB and Browser 256 KiB. Count limits never authorize uncounted payload bytes. One pending inbound object per recipient is at most 1 MiB. Simulation retains at most 128 ordinary and 8 lifecycle requests/results; queries at most 64 total across two generations; occurrences at most 1024 retained/staged per required recipient. Lifecycle batches contain at most 8 requests; ordinary/query/animation request batches at most 32. Current f32 byte-layout arithmetic must also fit these fixed quotas and pass simultaneous saturation controls.

Transport Return does not release a semantic request/result. Results and queries retain original generation/sequence and required/read revision until contiguous acknowledgement. Query Cancel has its own slot/result and its target resolves once; Reset cancels pending queries while completed terminal outcomes remain unchanged. Topology installation acknowledgement is distinct from transfer-disposal acknowledgement; state delivery waits for installation.

Animation requests route only browser→animation; unsupported simulation/animation reverse routes reject. Controls wait for registration acknowledgement. Animation applies admitted browser requests before physical-feedback evaluation.

Animation UI/world streams share one aggregate 128-entry request/result pool and at most two retained result generations, not separate allowances. Retire/acknowledge the old world generation before admitting new-generation results; UI remains live within the same caps. Navigation replaces world then UI without a third result window. Target/property claims never overlap; attempted external instance IDs are not reused.

## Lifecycle and atomicity

Host modes are Building, Running, Paused, Completed and Faulted. Completed retains runtime state for display after goal or the declared Run limit; it is not editable construction. Session phases are Starting/Ready/Recovering/Disposed/Unsupported; transition phases are Idle/Preparing/Committing/AwaitingRecipients. Browser operation outcomes distinguish admission, commit, application, completion, rejection and indeterminate process loss.

Startup uses a fresh session, generation 1, revision 0, tick 0 and empty validated Building construction before explicit initial ReplaceConstruction. No user command is admitted before matching readiness and clock/capability checks. Return/ack/fault handling remains available during barriers. Cancel discards only precommit candidates and cannot undo an installed world. New Reset/Load cannot overtake prior completion or exceed retained-generation bounds.

| Command | Building | Running | Paused | Completed | Faulted |
| --- | --- | --- | --- | --- | --- |
| ReplaceConstruction | Build candidate | Build candidate | Build candidate | Build candidate | Only safe recovery |
| Create/Replace/Remove entity; Connect/Disconnect | Apply | Reject | Reject | Reject | Reject |
| Binary/Scalar input; Pulse | Reject | Apply at admitted tick | Wait for Step/Resume tick | Reject | Reject |
| Run | Running | Reject | Reject | Reject | Reject |
| Pause | Reject | Paused | Reject | Reject | Reject |
| Resume | Reject | Reject | Running | Reject | Reject |
| Step one tick | Reject | Reject | Paused or Completed | Reject | Reject |
| Reset | Building | Building | Building | Building | Only safe recovery |
| Save construction | Apply | Reject | Reject | Reject | Reject |
| Cancel | Apply | Apply | Apply | Apply | Only usable coordinator |

Run captures exact construction, retains generation, starts tick zero and increments revision once. Reset restores captured pre-Run construction; Building Reset preserves current construction but still advances generation. Load/Reset advance generation and revision once, tick zero. Each gameplay tick increments revision once; Step does not add a second revision. Successful Save/Pause/Resume/Cancel increments once; rejected application does not.

WASM solver completion and validation precede publication/commit. The commit region contains only prevalidated assignments and checkpoint release: no allocation, serialization, external callback, transport send or fallible resource disposal. Precommit failure restores all authority and resources; all restoration participants are attempted and failures retained. ReversibleFailure permits explicit Reset/Load/Cancel from known-good construction, never hidden Run retry. IntegrityLost requires explicit session recovery. ## Clocks, histories and performance

Game values evaluate as IEEE-754 f32 through authoring, solver, committed reads and presentation. Game timestamps use the shared Abstractions `PhysicalTime` (u64 480Hz ordinal plus f32 phase in[-2048,2048),4096 units/ordinal); no floating absolute game-seconds counter is retained. Convert external native clocks to integral nanoseconds before internal arithmetic, and subtract integer anchors before local f32 motion/animation. The sole signed-nanosecond derivation/ring/interop layout and364-byte presentation diagnostic are specified in [shared clock cadence](shared-clock-cadence.md#integer-time-and-local-f32-evaluation). The member-level external adapter inventory and semantic controls live in `GameFloatGuardTests`; they do not exempt neighboring game members. PERF-40–45 and REQ-09/14 retain their current game-fidelity acceptance. Native proof is required now; browser and detailed performance qualification remain at their named gates.

Use one continuous session master clock owned by Simulation, with context-local monotonic integer nanoseconds only as calibrated measurement/wakeup adapters. All subsystem pulses derive from its admitted epoch and typed cadence configuration; no per-Run or frame-delta clock is an independent scheduling authority. The complete [shared-clock and configurable-cadence contract](shared-clock-cadence.md) defines exact rational pulse ordinals, lifecycle projections, supported rates, forward configuration admission and proof. The active defaults are 120 Hz simulation/four 480 Hz physical substeps, 60 Hz animation and 60 Hz presentation, with no player frequency controls. Retained internal configuration supports 60/120/240 Hz with eight/four/two actual physical substeps, independently selected animation and presentation cadences, and no dropped physics. Timers/display callbacks only wake scheduling. Future default changes require affected qualification; alternate internal profiles do not gate the active default merely because the protocol can represent them.

The Simulation's own event loop never answers a clock probe (Story 9.4b): solver ticks would delay it. A dedicated master context that the Simulation spawns and owns blocks on the session clock ring and stamps each probe in the Simulation's native domain, derived from the shared isolated time origin plus a correction the Simulation maintains (`WorkshopClockDerivation`). The derivation is never trusted once. Only an exchange whose Simulation [before, after] bracket is at most 0.0316 ms wide (twice the 0.0158 ms bound: the declared 100 µs uncertainty less the 84.1255 µs native error) is evidence; a wider or unanswered one proves nothing and is retried. Startup needs 16 narrow exchanges inside 500 attempts of at most 2 ms each (within the 5 s qualification deadline). An exchange the master has not yet taken (the master context still starting) is waited for, up to the same 2 ms per attempt, and is counted as unanswered only if that wait times out, so a slow master start does not spend the attempt budget. The isolated contexts' time origins differ by a constant of a few tens of microseconds (measured −27.5 to +7.6 µs in Chrome), so startup derives that offset: the startup correction is the centre of the corrections admitted by the most narrow exchanges (each admits the corrections that place its master reading within 0.0158 ms of its bracket), installed under the initial epoch before any requester qualifies. A narrow exchange that admits none of that common range is a scheduling outlier: at most four are set aside and counted (`startupOutliers`); more than four (no stable offset) or an exhausted budget refuse the session. A derived offset beyond 0.1 ms (the declared timestamp uncertainty) is applied like any other and recorded once as a typed, counted `CCGPU_CLOCK_OFFSET_WIDE` record carrying the offset and its admitted interval (D14 as amended 19 Oct 2026: each worker's time origin carries its own host-clock reference, so a host clock step can widen a legitimate session's offset, and the offset is corrected either way). Then one check every 100 ms, always between tick turns, keeps checking it: up to four back-to-back exchanges until one is narrow (the first wakes a master context asleep since the last check), all within one 2 ms exchange timeout in total, each retry counted; the check uses the narrow exchange, or else the last one answered. An exchange still unserved makes the next check return at once. A narrow inconsistent check moves the correction toward the bracket midpoint: an error of at most 0.1 ms slews by at most 0.005 ms per check (50 ppm, a tenth of every mapping's 500 ppm drift budget) under the same derivation epoch, so no requester mapping recalibrates; a larger error installs the midpoint under a new epoch, and every requester mapping recalibrates on the first reply of that epoch. Startup, every re-derivation, the first slewed, inconclusive or unanswered check of each run, and a summary every 100 checks are typed `CCGPU_CLOCK_DERIVATION` records carrying every counter; no check outcome stops anything. Because the master keeps answering while the Simulation's event loop hangs, clock replies never prove the Simulation alive: each check turn also advances a heartbeat word in the clock ring, and the Browser faults the session with a typed `SimulationUnresponsive` transport failure (the Workshop then shows the retired session) when the heartbeat has not advanced for 1000 ms of its own running service while the page is visible. A clock reply the wire decoder rejects is never applied or silently dropped: both requesters receive replies only through the wire's one reply path (`WorkshopClockWire.ReceiveEncoded`), which counts each one as exactly one typed `Malformed` `CCGPU_CLOCK_REPLY_REJECTED` record, which every Chrome suite fails on, and its probe expires on the ordinary mapping path. A requester waits for the master's reply at most the 250 ms probe lifetime (`ReplyWaitMilliseconds`); a reply still unwritten then is abandoned, so a dead master cannot pin a waiter. Only an accepted reply (the pending probe's own answer) can move a mapping's derivation epoch or recalibrate it; a stale or mismatched reply is classified first and changes nothing. A probe the master rejects (it does not own this session clock) and an accepted reply under a reversed derivation epoch are protocol violations and fail explicitly. A channel control that reaches the Animation worker while its installation is prepared or its mapping recalibrates is held unapplied and unacknowledged (capacity one, `AnimationControlDeferral`) as one typed, counted `CCGPU_ANIMATION_CONTROL_DEFERRED` record, and is applied by the first service turn with a committed installation and master time, which then returns without evaluating.

A lapse with a probe outstanding, a requester that kept running, and every other cause are not covered. Each recalibration is one typed, counted `CCGPU_CLOCK_RECALIBRATED` telemetry record naming its role and cause, and every Chrome suite fails on one.
