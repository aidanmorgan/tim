# High-Performance Generalised Data-Driven Physics Architecture

This document defines the numerical authority, compilation model, solver model, and game-grade tolerance envelope for the game engine. It supersedes earlier experimental WebGPU compute shader and half-precision (`f16`) specifications with an architecture designed for **hundreds of concurrent puzzle elements**, **universal WebGL 2 and WebGPU compatibility**, **standard IEEE-754 `f32` precision with WebAssembly SIMD128 vectorization**, and a **lock-free shared memory pose ring** (zero-copy exchange between the runtimes is the target of `ENGINE-WASM-THREADS`; see the isolation authority's [Current status](architecture/element-package-isolation.md#current-status)).

The engine operates under the [general data-driven engine contract](engine-contracts.md) and maintains **strictly zero external dependencies for physics** (no Box2D, no Jolt, no Rapier, no PhysX, and zero npm/NuGet physics packages). All algorithms, vector mathematics, spatial hierarchies, and constraint solvers are custom, data-driven implementations authored directly within this repository. Typed element declarations select reusable physical capabilities, never element-specific solvers, bespoke equation tables, or per-part update loops. Each puzzle element is declared once in its own `elements/<Name>/` package; `tools/BundleElements` writes the packages into one element bundle at build time, and the runtime loads only that bundle ([bundle loading](engine-contracts.md#element-bundle-loading-contract)), identifying elements by the typed id the bundle issues. New elements declare their capabilities, artwork, and bindings without engine enum edits or switch statements, and the Free Workshop palette lists every bundle element. The [sole design authority](architecture/element-package-isolation.md) governs this design; its Current status lists where the tree falls short. Missing behavior extends the general engine within its consuming slice. Domain-specialised capability kernels selected by declared data are valid; element-selected kernels are forbidden.

## Universal Web Platform Authority

### Dedicated Simulation Worker
Authoritative continuous mechanics, collision detection, constraint solving, and multi-domain physical fields execute exclusively on a dedicated simulation Web Worker. The solver is C# compiled to WebAssembly with 128-bit SIMD (`wasm-simd128`) enabled (`CuriousContraptions.Simulation/CuriousContraptions.Simulation.csproj:22`). Sub-millisecond execution across hundreds of bodies is the target of the performance stories `ENGINE-TICK-ALLOCATION` and `ENGINE-SOA-SIMD`, and same-build replay is exercised by the Reset and replay tests (`CuriousContraptions.tests/TrampolineTests.cs:2174`, `F32BehaviourIdentityTests`) but not established in general, with a canonical pair order the `ENGINE-SPATIAL-QUERIES` target; both are listed in [Current status](architecture/element-package-isolation.md#current-status). All solver arithmetic runs in the C# WASM worker; `CuriousContraptions.Simulation/wwwroot/worker.ts`, shipped as the compiled `worker.js`, is a host that forwards typed envelopes and copies committed bytes into the shared rings (`CuriousContraptions.Simulation/wwwroot/worker.ts:286-290`), with no physics. Position, rotation and velocity are committed as f32 through one canonical pose path. No half-precision lane remains ([precision status](#precision-status)); this is not a claim of complete SIMD or whole-engine f32 qualification.

### WebGL 2 Support (WebGPU as Target)
By executing the core simulation in vectorized WASM on a dedicated worker, the physics engine is completely decoupled from the underlying graphics API:
- The game renders through Godot's `gl_compatibility` renderer, which is WebGL 2 on the web (`project.godot:17-18`); WebGPU is a target of `ENGINE-INSTANCED-RENDERING`, whose first slice establishes whether it is reachable.
- No dependency is placed on optional or fragmented GPU features such as `shader-f16` or compute shaders in the graphics pipeline.
- WebGL 2 is the production target today; WebGPU joins it only through `ENGINE-INSTANCED-RENDERING`.

### Shared Memory Pipeline
The simulation worker and the browser main thread share a pre-allocated `SharedArrayBuffer` under cross-origin isolation (`crossOriginIsolated`). Today the pose ring in it has three fixed slots behind a sequence lock (`engine/gpu/WorkshopPoseRing.cs:14`, `CuriousContraptions.web/wwwroot/pose-ring.ts:13`, `:95-98`); it is written every tick, and a `PoseReader` is constructed on the main thread (`CuriousContraptions.web/wwwroot/workshop-client.ts:152`, `:256-257`) but never read. Each exchange costs at least one JavaScript-mediated copy per side: C# composes a new slot array (`engine/gpu/WorkshopPoseRing.cs:58-60`) that is marshalled to the worker, the worker copies it (`CuriousContraptions.Simulation/wwwroot/worker.ts:290`) and the ring copies it again (`CuriousContraptions.web/wwwroot/pose-ring.ts:96`). The renderer is fed by the whole per-tick FlatBuffers read, decoded on the main thread (`CuriousContraptions.web/wwwroot/workshop-client.ts:273-275` → `engine/gpu/BrowserWorkshopClient.cs:321-339` → `engine/MachineWorld.Gpu.cs:238-242`) and again on the animation worker (`CuriousContraptions.Simulation/wwwroot/worker.ts:292-293` → `CuriousContraptions.Animation.Worker/Program.cs:213-215`); each body is one node transform (`engine/MachinePart.cs:342-350`). No path reads GPU state back (`mapAsync` appears nowhere). Target: under `ENGINE-WIRE-ABI` the ring is multi-buffered with its depth derived from tick rate and render delay (owner decision 24k, 23 November 2026) and becomes the renderer's feed; under `ENGINE-WASM-THREADS` C# writes it in place with no producer copy and a consumer reads it with at most one copy; under `ENGINE-INSTANCED-RENDERING` the renderer uploads the poses to GPU instance buffers. Each is listed in [Current status](architecture/element-package-isolation.md#current-status).

The FlatBuffers wire (`schemas/workshop_wire.fbs`, `schemas/workshop_authoring.fbs`) is the control plane and the save. Every shared-memory and worker-message layout is hand-defined until `ENGINE-WIRE-ABI`, for example the pose ring (`engine/gpu/WorkshopPoseRing.cs:14-17`, `CuriousContraptions.web/wwwroot/pose-ring.ts:12-15`), the event ring (`CuriousContraptions.Abstractions/EventRingBuffer.cs:104-106`, `CuriousContraptions.web/wwwroot/event-ring-cursor.ts:14-20`) and the clock ring (`engine/gpu/WorkshopClockWire.cs:10-17`). The physics worker blocks in `Atomics.wait` for at most 2 ms per wait (`engine/gpu/WorkshopClockDerivation.cs:39`): at startup, qualification repeats such waits until it has 16 narrow exchanges, within 500 attempts, before the worker is ready (`CuriousContraptions.web/wwwroot/clock-ring.ts:243-251`; `engine/gpu/WorkshopClockDerivation.cs:13-17`, `:37-38`), and every 100 ms derivation check blocks the same way (`CuriousContraptions.Simulation/wwwroot/worker.ts:168`, `:179` → `clock-ring.ts:270`; `WorkshopClockDerivation.cs:40`). This is recorded, and it is changed only if the publication-path measurement (R6) shows it matters.

## Compilation Model and Tri-Graph Architecture

The game architecture strictly separates data and operations into three decoupled graphs optimized for their specific access patterns:

```
+-------------------------------------------------------------------------------+
|                       1. LOGICAL SCENE / MACHINE GRAPH                        |
|  - Owned by C# Main Thread (Authoring, Sockets, Parts, Serialization, UI)     |
|  - Relational graph: MachinePart nodes, declared ports, WorkshopConnection    |
+---------------------------------------+---------------------------------------+
                                        | Compile-to-State at Run
                                        v
+-------------------------------------------------------------------------------+
|                       2. PHYSICS GRAPH (Execution Core)                       |
|  - Owned by WASM Worker (byte records, constraints; target: SoA, islands)     |
|  - Topological: Bipartite graph (Bodies <-> Contacts/Joints)                  |
|  - Spatial: binary AABB BVH, speed-cap fattening (target: velocity)           |
+---------------------------------------+---------------------------------------+
                                        | Committed read (target: the pose ring, ENGINE-WIRE-ABI)
                                        v
+-------------------------------------------------------------------------------+
|                       3. RENDERING GRAPH (GPU Presentation)                   |
|  - Owned by Browser Main Thread (WebGL 2; target: WebGPU, instanced batches)  |
|  - Target: grouped by (MeshID, PipelineID), hundreds of instances in 1-2 calls|
+-------------------------------------------------------------------------------+
```

**Implementation status.** Every "flat", "contiguous" or "SIMD-aligned" table in this section is the target of `ENGINE-SOA-SIMD`. Today the body and collider tables are array-of-structures byte records with typed offsets (body 160 bytes, collider 96 bytes, `engine/gpu/PhysicsGpuAbi.cs:22`, `:45`); each tick copies the world (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:254`) and decodes it into pooled body and collider objects. Islands and sleeping (`ENGINE-ISLANDS-SLEEP`), the pose ring as the renderer's feed (`ENGINE-WIRE-ABI`) and instanced batches (`ENGINE-INSTANCED-RENDERING`) are also target; [Current status](architecture/element-package-isolation.md#current-status) lists each with its owner.

### 1. Logical Scene Graph (Machine Graph)
The authoring representation manipulated by the player in build mode. It maintains high-level entity hierarchies, declared port connections (`WorkshopConnection`, `engine/gpu/WorkshopConnections.cs:31`), parameter configurations, electrical/signal wiring, and JSON save/load state. It is static during simulation runs and contains full object metadata. Puzzle elements come from the element bundle and are identified by the typed id it issues; the Free Workshop palette lists every bundle element. Connection ports (exposed/output and accepted/input) and their connection domains (`Activation`, `Electrical`, `Rope`, `Mechanical`; `engine/gpu/WorkshopConnections.cs:11`) are declared in each element's package, referencing `Loc_Port_<Id>` locator nodes in its `.tscn` scene to establish 3D socket anchors without hardcoded coordinate tables.

### 2. Physics Graph (Simulation Core)
When the player presses **Run**, the logical scene graph is compiled into a flat, contiguous, SIMD-aligned **Physics Graph**:
- One homogeneous scene record comprising bodies, shapes, materials, constraints, force regions, energy stores, sensors, triggers, and network nodes across all physical domains (mechanical contact and electrical supply routes today; optical ray marching, acoustic/pneumatic fields, thermal and radiation as their stories land).
- Colliders originate from the element's own `.tscn` scene: its collision proxy nodes (`col_box`, `col_sphere`, `col_capsule`, `col_cylinder`, `col_hull`) are extracted without element branching (at build time into the bundle, under Story 9A.16) and mapped to flat SIMD collider tables. Box, sphere and (Story 10.1) cylinder proxies are admitted: a `CylinderShape3D`, or a `CylinderMesh` whose top and bottom radii are equal, with explicit `radius` and `height`, axis local +Y and equal radial scale, bakes as the solid Cylinder $(r, w/2, r)$. A hidden `col_*` `MeshInstance3D` sharing the art's mesh declares a true hollow collider (engine-hollow-shapes, [hollow geometry](hollow-geometry-design.md#declaration-data)): a `CylinderMesh` with both caps off and `metadata/wall_thickness` bakes as a Tube (equal radii) or Frustum (tapered), a `TorusMesh` as a Torus (full and solid, or a segment and hollow through `metadata/sweep_degrees` and `metadata/wall_thickness`). Capsule and hull proxies are rejected until their stories admit them. No procedural geometry or hardcoded shape tables are permitted in C#.
- The WASM SIMD physics worker consumes flat generic capability and collider tables compiled from the bundle's declarations, sized from the compiled scene, with strictly zero catalogue-specific kernel branches, solvers, or update loops.
- **One unified generalised data-driven physics engine advances this state.** Strictly zero element-specific solvers, zero per-part update loops, and zero element-selected kernel branches.
- Multi-domain solver couplings (compiled electrical supply routes over the reachability graph, discrete activation events) compile from declared ports rather than hardcoded C# tables or element-specific branches. Modified Nodal Analysis is a named later capability, added by the first element story that needs it.
- Target (`ENGINE-SOA-SIMD`): flat contiguous SIMD-aligned Structure-of-Arrays (SoA) memory tables with 64-byte cache line alignment, in place of today's byte records (status paragraph above).
- A dynamic binary Bounding Volume Hierarchy (`CuriousContraptions.Simulation/WorkshopDynamicBvh.cs:6-19`), rebuilt every substep with each moving leaf fattened by the speed limits (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:806-866`), produces the contact candidate pairs; other phases still scan every body or row. Target (`ENGINE-SPATIAL-QUERIES`): persistent trees and one query interface for every phase.
- Target (`ENGINE-ISLANDS-SLEEP`): Disjoint Set Union (DSU / Union-Find) partitions bodies and constraints into independent Simulation Islands; no island exists today.
- Generic Box2D v3 Temporal Gauss-Seidel (TGS Soft) solver unifies non-penetration, friction, and bilateral joints into effective constraint mass.
- Narrowphase collision detection uses generic analytic manifolds (Sphere, Box, Plane, solid Cylinder; capsule and hull proxies are refused at bundle time, `tools/BundleElements/SceneGeometryExtractor.cs:103-106`, `:117-123`, and a convex profile is the `ENGINE-PROFILE-COLLIDER` target) and the exact signed distance fields of the hollow kinds (Tube, Frustum, Torus).
- Multi-domain physical fields (electrical supply, finite energy stores; optical rays and acoustics as their stories land) execute through shared capability kernels.

### 3. Rendering Graph (Presentation Pipeline)
The visual representation on the browser main thread, using visual PBR meshes from the element's `.tscn` scene. Today it consumes the committed FlatBuffers read and moves one node transform per body (`engine/MachinePart.cs:342-350`). Target: it consumes read-only pose data from the shared memory ring (`ENGINE-WIRE-ABI`) and translates it into GPU instanced draw batches grouped strictly by mesh and material pipeline (`ENGINE-INSTANCED-RENDERING`).

### Independent Systems, One-Way Data Flow
- **Simulation Worker (Physics):** Runs at a committed tick of 60, 120 (the default) or 240 Hz with 480 Hz sub-stepping (`CuriousContraptions.Abstractions/CadenceValues.cs:68-74`) on a dedicated WebAssembly SIMD worker. Owns physical truth. The physics worker consumes flat generic capability and collider tables compiled from the bundle's declarations, advancing state through the unified, generalised, data-driven engine with strictly zero catalogue-specific kernel branches, solvers, or update loops.
- **Animation Worker (Cosmetics):** All animation executes on an independent Animation Web Worker at 60 Hz, completely decoupled from physical truth. Compiles an independent animation model from the same authoring data; evaluates procedural curves, uniform or per-axis scale mappings (declared as `PresentationProperty.UniformScale`, `ScaleX`, `ScaleY` or `ScaleZ`, `CuriousContraptions.Abstractions/ElementPresentation.cs:14`; the animation worker evaluates one scale value, `AnimationProperty.UniformScale`, `engine/gpu/WorkshopDeclaredPresentation.cs:741`, and the presenter applies it to the declared axis, `engine/WorkshopVisualBinding.cs:49-55`), motor spin and indicator/UI easing driven by declarative bindings to committed physical poses, committed level states and one-shot event-ring occurrences. Strictly zero per-element animation scripts or callbacks in the animation host. Fed one-way by committed physics results. Never feeds back into physical state.
- **Renderer (Main Thread):** Runs at display refresh cadence (30–144 FPS). Smoothly interpolates between committed physics pose brackets, using the committed motion pieces of the posted read (`engine/gpu/WorkshopPoseHistory.cs:285-303` → `engine/gpu/PhysicsMotionRead.cs:132-185`); the shared `SharedArrayBuffer` ring as that feed, with its derived depth, is the `ENGINE-WIRE-ABI` target.
Data flows strictly one-way: physics → animation → renderer and physics → renderer; nothing flows back into physics. Physics always runs faster than rendering; rendering never influences physical results.

Adding a new puzzle element means adding declaration data (the capabilities it instantiates, its geometric parameters, exposed/accepted ports with named mesh node socket anchors, art assets, and animation bindings) to its own `elements/<Name>/` package. No new element requires solver modifications, engine enum additions, hardcoded connection tables, or bespoke simulation branches.

<a id="zero-element-assumptions-physics"></a>

### Zero Element Assumptions & Generic Combination Invariant

The physics simulation core and compilation pipeline enforce the non-negotiable architectural invariant of **zero element assumptions and generic combination support**:
- **Zero Element Assumptions:** The physics engine makes strictly zero assumptions about which puzzle elements exist or have been loaded. No part identity, kind tag, or catalog class exists in the solver.
- **Universal Arbitrary Combinations:** The engine supports ANY arbitrary combination of puzzle elements without special cases, element checks, or hardcoded couplings. If hundreds of diverse parts collide, mesh, or wire together, all interactions evolve through generic mathematical models.
- **Purely Homogeneous Tables & Generic Collider Extraction:** All rigid body integration (symplectic Euler), narrowphase manifold generation (Sphere, Box, Plane, solid Cylinder, the hollow Tube, Frustum and Torus; a convex profile is the `ENGINE-PROFILE-COLLIDER` target), constraint resolution (Box2D v3 TGS Soft), and multi-domain network passes (electrical supply routes now; optical ray marching and acoustic fields later) operate strictly on flat homogeneous capability tables. Collision shapes are extracted generically from the scene's `col_*` proxy nodes based solely on geometric properties (half-extents, radii, lengths) without element-specific branching or hardcoded shape tables.
- **Strictly Zero Identity Branching:** No physics compiler pass, solver kernel, or integration loop may branch, switch, or execute conditionals based on a part's identity, name, or purpose. When two colliders touch, their contact dynamics are governed 100% by universal geometric manifolds, Coulomb friction cones, and material restitution laws; the solver neither knows nor cares whether the collider belongs to a Tennis Ball, a Domino, or an authored custom fixture.

<a id="numeric-representation"></a>
## Numeric Representation and Precision

All authoritative continuous simulation state, velocity integration, spatial coordinates, and constraint solving use standard **IEEE-754 single-precision floating-point (`f32`)**.

### Precision Invariants
- **Single-Precision Float (`f32`):** 24-bit mantissa ($\approx 7.2$ decimal digits) and 8-bit exponent ($\pm 10^{38}$). This eliminates catastrophic cancellation in rotational torque arms, prevents exponent overflow in kinetic energy calculations, and provides native alignment for 128-bit SIMD registers (`wasm_v128`).
- **Quantized World Domain:** Simulation coordinates span a standard puzzle volume $[-64, 64]\text{ m}$ per axis with sub-millimeter precision. Coordinate snapping during construction quantizes to canonical grid units ($0.1\text{ m}$ or $1/16\text{ m}$), but internal solver arithmetic operates in full continuous `f32`.
- **WASM SIMD128 Vectorization:** 4-wide single-precision float operations (`f32x4.add`, `f32x4.mul`, `f32x4.min`, `f32x4.max`) execute simultaneously in hardware registers. Today they serve the revolute and prismatic joint rows (`CuriousContraptions.Simulation/RevoluteConstraintSolver.cs:213-221`, `CuriousContraptions.Simulation/PrismaticConstraintSolver.cs:208-216`, `engine/gpu/SoftConstraint.cs:51-58`), the single tensile row, broadcast into all four lanes rather than batched (`CuriousContraptions.Simulation/TensileConstraintSolver.cs:80-82`), and small helpers such as the contact work carrier (`engine/gpu/ContactWorkImpulse.cs:15`). Broadphase slab tests (`CuriousContraptions.Simulation/WorkshopDynamicBvh.cs:154-158`), contact impulse updates and bounding box evaluations are scalar; vectorizing them is the target of `ENGINE-SOA-SIMD`.
- **No Hidden Precision Channels:** No double-precision (`f64`) shadow state or narrow 16-bit float truncation is permitted in the simulation loop. Game saves serialize exact 32-bit float bit patterns alongside typed integer configuration states.

<a id="capability-inventory"></a>
## Generic Capability Inventory

Every puzzle element is an instance of one or more shared physical capabilities declared in its element package and compiled into flat data tables. The simulation worker and compilation pipelines process these tables homogeneously with zero catalogue-specific kernel branches:

| Capability | Declared Data Content | Execution Behavior |
| :--- | :--- | :--- |
| **Rigid Body** | Mass, 3x3 inertia tensor, world pose (position vector, orientation quaternion), linear and angular velocities, linear drag coefficient, motion type (Dynamic or Static). No island index is stored; islands are the `ENGINE-ISLANDS-SLEEP` target. | Integrated via symplectic Euler at 480 Hz; declared linear drag decays the linear velocity exactly ($e^{-c\,\Delta t}$) after gravity each sub-step, and no angular drag exists; orientation quaternion normalized every sub-step. Each committed tick initializes a transient relative quaternion to identity and its start quaternion from committed input; world-space increments left-compose the relative quaternion, and physical orientation is normalized relative × start. ### 2. Narrowphase: Analytic Manifolds & 4-Point Area Reduction
- **Closed-Form, Fixed-Count Analytic Primitives (shape-pair dispatch, `CuriousContraptions.Simulation/WorkshopCollisionKernels.cs:1999-2028`):** Sphere-Sphere, Sphere-Box, Box-Box (15-axis SAT with reference-face clipping), Sphere-Plane, Box-Plane (up to four deepest vertices) and the solid Cylinder pairs below are computed via closed-form geometry without iterative GJK/EPA/MPR loops. The cylinder's curved rims add fixed-count refinements of closed-form signed distances, described below. Capsule and hull proxies are refused at bundle time (`tools/BundleElements/SceneGeometryExtractor.cs:103-106`, `:117-123`); a convex profile is the `ENGINE-PROFILE-COLLIDER` target.
- **Solid Cylinder (Story 10.1):** axis local +Y, radius $r$, half-width $h$; its exact support projection on a unit $u$ is $h|u\cdot a| + r\sqrt{1-(u\cdot a)^2}$, which also gives its exact rotated AABB (fattened for spin by $\sqrt{r^2+h^2}$). Inertia compiles on the canonical path: axial $m r^2/2$, transverse $m(3r^2+w^2)/12$. A contact normal within the cap tolerance of the axis ($|n\cdot a| \ge 0.98$) meets a cap; within the same angle of the axis-perpendicular plane ($|n\cdot a| \le \sqrt{1-0.98^2}$) it meets the curved side along a generator line; otherwise one rim point.
  - *Cylinder–Plane:* four points of the facing cap starting at its true deepest rim point (the radial direction of $-n$) and at 90° steps from it (upright, from U0), else the deepest rim point of each cap within the margin (two along the side, one tilted). The cap manifold therefore always contains the true lowest point and continues into the rim regime.
  - *Cylinder–Sphere:* the exact closest point of the solid (axial and radial coordinates clamped); a centre inside exits by the shallower feature, side or cap. One point.
  - *Cylinder–Box and Cylinder–Cylinder — gap and normal:* a SAT over the face normals and axes, axis × edge or axis, the closest-point direction of the two axis segments and the radial directions from an axis to box vertices or cap centres (exact support projections) only proves separation beyond the margin early. The gap and normal come from the **exact closest features**:
    - a box face, or a cap, facing the partner whose support point lies over it;
    - the two sides through the axes' common perpendicular (or the middle of a parallel overlap);
    - the minimum of the cylinder's closed-form signed distance along every box edge (convex along a segment: 24 golden-section steps) and along every rim of one cylinder against the other solid (16 fixed angular samples, then 16 golden-section steps in the best bracket).

    Every count is fixed: there is no simplex, convergence test or data-dependent iteration, so this is not GJK/EPA/MPR. Each golden-section search makes 2 initial evaluations plus 1 per step, so the per-pair cost is a bounded constant:
    - **cylinder–box:** 12 edges × 26 = 312 closed-form signed-distance evaluations, plus 12 closest-point evaluations and up to 6 face checks;
    - **cylinder–cylinder:** 4 rims × 34 (16 samples + 2 + 16 steps) = 136 signed-distance evaluations, plus 4 closest-point evaluations, up to 4 cap checks and 1 side–side check.

    The counts are fixed constants (`SegmentSteps` 24, `RimSamples` 16, `RimSteps` 16) with no convergence test. Ratified by the coordinator, 23 Oct 2026, as compatible with the "no iterative GJK/EPA" rule. Separated within the margin, the gap is the exact distance (proved against an independent closest-point oracle to 0.5 mm).
    - **Shallow cylinder–box overlap (Story 10.1 review F4, up to 1 mm; cylinder–cylinder has no core, review N9):** the same measures run between the cylinder's core and the box, the core shrunk by a margin of 1 mm on every face (at most half the radius or half-width). The gap is the core distance less the margins, never positive: the exact shapes overlap, so the core's rim rounding (at most 0.41 of the margin, along the rim's diagonal) cannot report them apart. The normal is the cores' closest-feature direction. This is exact on caps, sides and faces. The exact shapes' deepest point would exit by the cap or the side, flipping between them round a rim tick by tick; that flipping lost warm starts and pumped energy into a box resting on a rim. Each such evaluation doubles the measure cost above.
    - **Deeper overlap:** the shallower of the SAT depth and the deepest closest-feature measure.
    - **Depth clamp:** no manifold point claims more depth than its pair (N5).
  - *Cylinder–Box and Cylinder–Cylinder — manifolds by $n\cdot a$:* a cap meets a box face or a cap as their common region (eight fixed rim samples plus the rim point deepest toward the partner, partner vertices inside, rim crossings, reduced to four); a side meets an aligned face as the clipped generator.
    - **Side emission rule (Story 10.1 review F4, round 4):** a box edge within the cap tolerance of parallel emits the edge's closest point to the axis and both ends of their common stretch; two crossed or skewed cylinder sides emit their closest point and each facing-generator end that lies within the speculative margin against the other side. Every such point carries its own radial signed gap and its own radial normal, so a skewed side's far end is a speculative row before it lands. Parallel cylinder sides (within 2°) keep the two stretch ends, each at its own side distance.
    - **Reduction to four:** the shared side/hollow reducer keeps the deepest point (first on a tie), then the point farthest from it (first on a tie). Fill remaining slots by maximizing the summed triangle areas formed with retained point pairs; area ties maximize summed squared distances to retained points, then prefer lower gap and original order. With two retained points this maximizes triangle area; with three coplanar points it maximizes the expanded support hull. Collinear zero-area ties use the same distance/depth/order comparator, preserving both endpoints. Emit the selected original points in original order. This preserves depth and line span while distributing remaining support across the available geometry.
    - **Closest-witness depth coverage:** every cylinder–box and cylinder–cylinder manifold is checked for a point covering the pair's gap within 0.1 mm. If existing points do not cover that depth, the closest features' midpoint joins with its own normal and signed gap; common reduction and the pair-depth bound apply. Exact closest-point membership is not required when an existing point already covers the depth.
    - **Radial directions:** re-orthogonalised once against the axis; a radial part shorter than 1e-3 of its vector takes the reference direction. An integrated orientation is not exactly unit, and on a turned-over body the axis's length error leaves an axial residue that rivals a micro-radian radial part (a cap tilted 2e-6 rad once read a −24.8 mm bench gap). Another side counts only when its axis is parallel within 2°. Each end of a stretch is measured by its own distance to the partner's curved side. Skewed further, two sides touch at one point: a two-point stretch there put the rows at a rolling cylinder's rim ends and pumped energy into it (review F4). A crossing edge or side meets at one point; a cap on a side gives the generator's chord across the disc; a tilted rim gives one point midway between the exact closest points. Empty and populated emissions use the same closest-witness depth-coverage rule; there is no separate empty-clip construction.
  - Feature ids name the cylinder feature a point came from (cap, side, rim or a numbered sample), so a warm start carries over while that feature persists. Warm-start stability while rolling is not separately qualified.
- **Finite cylinder–box support:** The side generator facing the candidate face normal is clipped against that finite face before contact emission. If its projected interval is absent, the geometry is an edge or point; the closest pair normal cannot turn an edge into a clipped face. Emitted face points use that face's normal and depth. Outside cylinder distance gradients are formed from radial/cap excess coordinates, avoiding cancellation between nearly coincident world points at tiny gaps. This preserves the analytic distance law and existing inside/rolling/normal solver rules.
- **One Constraint Row for Every Pair:** each manifold point becomes the same TGS Soft normal row (lever arms about the centre of mass, world inverse inertia from the compiled principal moments, normal warm start keyed by collider pair and feature, speculative margin, dissipative restitution). Tangential force and normal-axis twist belong to the shared central friction patches described below. Pair laws are geometric-mean friction, product restitution and maximum bounce threshold from the declared materials; no shape or element owns a different response. A rolling support is no material point: a sphere's contact stays under its centre, and a curved-side cylinder contact is the generator facing the partner at the anchor's axial coordinate, so within a substep its support moves with that material axis point plus $r$ times the turn of the facing radial direction about the moved axis. Rolling about the axis leaves that direction unchanged; tumbling turns it, so no energy is gained when a lying cylinder tumbles end over end. Cap, rim and every other contact follow the material anchor. Every manifold with a sphere, and every manifold with a curved-side cylinder contact (arm $r$, coordinator decision under owner delegation, Story 10.1, extending the every-contact rule), adds one rolling-resistance row (Box2D v3 coefficient mixing, not warm-started: its impulse restarts from zero every sub-step), solved after the normal rows of each sweep and applied equal and opposite to both bodies whether the partner is static or dynamic: it drives the relative angular velocity about the manifold's rolling axes toward zero within the circular bound $C_{rr}\,r\sum\lambda_N$, so it never reverses a ball on a static support (against a dynamic anisotropic box the per-axis diagonal effective masses are an approximation); the rolling row itself does not resist spin about the contact normal. A struck body (for example a Domino a ball rolls over) receives the reaction, so its outcome includes the ball's resistance (owner decision 9 Oct 2026).
  - **Rolling axes per manifold** (engine slice "lying cylinder axial creep", 24 Oct 2026): the row resists only the rolling axes of the manifold's curved supports. A one-axis row's axis is projected into the tangent plane of an axis-support point's own normal. Every such normal is within the side tolerance of the axis's perpendicular plane (the pair normal the narrowphase classified the side by, or a radial normal of that cylinder's own axis), so the projection keeps at least $\sqrt{1 - 0.199^2} = 0.98$ of one side's axis, and at least 0.976 of two parallel sides' bisector (within 1° of each axis, $|n\cdot b| \le \sin(\arcsin 0.199 + 1°) = 0.216$). `EveryAxisSupportPointARollingRowProjectsThroughIsWithinTheSideTolerance` pins the invariant on the named sites and a seeded pose sweep.
    - A sphere, on either side: both contact tangents.
    - One curved cylinder side (an axis-support point): its own axis only. The other tangent is pitch, a rocking of the line contact that its two normal rows already carry. Resisting pitch held a tilt against their levelling torque, and the excess leaked through the friction rows, r below the centre of mass, into steady axial walking.
    - Two curved sides whose raw axes are parallel within the narrowphase's 2° (`LineAlignment`, the narrowphase's own test): their common axis, the sign-aligned bisector of the two axes. Crossed sides touch at a point: both tangents.
    - No curved support (faces, caps, rims): no row, as before.

    A one-axis row has a single direction and zero mass on the second, so a lying cylinder's pitch rocking is damped by its normal rows alone (it peaks at the same tilt whatever its $C_{rr}$).
- **Normal row branch: one rule with a manifold-coherent slop band** (engine slice "lying cylinder axial creep", 24–25 Oct 2026). Every normal row takes one rule on $s$ = separation + slop (0.2 mm) and its manifold's soft flag (some point of the manifold has $s \le 0$):
  - **rigid** with the speculative allowance $s/h$, in the solve and the relax pass, when $s > 0$, unless the point is inside the band (separation $\le 0$) and the flag is set;
  - otherwise **soft** in the solve pass (bias $\max(b\,s, -0.012\text{ m/s})$ with the contact's soft mass and impulse scales, $b = \omega/(2\zeta + h\omega)$ at 60 Hz, $\zeta = 10$; for a band point $b\,s > 0$), and rigid with no bias in relax.

- **Hollow kinds (engine-hollow-shapes):** Tube, Frustum and Torus colliders are 2D profiles revolved about their local +Y (a torus over its sweep, with flat end faces), read through one exact signed distance field (`HollowSolid`). Surface-error bound and tests in [hollow geometry](hollow-geometry-design.md#surface-error-bound).
- **4-Point Manifold Reduction:** Contact polygons from face clipping are reduced to the 4 area-maximizing extreme points (deepest point, furthest point, and two points maximizing triangle/quad area).
- **Central friction patches:** After generic buried-feature removal, contacts of the same canonical rigid-body/material pair form compatible patches using pairwise normal agreement: each component differs by at most128u (u=2^-24), and support span times vector normal difference is at most existing ContactSlop. This is a practical f32 reconstruction allowance, not a certified error count; pairwise membership prevents chaining. A deterministic normalized mean defines the friction frame while original contact normals remain unchanged for normal/restitution solving. The live footprint includes geometrically closed or positive-normal-load witnesses; its unweighted centroid and RMS tangent radius exclude separated zero-load speculative children. Rebase the old applied wrench before a changed footprint/basis is solved; zero membership/load contributes no friction. Two central tangent rows and a scaled twist row $r\omega_{relative}$ share one Coulomb ball $\lambda_1^2+\lambda_2^2+\lambda_3^2\le(\mu N)^2$, where $\lambda_3=\tau/r$, $N=\sum\max(\lambda_N,0)$ within the patch and $\mu=\sqrt{\mu_A\mu_B}$. A single point has zero twist radius and no twist resistance.
- **Coupled friction minimization:** The full symmetric $K=JM^{-1}J^T$ defines the accumulated-impulse kinetic quadratic with free velocity $Jv-K\lambda_{old}$. Cyclic f32 Jacobi diagonalization takes at most twelve sweeps, stopping each off-diagonal rotation below one relative f32 epsilon of its diagonal scale. Nonpositive eigenvalues define the numerical nullspace. The unconstrained minimum is accepted inside the Coulomb ball; outside it, a PSD trust-region multiplier is bracketed by $||b||/(\mu N)$ and bisected 32 times, retaining the feasible endpoint. This solves the same quadratic in singular and nonsingular cases. It is not radial projection of a coupled unconstrained minimum. Solve, relax and post-restitution use the same patch solver and current normal load.
- **Feature ID Warm-Starting:** Point-feature caches retain only normal impulses, reused only when the entire normal support set's sorted full collider-pair/feature tuples and block membership matches the preceding substep. Changed membership initializes every normal accumulator to zero before warm application; partial retained load distributions are not applied. The shared ContactFeatureSetKey is independent of enumeration order and normal rotation. Friction caches use the same complete typed collider-pair/feature-set key, storing world tangent impulse and normal-axis torque. Current tangents/radius reproject those values and the current Coulomb budget bounds them before one central application. Membership changes start at zero; normal rotation does not itself change the key. Both caches rebuild every substep and clear at Reset/scene replacement; neither is serialized.
- **Speculative Contacts:** A pair generates contacts within the speculative margin $0.004\text{ m} + (|\Delta\mathbf{v}| + \text{spin reach})\,h$ (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:1112-1117`); its speculative constraints remove excess closing velocity without continuous swept root-finding. The conservative advancement below covers spheres only (`CuriousContraptions.Simulation/WorkshopCollisionKernels.cs:639-645`, `:1940-1949`); tunnelling of other shapes is not generally qualified, owned by `ENGINE-TUNNEL-QUALIFICATION`. A sphere's speculative contact that will close within two substeps (the solve stops what this substep reaches, the relax pass what the next would) takes its normal at the predicted touch: its centre is advanced along the pair's relative linear velocity by conservative advancement (at most four probes of the same pair kernel), the contact keeps the distance still to close along that normal as its gap, and its point stays on the advanced sphere's centre line. Two moving spheres keep their generated contact. A speculative point that carries normal impulse in a substep is a contact for restitution, contact events and contact loads.
- **Restitution (engine restitution slice, 24 Oct 2026):** one pass per 480 Hz substep, after the relax sweeps and before the second velocity clamp; each substep is a complete Box2D v3 step (collide, prepare, solve, integrate, relax), so this is the faithful mapping of Box2D's once-per-step pass. A point bounces when it carried normal impulse in that substep, touching or speculative, and its approach exceeds the pair's bounce threshold strictly. The approach is the relative normal velocity at the point from the bodies' substep-start velocities (before guides, supplied drives, gravity and drag; Box2D prepares before integrating velocities). Bouncing contacts are grouped, by a union-find over the dynamic bodies they join (`CuriousContraptions.Simulation/WorkshopConstraintSolver.cs:609-617`, `:660-664`) and the bodies guide-linked to them (`:629-635`), with the active supporting contacts of those bodies, whose dynamic support partners `ExpandRestitutionSupports` merges into the group (`:719-754`, `:744-748`); a manifold's supporting points join only when that manifold has no bouncing point (`:777`; target undecided, [deferred to ENGINE-ISLANDS-SLEEP planning](../_bmad-output/implementation-artifacts/deferred-work.md#restitution-mixed-manifold-rule)); one accumulated active-set block solve over each group drives its bouncing points to $-e$ times their own approach and its supporting points to zero normal velocity (`ApplyRestitution`, `:701`, `:846-848`, `:870`), with nonnegative total impulses; no soft-contact or penetration bias enters the target. Each manifold that bounced is then given one more friction and rolling pass whose cones include the restitution impulse, so an impact keeps its Coulomb share of tangential impulse (a deviation from Box2D's pass, which runs after several frictional substeps). There is no cross-substep approach memory: an impact is resolved in the substep that stops it. The pass is bounded by energy: the dynamic bodies joined by that substep's bouncing manifolds form groups, and a group's kinetic energy after the pass may not exceed the larger of its kinetic energy before the contact solve (after gravity and drag) and after the relax sweeps; a group over the bound has its restitution change scaled back along the line from its relaxed velocities. Independent Newton targets on a body shared by several impacts (a box landing on a box that bounces on the bench in the same substep) would otherwise return more than the impacts removed (reviewer F1, e ≥ 0.95). The energy bound is applied per group (`CuriousContraptions.Simulation/WorkshopConstraintSolver.cs:709`). Open, owned by `ENGINE-ISLANDS-SLEEP`: a group is cut to 8 points, bouncing points first (`:685-688`); `ExpandRestitutionSupports` follows a contact between dynamic bodies only when its normal has an upward (+Y) component on the touched body's side (`:739`), and `GatherRestitutionIsland` (`:756-783`) counts support from a partner outside the group, such as a static body, only under the same one-sided upward condition, while a contact between two bodies in the group counts at any normal (`:769`). Contact events report that approach and contact loads count that point, in the substep the impact is resolved.

### 3. Constraint Solver: Box2D v3 "TGS Soft" Formulation
Every contact, limit, and joint is modeled as an implicit damped spring-damper constraint integrated directly into the effective constraint mass:
$$\beta = \frac{h \omega}{2 \zeta + h \omega}, \quad \gamma = \frac{1}{h m_{\text{eff}} (2 \zeta \omega + h \omega^2)}$$
$$\mathbf{M}_{\text{eff}} = \left( J M^{-1} J^T + \gamma \right)^{-1}$$
$$\Delta \lambda = -\mathbf{M}_{\text{eff}} \left( J v + \frac{\beta}{h} C + \gamma \lambda_{\text{total}} \right)$$
- Compliance $\gamma$ and softness bias $\beta$ regularize constraint corrections; they do not by themselves guarantee energy conservation or dissipation.
- **Numerical envelope:** Verify contacts, limits and joints against the game-grade error and energy envelope, including external work. Residuals clamp or continue; actual behavior, not the softness formula alone, establishes acceptance.
- **4-Wide SIMD Batching:** today the revolute and prismatic joint rows evaluate in WASM SIMD128 `f32x4` (`CuriousContraptions.Simulation/RevoluteConstraintSolver.cs:213-221`, `CuriousContraptions.Simulation/PrismaticConstraintSolver.cs:208-216`); contact rows are solved one at a time (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.Motors.cs:104`, `:125`). Target (`ENGINE-SOA-SIMD`): four contact rows or manifold points per `f32x4` instruction within an island.

## Modern Engine Architectural Patterns (Zero-Dependency In-Tree Formulation)

**Implementation status.** These ten patterns are partly target. Running today, with the differences stated in each: speculative contacts (3), contact feature warm-starting (4), four-point manifold reduction (5), compliant soft constraints (6), demand-grown storage (8) and symplectic multi-substepping (9). Target: the Quad-BVH, dual tree and canonical pair order (1, 2 and 10) of `ENGINE-SPATIAL-QUERIES`, islands and sleeping (7) of `ENGINE-ISLANDS-SLEEP`, and cache-line aligned SoA tables (10) of `ENGINE-SOA-SIMD`. The throughput and deterministic replays named below are goals: same-build replay is exercised by the Reset and replay tests (`CuriousContraptions.tests/TrampolineTests.cs:2174`, `F32BehaviourIdentityTests`) but not established in general, and a canonical pair order is the `ENGINE-SPATIAL-QUERIES` target ([Current status](architecture/element-package-isolation.md#current-status)).

To guarantee industry-grade stability, sub-millisecond multi-body throughput, and deterministic replays across desktop and mobile browsers, the engine incorporates ten core architectural best practices inspired by modern high-performance physics engines (such as Jolt Physics), implemented strictly as **100% custom, in-engine, data-driven C# and TypeScript code with zero external libraries or dependencies**:

### 1. Target: 4-Wide SIMD Quad-AABB BVH (`wasm-simd128`)
Target (`ENGINE-SPATIAL-QUERIES`; its SIMD lanes `ENGINE-SOA-SIMD`): in place of today's scalar binary tree, the broadphase spatial hierarchy becomes a 4-child Bounding Volume Hierarchy (Quad-BVH) directly mapped to WebAssembly 128-bit SIMD vector registers:
- **Transposed Node Layout:** Each inner node packs the AABBs of its 4 children into transposed SIMD vectors:
  - $\mathbf{min}_x = [c_0.\min.x, \; c_1.\min.x, \; c_2.\min.x, \; c_3.\min.x]$
  - $\mathbf{max}_x = [c_0.\max.x, \; c_1.\max.x, \; c_2.\max.x, \; c_3.\max.x]$
  - $\mathbf{min}_y, \mathbf{max}_y, \mathbf{min}_z, \mathbf{max}_z$ arranged identically.
- **Single-Instruction 4-Way Overlap Test:** Testing a query volume (or fat AABB) against all 4 child bounds executes concurrently using `f32x4.min`, `f32x4.max`, `f32x4.le`, and `f32x4.ge`, producing a 4-bit hit mask in a single instruction sequence (`i32x4.bitmask`).
- **$\log_4$ Tree Depth:** The Quad-BVH halves the tree depth compared to binary trees ($O(\log_4 N)$), minimizing cache line misses during tree traversal and eliminating CPU branch mispredictions.

### 2. Target: Dual-Tree Broadphase (Static vs. Dynamic Acceleration)
Target (`ENGINE-SPATIAL-QUERIES`): inspired by Jolt's dual-tree partitioning, the world broadphase becomes two specialized spatial structures. Today one tree holds every collider and static leaves are reinserted every sub-step (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:812-862`); subtrees without a moving body are pruned (`CuriousContraptions.Simulation/WorkshopDynamicBvh.cs:15-16`, `:154`, `:182`) and static–static pairs are dropped (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:876`).
- **Static Quad-BVH:** Holds all non-moving level geometry. Built once or updated lazily with Surface Area Heuristic (SAH) tree rotations. Zero per-tick updates or node refits occur for static colliders.
- **Dynamic Quad-BVH:** Holds dynamic rigid bodies with velocity-fattened bounding boxes:
  $$\mathbf{AABB}_{\text{fat}} = \left[ \mathbf{p}_{\text{min}} - (|\mathbf{v}| h + \mathbf{s}_{\text{slop}}), \; \mathbf{p}_{\text{max}} + (|\mathbf{v}| h + \mathbf{s}_{\text{slop}}) \right]$$
- **Pruned Query Matrix:** Dynamic-to-Static queries traverse the static tree without ever rebuilding it; Dynamic-to-Dynamic queries traverse the dynamic tree; Static-to-Static interactions are completely skipped (0 ms cost).

### 3. Speculative Contacts for Continuous Collision Detection (CCD)
High-speed rigid bodies (such as balls accelerated by gravity or bumpers hitting thin walls) can traverse more than their bounding extent in a single sub-step, causing discrete collision tunneling. Instead of computationally expensive swept root-finding or interval arithmetic:
- **Velocity-Expanded Speculative Distance:** the contact generation envelope is expanded by the speculative margin, today over the pair's relative speed and spin reach rather than the normal approach alone (`CuriousContraptions.Simulation/WorkshopPhysicsEngine.cs:1112-1117`):
  $$d_{\text{spec}} = 0.004\text{ m} + (|\Delta\mathbf{v}| + \text{spin reach})\, h$$
- **Early Constraint Allocation:** When the separation distance $g$ satisfies $0 < g \le d_{\text{spec}}$, a speculative contact constraint is allocated in the narrowphase manifold.
- **Target Velocity Absorption:** The constraint sets a target relative velocity:
  $$v_{\text{target}} = -\frac{g}{h}$$
- **Zero Penetration without Ghost Collisions:** The TGS Soft solver applies an impulse that reduces the approaching normal velocity to zero exactly when the surface is reached, so glancing bodies continue without artificial snagging. Conservative advancement covers spheres only; tunnelling of other shapes through thin walls is not generally qualified, owned by `ENGINE-TUNNEL-QUALIFICATION`.

### 4. Contact Feature Identity & Warm-Starting
- **Contact Identity:** a contact point is identified by `ContactFeatureIdentity(A, B, Feature, OwnerA, OwnerB, FaceA, FaceB)` (`CuriousContraptions.Simulation/WorkshopFrictionSolver.cs:9-10`, filled at `:20-21`): its two colliders, the feature, the two owning body slots and, for a box, the faces.
- **Persistent Contact Caching:** the normal and friction caches are keyed by these identities over the complete support set (Feature ID Warm-Starting above).
- **Warm-Starting Impulses:** Matching point features inherit normal impulse. Exact patch feature membership inherits world tangent impulse and normal-axis torque, reprojected into current geometry and budget; see the central friction law above.

### 5. Deterministic 4-Point Area-Maximizing Manifold Reduction
Polyhedral contact generation (such as 3D Box-Box SAT clipping or domino-on-workbench contact) can generate complex polygonal intersection shapes with 6 to 8 vertices. To guarantee constant-sized solver batches and numeric determinism:
- **Extreme Point 1:** The point with the maximum penetration depth (deepest contact).
- **Extreme Point 2:** The point furthest from Point 1 in Euclidean distance.
- **Extreme Point 3:** The point that maximizes the cross product magnitude $|(\mathbf{p}_3 - \mathbf{p}_1) \times (\mathbf{p}_2 - \mathbf{p}_1)|$, maximizing the triangle support area.
- **Extreme Point 4:** The point on the opposite side of the line $\overline{\mathbf{p}_1 \mathbf{p}_2}$ that maximizes the quadrilateral area.
- **Four-row normal blocks:** Each local active-set normal block has at most4 points. A rigid compound support set retains all necessary witnesses in as many demand-sized blocks as required; four is not a global compound/scene contact cap. Friction/rolling retains one shared support-set lifecycle.

### 6. Unified Compliant Soft Constraints (Spring-Damper Formulation)
All bilateral and unilateral constraints—rigid contact normals, Coulomb friction, prismatic sliders, revolute hinges, tensile rope routes and ratio transmissions (`CuriousContraptions.Simulation/MechanicalTransmissionSolver.cs:8-14`)—are unified under an implicit compliant spring-damper formulation:
- **Kinematic Constraint & Jacobian:** For any constraint function $C(\mathbf{x}) = 0$, the kinematic velocity constraint is $J \mathbf{v} = 0$, where $J = \frac{\partial C}{\partial \mathbf{x}}$.
- **Compliance $\gamma$ and Softness $\beta$:** Parameterized by natural frequency $\omega$ (stiffness) and damping ratio $\zeta$:
  $$\beta = \frac{h \omega}{2 \zeta + h \omega}, \quad \gamma = \frac{1}{h m_{\text{eff}} (2 \zeta \omega + h \omega^2)}$$
- **Unified Effective Mass:**
  $$\mathbf{M}_{\text{eff}} = \left( J M^{-1} J^T + \gamma \right)^{-1}$$
- **Bounded numerical behavior:** Substeps and compliance improve constraint conditioning but do not guarantee stability or zero energy gain for every coupled scene. Verify physical time scale, damping, contacts and stops within the game-grade envelope; retain the declared velocity bounds and residual handling.
- **Stabilisation softness acts only in the solve pass (engine-tensile-drive-coupling, 4 Nov 2026):** a row whose softness only stabilises it, a soft contact normal row (the normal row branch above) or a tensile (rope) length row (60 Hz, ζ = 10), is soft with its bias in the solve pass and rigid with no bias ($\gamma = 0$, bias 0) in the relax pass. A row soft in relax converges there to $Jv = -\gamma\lambda$ and commits that false velocity, $F\,m^{-1}/(2\zeta\omega + h\omega^2)$ (1.25 mm/s on any load hanging from a static anchor), which a supplied hinge or slider drive held by the rope reads as spin, travel and work. Declared springs (the prismatic spring row and the revolute axial spring) keep their law, softness and bias in both passes. Every other joint row has no softness ($\gamma = 0$). Positions still integrate from the solve-pass velocity; the rope's `Travel` ledger samples the pre-relax velocity and the hinge drive's travel and work ledgers the post-relax velocity, so a drive's ledger no longer counts the rope's elastic take-up.
- **Declared supplied drive (C-Gate, 22 Oct 2026):** a slider may declare a `PrismaticDriveDescriptor` (target, maximum speed, stopping acceleration, maximum effort, maximum power), enabled while its element's compiled PowerIn route is closed. It compiles to a separate `PrismaticDriveDeclaration` row (the prismatic record's immutable `DriveKind` and drive lanes). On every substep the one generic law reads the joint's own axial row and applies, along it, the force $F = m\,\Delta v/h + k\,x - m\,g_{\text{axis}}$, where $\Delta v$ moves toward $\operatorname{sign}(d)\min(v_{\max}, \sqrt{2 a |d|}, |d|/h)$ by at most $a h$ (the $|d|/h$ cap, Story 9A.44, is the speed that closes the remaining distance in one substep, so the hold at the target does not chatter). $F$ is clamped to $\pm F_{\max}$, then to $|F v| \le P_{\max}$ at the current axial speed. A route may drive only a slider that declares a drive. Each committed tick also writes the prismatic's moving-contact lane: whether its moving body took a positive normal contact impulse from a body other than its base.

  $$\mathbf{v}_{t+h} = \mathbf{v}_t + \mathbf{M}^{-1} \mathbf{F}_{\text{ext}} h + \mathbf{M}^{-1} \mathbf{J}^T \boldsymbol{\lambda}$$
  $$\mathbf{x}_{t+h} = \mathbf{x}_t + \mathbf{v}_{t+h} h$$
  $$\Delta\mathbf{q} = \left(\frac{\boldsymbol{\omega}}{|\boldsymbol{\omega}|}\sin\frac{|\boldsymbol{\omega}| h}{2},\ \cos\frac{|\boldsymbol{\omega}| h}{2}\right), \quad \mathbf{q}_{\text{rel}} \leftarrow \text{Normalize}(\Delta\mathbf{q}\,\mathbf{q}_{\text{rel}}), \quad \mathbf{q} = \text{Normalize}(\mathbf{q}_{\text{rel}}\,\mathbf{q}_{\text{start}})$$

## Game-Grade Envelope

Apply the [float comparison and effort rules](testing-guidance.md#float-comparison-and-effort-rules): use quantity-specific absolute/relative allowances where appropriate, chosen for gameplay scale and observation duration. No universal machine epsilon, historical trajectory pin or numerical-only repair loop defines scene acceptance.

**Gameplay fidelity (owner, 28 October 2026):** choose scene-level accuracy from functional clearance, intended contact and routing, visible stability, cumulative drift over a play window and energy conservation. Float spacing, a fraction of slop or closeness to an old trajectory alone is insufficient justification. Tight arithmetic, canonical codec and admission-boundary checks remain useful where those are the actual contracts. Existing micrometre/microradian observations below are scoped implementation evidence, not universal game requirements; reconsider an obsolete oracle before tuning a solver to it. Preserve meaningful physical bounds and document replacement coverage; do not multiply tolerances or fit margins to outputs.

The engine enforces a strict clamp-or-continue policy. Numerical errors, extreme velocities, or anomalous user constructions are handled cleanly without crashing the browser or terminating the simulation tick. Development timing budgets (e.g., <0.5 ms tick time, 60 FPS pacing, zero clock-debt over 20 runs) are target recommendations and advisory telemetry during incremental development slices; they are not blocking pass/fail gates for functional slices. ## Forward-Only Refactoring and Deletion Mandate

This architecture operates on a strict **forward-only refactoring policy**:
- **Zero Backwards-Compatibility Shims:** No compatibility wrappers, transitional adaptors, emulation shims, or parallel CPU/GPU execution modes are permitted.
- **Code Removal:** Superseded systems—including old WebGPU WGSL compute shaders (`physics.wgsl`), half-precision (`f16`) bitwise manipulation codecs, and Baumgarte position stabilization—are permanently removed from the active codebase upon completion of the forward implementation.
- **Preservation through Refactoring:** All named puzzle elements, their catalog definitions, and the progressively taught campaign levels (at least 150) remain fully preserved and are refactored directly to the new declarative capability formats.
