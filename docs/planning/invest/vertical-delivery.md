## What is a task here?

A playable slice demonstrates one named interaction through real UI, canonical IEEE-754 f32 construction, typed commands, the actual WASM simulation worker, universal WebGL 2/WebGPU instanced renderer, visible feedback and Reset. Its ABI, geometry, compiler, queue, unit tests, cleanup and evidence are supporting criteria with the same stable implementation/reviewer pair. They are not independently valuable product stories or weeks of prerequisite subsystem completion.

Aggregate rows are completion conjunctions, not a serial queue to finish before touching UI. Design decisions must settle a named uncertainty needed by the next slice, with finite inputs and an observable decision oracle. Historical checkpoints retain evidence and surviving acceptance. No row's title or a template automatically establishes INVEST readiness. Owner identities and their exact source members are kept in [requirements](../requirements.md) and [named elements](named-elements.md); the former obligation map was deleted on 5 October 2026 and remains in git history as evidence only.

A required-now supporting criterion must have an independently reviewed result for the named slice before its dependent behavior is accepted. It cannot be waived because the parent audit is later. The complete parent remains open until all of its children pass. Conversely, an unrelated missing law/mode/device is not a prerequisite for demonstrating an already admitted part on the declared development device; it still blocks its own scope and the full release gate.

**Timing and Performance Relaxation:** Fixed-step timing budgets (e.g., 2.5 ms tick p95, <0.5 ms solver execution time, zero clock-debt thresholds over 20 runs, and display-rate 60 FPS pacing) are target recommendations and preferred engineering guidelines. They are tracked as diagnostic telemetry and advisory metrics, but do NOT act as gating pass/fail constraints during functional slice delivery. A development slice is accepted when functional mechanics, visual presentation, non-tunneling, and exact Reset/Save-Load pass. Formal qualification of hardware/timing budgets is deferred to the P0-034 stage gate.

## Rolling roadmap: grow a game people can play

**One execution plan, not competing queues.** TODO owns the current slice and the next one or two; this ordered roadmap is the programme. Each slice is a thin vertical INVEST slice whose acceptance a player can observe in Chrome through Playwright, adds one generic data-driven capability or one element by declaration, and names the legacy it deletes. Physics is one generic WASM SIMD128 f32 solver over the compiled initial state and animation is a separate compiled model, operating with **strictly zero external physics dependencies** (no Box2D, no Jolt, no Rapier; 100% custom in-engine algorithms incorporating modern best practices: Quad-BVH SIMD vectorization, Speculative Contacts for CCD, 4-point area-maximizing manifold reduction, unified compliant soft constraints, and deterministic pair sorting); the [compilation model](../../gpu-f32-physics.md#compilation-model), [modern engine patterns](../../gpu-f32-physics.md#modern-engine-patterns), and [game-grade envelope](../../gpu-f32-physics.md#game-grade-envelope) are fixed. Already playable: Basketball, Receiver, Ramp, Wall, Impact switch → Signal lamp, Delay (`delayed_signal` solved) and the manually constructed Bumper interaction.

**Minimum playable loop:** select an existing level whose typed goals, locked parts, inventory, connections and profiles are actually admitted, place/connect through real controls, Run, observe a meaningful unsuccessful route, Reset, change the construction, achieve the authoritative goal and visible Solved result, then Build again/Reset. Exercise save/load where supported. A Workshop mechanism with a glowing lamp is progress but does not by itself prove a level goal or a retry loop.

**Definition of done for the programme:** 150 progressively taught levels plus unlimited free play; one generic WASM SIMD128 f32 physics solver advancing the compiled initial state and a separate animation engine compiled from the same element data, both driven only by element data plus the player's initial state, in separate workers at independent rates with one-way physics → animation data flow; a renderer on the browser main thread at 30–60 FPS consuming both systems, physics always faster than rendering; new puzzle elements can be added in the future without changes to the physics or animation systems, because an element is defined by its visual, physics and animation behaviours (declaration data) that the solvers use when the simulation runs; zero legacy physics or animation code in the tree.

### Per-slice template

- **Outcome:** one player-visible interaction or level.
- **Capability (generic):** the single data-driven capability added, or none.
- **Declarations touched:** element/level records and bindings.
- **Legacy deleted:** named files or paths removed in this slice.
- **Done when:** 3–5 Chrome-observable bullets, always including exact Reset and Save/Load where supported; timing latency and clock debt are recorded as advisory telemetry and do not gate functional slice acceptance.
- **Controls (negative):** the meaningful unsuccessful route and unsupported-input rejection.
- **Reviewer checks:** production build, tests, actual Chrome run, and `grep` for element/puzzle identifiers in the physics solver, the WorkshopPhysicsCompiler.cs solver dispatch and the animation evaluator selection (must find nothing).
