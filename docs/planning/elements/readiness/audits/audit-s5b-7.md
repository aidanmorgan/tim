## Blocking findings

### B1. The fixed root-schema invocation breaks S5's required deleted-schema-file test, or else leaves stale TypeScript (classification: wrong specified behaviour)

- **Where:** contract `:26`, `:66` and task 1 `:127` (the TypeScript step runs `--ts --gen-all` on the literal `schemas/workshop_authoring.fbs`); `:31` (the steps "declare the same inputs"). S5: `CuriousContraptions.FlatBuffers.csproj:118-133` (`ListWireSchemas` writes `$(IntermediateOutputPath)WireSchemas.list`; `GenerateWireAccessors` has `Inputs="@(WireSchema);$(IntermediateOutputPath)WireSchemas.list;$(MSBuildProjectFullPath)"`); `WorkshopWireBuildTests.cs:104-117`, `ADeletedSchemaFileLeavesNoGeneratedSource` (S5 M4 boundary, a required test): deletes `schemas/workshop_authoring.fbs` from the copy and expects the build to succeed with no `SavedConstruction`.
- **Defect:** run here with the pinned compiler (digest `f004709c…`, equal to the pin at `csproj:31`), `flatc --ts --gen-all` on a missing schema prints `unable to load file` and exits 1. If the TypeScript target uses S5's Inputs, as `:31` requires, the deleted file changes `WireSchemas.list`, the target runs, `flatc` fails and the build fails: S5's test goes red in the full round. If it uses only the inputs `:31` lists (schemas and project file, no list), the target is skipped and `tools/e2e/.wire/` still exports the deleted schema's types, which no test catches (T4 covers a removed type, not a removed file). The contract specifies neither outcome. Passing `@(WireSchema)` instead is not safe either: the entry module is whatever the last schema reaches. Run here: `--ts --gen-all` on `workshop_wire.fbs workshop_authoring.fbs` writes an entry with 136 exports; on `workshop_authoring.fbs workshop_wire.fbs` (MSBuild's alphabetical glob order) it writes 127.
- **Consequence:** the full round fails on an existing S5 test that no S5b row predicts, or the TypeScript silently disagrees with the schemas after a schema-file deletion, the defect this slice exists to remove.
- **Fix (recommended default, Option A; the planner or coordinator decides):**
  1. Replace the literal root in `:26`, `:66` and task 1 with: "one `flatc --ts --gen-all` invocation over every `WireSchema`, ordered so that a schema comes after every schema it includes (a schema whose file name appears in another schema's `include` line goes first; the derived roots last), so the entry module is written by the root's run and re-exports every type it reaches. When a schema file is deleted, the remaining schemas are compiled the same way. T1 guards completeness on the real tree: a second, independent root would leave the entry short of the other root's types, and T1 fails naming them."
  2. Task 1 gains: "record the entry export count for both argument orders (measured at audit 7: 136 includer-last, 127 includer-first) and for `workshop_wire.fbs` alone (127)".
  3. Add matrix row T10: "A whole schema file deleted (`schemas/workshop_authoring.fbs`), then an incremental build | The build succeeds; no generated TypeScript file or entry export names a type only that schema declared (`SavedConstruction`); the entry exports exactly the remaining schema's types, derived from its text | No error expected". Table row: "T10 | S5's `WorkshopWireBuildTests.ADeletedSchemaFileLeavesNoGeneratedSource`, which now also asserts the TypeScript result | Control: `SavedConstruction` is exported before the delete. Boundary: the remaining schema includes nothing | planned". It extends an existing fact, so AC2 stays +8.
  - Option B (not recommended): name the root as a project item and fail the build with a typed error when it is missing. This changes S5's accepted M4 boundary and its test, which S5b's Never list (`:40`) does not obviously permit.

### B2. `FileWrites` outside `obj` and `bin` is never cleaned, so T8 counts the wrong event on a false basis (classification: test)

- **Where:** contract `:32` ("registered in `FileWrites` by glob after generation (a folder entry would leave the outputs after `Clean` and skip the target)"), `:33` (Inputs: "both schemas, the project file, the pinned digest"; Outputs: the entry module), `:56`, `:181` (T8 counts `TargetStarted` events named `GenerateWireTypeScript`).
- **Defect:** `CoreClean` (`Microsoft.Common.CurrentVersion.targets`, SDK 10.0.403, target at `:5986`) deletes only prior `FileWrites` that `FindUnderPath` places under `$(OutDir)` or `$(IntermediateOutputPath)`, and `IncrementalClean` filters the same way. Files under `tools/e2e/.wire/` are never deleted by `Clean`, whether registered by glob or by folder. With the contract's Inputs (no file under the intermediate directory), the three `--no-incremental` capture builds find the entry module newer than every input, and the target is skipped as up to date. T8 counts `TargetStarted`. If MSBuild raises `TargetStarted` for a target skipped as up to date (believed so, not verified here), "never zero" is vacuous: T8 cannot detect a target that never generates. If it does not, T8 reads 0 and fails in every round after the first. "The pinned digest" is not a separate input: it lives in the project file, which is already an input.
- **Consequence:** the one-writer and regeneration evidence T8 is meant to give is either absent or spuriously red.
- **Fix:**
  1. `:31` and `:33`: the target's Inputs and dependency are exactly S5's: `DependsOnTargets="ListWireSchemas"`, `Inputs="@(WireSchema);$(IntermediateOutputPath)WireSchemas.list;$(MSBuildProjectFullPath)"`, Outputs the entry module. `Clean` deletes `WireSchemas.list` (it is an S5 `FileWrites` entry under the intermediate directory), so every clean or `--no-incremental` build rewrites it and reruns the target, as S5's M7 does for C#. A deleted `.wire` folder reruns it through the missing output. Delete "the pinned digest" from both input lists.
  2. `:32`: delete the `FileWrites` sentence and its parenthesis; replace with: "`tools/e2e/.wire/` is outside `$(OutDir)` and `$(IntermediateOutputPath)`, so `Clean` never deletes it (`CoreClean` filters `FileWrites` by `FindUnderPath`); regeneration after a clean build comes from the intermediate-directory schema list in the Inputs." No `FileWrites` entry is needed.
  3. T8 (`:56`, `:181`) counts executions, not invocations: "counts the `Exec` tasks started inside target `GenerateWireTypeScript` of the FlatBuffers project file (`TaskStartedEventArgs` with that `TargetName` and `TaskName` `Exec`) and asserts exactly one per log". Keep the controls (0 and 2 refused, naming log and count) and the web-log boundary.
