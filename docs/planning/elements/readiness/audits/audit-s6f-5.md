# Planning audit: `spec-s6f-shape-and-mechanical-kind-tables.md` (S6f, the last slice), first audit (file 5)

Audited 24 November 2026 in the `spec-drafts` checkout at main `25df3cd5`, planning phase, read-only; nothing built or run. Contract: 2,031 words. Binding decisions: `owner-decisions-2026-11-22.md` (22, 24h, 3a, 37, 38). Complexity values come from the coordinator's threshold-12 log (`scratchpad/s6-metrics.log`), not re-measured. Scans: ast-grep 0.51.3, switches and per-member ladders as described in `audit-s6e-5.md` (constructor and `Add(...)` arguments excluded; `elements/`, tests, tools, generated code, `obj/` excluded).

## Verdict: Fail

The table idea is sound, and the pair table is a real improvement (`GenerateManifold` is at 21 and each new shape adds about eight arms). But as written: (1) it describes a pair table that does not match the code (a hollow pre-branch, swapped arguments, no typed refusal), (2) the pair test F1 cannot work (it fails on the baseline for hollow statics, covers only one argument order, and `WorkshopSceneCompiler` cannot build arbitrary pairs), (3) there is no measurement or rationale for a change on the solver's per-pair path, (4) AC1 names members that contain no shape dispatch, (5) its site lists miss about a dozen chains of its own enums and its closing statement (AC4, "closes S6") is undecidable and false, and (6) it is two slices of work. Under decision 24h the six slices together do not close S6 (finding B7).

### B2. The narrowphase table is not designed (wrong specified behaviour; changes the solver's dispatch)

Contract `:24`, `:30`, `:58`, Design Note 4. What the code requires and the contract omits:
1. The `IsHollow` pre-branch stays ahead of the table or becomes 33 cells. State which. If it stays, the table is 4 x 4 solid cells and "every ordered pair" (49) is false; if it goes, hollow cells hold `CollideHollow(partner, hollow)` with the hollow side chosen as today: when both are hollow, `colA` is the hollow side; otherwise the hollow one is.
2. Six of the 16 solid arms swap the arguments (`(Plane, Sphere)`, `(Sphere, Box)`, `(Plane, Box)`, `(Plane, Cylinder)`, `(Sphere, Cylinder)`, `(Box, Cylinder)`). A function pointer to `CollideSpherePlane` cannot serve both orders. State the cell form: `{ function, swapped }` with the call passing `(colB, colA)` when swapped, or six named wrapper methods. Box2D v3 registers one function per unordered pair and flips; here contact orientation (`ColA`, `ColB`) must stay as today, so a swap flag is the right form.
3. Pair order is set by collider index (`WorkshopPhysicsEngine.cs:870-877`, `PrepareContacts :1103`: `colA.Index < colB.Index`), so the same two bodies reach different cells depending on declaration order.
4. The call form: `static readonly delegate*<SimCollider, SimCollider, float, List<ContactPoint>, void>[,]` (the Simulation project allows unsafe, `CuriousContraptions.Simulation.csproj:6`) or delegates. Pick one and say why.
5. Index range: `ShapeKind` is 0 to 6; an out-of-range index throws `IndexOutOfRangeException` where today the switch is silent. Say it is unreachable (ingest) and that the lookup adds no default cell.
6. The three conversion switches `WorkshopHollowKernels.cs:16, :29, :159` map `ShapeKind` to the physics `ColliderShapeKind` and back; the values coincide (`Sphere` 0 to `Frustum` 6). They are conversions between two enums the contract forbids merging; state they become small tables or stay as a cast, with the reason.

### B3. F1 cannot discriminate and fails on the baseline for hollow statics (test)

Contract `:42`, `:134`, `:138`. Defects, each checked in code:
- `WorkshopSceneCompiler` compiles placed packages, so it reaches only the shape pairs delivered parts happen to declare; a missing cell for any other pair passes. The real admission path for arbitrary kinds is `LawScene` (`WorkshopPhysicsLawTests.cs`: `Box`, `Sphere`, `Cylinder`, `StaticBox`, `StaticSphere`, `StaticHollow`, `DynamicHollow`, a plane in the constructor, then `Admit()` through `PhysicsSceneDeclaration` and `PhysicsGpuAbi.Admission`).
- Both argument orders must reach the dispatch (B2.3). The existing hollow tests do this with a `reverseOrder` parameter (`WorkshopPhysicsLawHollowTests.cs:30-69`). F1 says nothing about order, so half the swapped cells may never run.
- "released 0.05 m above the static body's top, centred over it": over a `Tube` or `Frustum` the body falls through the bore, over a `Torus` through the hole; both are correct behaviour, so the stated bound fails on the baseline for those statics. For hollow-on-hollow pairs "top" is undefined.
- The bound "lowest point never drops below top - 0.01 m while over the footprint" does not apply to a body that rolls off a curved support; the contract notes this but not how the observation window ends.

Fix: replace row F1 and its test row with:
"F1. For each ordered pair `(A, B)` of the physics `ColliderShapeKind` values (7 x 7), built through `LawScene` in both creation orders, with the lower collider's top surface point on a vertical line through the upper collider's centre and the upper collider's lowest point `d = 0.002 m` above it (inside the speculative margin), `WorkshopCollisionKernels.GenerateManifold` (as `WorkshopPhysicsLawCylinderTests.Contacts` at `:969` already calls it) returns at least one contact and every contact's `Gap` is `d` within `1e-4` (the existing `Gaps` bound, `:975-980`), except `(Plane, Plane)`, which returns none. For a hollow lower collider the line passes through the wall (mid-wall radius at the top for `Tube` and `Frustum`, the ring centreline for `Torus`), never the bore. The expected `d` is the vertical distance between support points, computed in the test from the declared dimensions, independent of the production geometry. Control: the same colliders `0.05 m` beyond the margin return none. Boundary: both creation orders of the same pair return the same contact count and gaps within `1e-4` (symmetry); only pairs `PhysicsGpuAbi.Admission` admits." Then an end-to-end row F1e: "For one flat solid pair per arm of the 4 x 4 (Plane, Box and Cylinder-cap supports; Sphere, Box and Cylinder dynamics), `LawScene.Admit()` and `world.Step(world.TicksPerSecond)`: the dynamic body's lowest point never goes below the static top by more than 0.01 m while over its footprint (existing resting bounds, `WorkshopPhysicsLawHollowTests.cs:25-29`)". Hollow routing reuses the existing `WorkshopPhysicsLawHollowTests` theories as the probe's *present* evidence (they already run hollow against sphere, box and cylinder in both orders); F1 adds only the cells they do not cover.
