# Planning audit: `spec-s6b-response-codec-read-family-table.md` (S6b), fifth pass

Audited 24 November 2026, planning phase, read-only; nothing built, measured or run. Checkout `spec-drafts`, code at main `25df3cd5`. Binding decisions: `docs/planning/elements/readiness/owner-decisions-2026-11-22.md` (22, 24h, 24j, 24k, 37, 38). Standard: the audit brief and drafting brief. Contract lines are cited as `S6b:<line>`. Word count 2,131 (limit 6,000).

## Verdict: Fail

Six blocking defects in the contract text, all fixable without an owner decision. Four sit inside `<intent-contract>` (B1 to B3 and the R1 row), which is read-only after planning, so they must be corrected now. The route test as written reproduces the trap of the S6 fourth audit (F1): the production path refuses its input before the code under test runs.

## Blocking findings

### B1. "Wire bytes unchanged" cannot hold and cannot be tested (wrong specified behaviour; inside the intent)

- **Where:** `S6b:24` (Approach: "Wire bytes, the schema and every decoded value are unchanged"), `S6b:35` (Never: "a change to ... wire bytes"). Code: `engine/gpu/WorkshopWireFlatBuffers.cs:462-569`.
- **Defect:** Today the vectors are created in one order (ropes, guides, surfaces, transmissions, retentions, logic, actuator, loads, session, motion, electrical, drive targets, contact works, energy stores, chambers, finite work, airflow, gas, integrity, coordinate travel, bodies, captures, activations, timers, memory: `:471-516`) and the `Add` calls run in a different order, interleaved with fixed fields (`:517-566`). One table order cannot reproduce both, so the placement of vectors and fields inside the buffer changes. AGENTS.md forbids byte-identity acceptance, and the same contract forbids byte comparisons (`S6b:37`), so the claim has no test and is false as worded.
- **Consequence:** An implementer either builds two orders to honour it (needless machinery) or breaks a promise the contract made; a reviewer cannot judge it.
- **Fix:** In `S6b:24` replace "Wire bytes, the schema and every decoded value are unchanged." with "The schema, the set of fields and every decoded value are unchanged; where vectors and fields sit inside the buffer is not a contract (no byte-identity acceptance)." In `S6b:35` replace "wire bytes" with "the schema's field set".

### B2. "Same order on both paths" is false today (wrong specified behaviour; inside the intent)

- **Where:** `S6b:32`. Code: encode `ValidateResponseEncoding` `WorkshopWireFlatBuffers.cs:770-784` runs Memory, Capture, ScheduleIdentity, PresentationOwners, PhysicalRead; decode `:693-716` runs PhysicalRead, Capture, ScheduleIdentity, PresentationOwners, Memory.
- **Defect:** The sentence says the four validators run "in the same order on both paths". They do not today; read literally it asks for a change.
- **Fix:** Replace `S6b:32` with "On each path `WorkshopMessages.ValidatePhysicalRead`, `ValidateCapture`, `ValidateScheduleIdentity`, `ValidatePresentationOwners` and the memory check run in the order they run today (encode: memory, capture, schedule identity, owners, physical read; decode: physical read, capture, schedule identity, owners, memory), and each family's decoder runs in today's order (bodies, captures, activations, timers, energy stores, contact works, electrical, drive targets, ropes, guides, surfaces, transmissions, logic, actuator drives, contact loads, activation memory, motion, then retentions, chambers, finite work, gas, integrity, airflow, coordinate travel) so the first refusal for an input with two defects is unchanged."

### B3. R1 and its test cannot be satisfied: the encoder refuses a read with one family populated (test; inside the intent)

- **Where:** `S6b:43` (R1: "one read family populated ... every other family empty"), `S6b:142` (test row).
- **Defect:** `ValidatePhysicalRead` (`engine/gpu/WorkshopMessages.cs:18-44`) and the three read validators refuse most single-family reads at encode, before any row runs. A read past tick 0 requires motion (`:28`, `:29`); motion must bind to `Bodies` (`:28`); a capture's target must be a read body (`:41`); a gas store's body must be a read body (`GasReadValidation.cs:13`); a chamber candidate or departing body, or a finite-work payload, must be a read body (`ChamberReadValidation.cs:10-18`); a latched activation needs a body unless its kind is oscillator, threshold, timer or contact load, and a nonzero tick (`:31-36`); a broken integrity row and any coordinate-travel ordinal are bounded by the motion's last ordinal (`GasReadValidation.cs:20-24`, `CoordinateTravelReadValidation.cs:13`). A test that builds `new WorkshopRead(...)` with only family X therefore fails on the baseline with `ArgumentException`, or, if the author adds the prerequisites, no longer has "every other family empty". This is the same defect class as S6 audit F1.
- **Consequence:** The theory over 24 cases cannot be written as specified; the implementer has to discover the prerequisites per family.
- **Fix:** In `S6b:43` replace the R1 input with "A read built on the base read `WireFaultTests.PhysicalRead(1)` (one body, its committed motion, one capture latch), with exactly one further family populated by one row valid under the production validators, for each of the other 22 families; bodies, motion and captures are themselves each exercised by a case that varies them". In the test table (`S6b:142`) replace the control with "every family other than the base read's three and the one under test decodes empty; the base read's three decode equal to the base" and the boundary with "the family populated with two rows keeps its order, and with zero rows decodes empty (absent and empty vectors alike)". Delete "the largest admitted count field (rope `CutSpan`, timer ordinals)": no such bound is defined. R2 uses the same base. State the test-count delta now: 24 (R1) + 1 (R2) + 1 (completeness) + 1 (R3) + 1 (R4) = 28.

### B4. R3 does not say how a 42-field buffer is produced and admitted (test; inside the intent)

- **Where:** `S6b:45`, `S6b:145`. Code: `WorkshopWireFlatBuffers.cs:36-52` (the verifier runs first, then the field-count check).
- **Defect:** No test today asserts "Runtime record contains undefined fields." for a response (`rg "undefined fields" CuriousContraptions.tests` is empty). Only a buffer that the vendored verifier accepts reaches the check; otherwise the case ends in `VerifierRejected` and fails on the baseline, or an author asserts the wrong reason.
- **Fix:** Add to `S6b:145`: "Built with the raw builder, as `WireFaultTests.MessageWithoutSessionIsAMissingField` (`WireFaultTests.cs:198-208`) builds its response: `StartTable(42)`, `AddUlong(0, 10)`, `AddStruct`/`AddOffset(40, ...)` for `physical_commit`, and `AddByte(41, 1, 0)` so the vtable really has 42 slots. Asserted: `WireFaultReason.OutOfRange` and message `Runtime record contains undefined fields.`. Control: the same builder with `StartTable(41)` and no slot 41 passes the count check and is refused later with `WireFaultReason.MissingField` (no session), which proves the verifier admits the shape and only the count differs." If the verifier refuses the 42-slot buffer, the case returns to planning.

### B5. R4 cites a test that asserts something else; the decode refusal is untested (test)

- **Where:** `S6b:46` (R4 -> `WireFaultTests`), `S6b:27` (Always: the absent-motion `WireFaultException`).
- **Defect:** `WireFaultTests.CommittedReadWithoutMotionIsRejected` (`WireFaultTests.cs:191-196`) asserts `ArgumentException` at **encode** (`ValidatePhysicalRead`, `WorkshopMessages.cs:29`). The `WireFaultException(MissingField, "The committed read at tick N has no motion.")` is thrown only by `DecodeResponseRecord` (`:696-698`), reachable only from a buffer built without a motion vector. `rg "has no motion|MissingField" CuriousContraptions.tests` finds no test of it. The motion row will carry exactly this line, so a refactor could drop it unnoticed.
- **Fix:** In `S6b:80` list "decode refusal of a committed read without motion" under *Present, untested*, and add to `WorkshopResponseRouteTests` `ACommittedReadBuiltWithoutMotionIsAMissingFieldOnDecode`: raw builder as in B4 with a session, `tick` 5, `kind` Read, `publication` 1, `physical_commit` and no motion; expect `WireFaultException`, `MissingField`; control: the same buffer at tick 0 decodes with `Motion` null. Change the R4 row's test cell to that test (keep `CommittedReadWithoutMotionIsRejected` as the encode-side control).

### B6. The row shape is unspecified, so the central design question is open, and the benefit is overstated (Sufficient; design)

- **Where:** `S6b:24`, `S6b:66`, `S6b:112-118` (design notes 2 and 5).
- **Defect:** The 24 families are heterogeneous. Encoders return `VectorOffset?` (`:206-445`) or `VectorOffset` (`Chambers.cs:73`, `GasRead.cs:10`, `Retention.cs:10`), `EncodeEnergyStoreRead` always adds (even empty), others add only on `HasValue`. Decoders return `T[]` or distinct `Physics*Read` structs (`:787-870`, `Chambers.cs:85`) and feed one positional `new WorkshopRead(...)` call (`:700-706`); the eight presentation families are packed into one `PhysicsPresentationRead`; the motion decoder needs the decoded bodies and tick (`:697-699`); bodies need epoch and tick. A uniform row needs (a) an encode phase that stores up to 24 offsets with no per-tick allocation (a `stackalloc` span of `VectorOffset`, not a heap array), (b) an `Add` delegate per field, (c) a decode step that writes into a private mutable accumulator that the `WorkshopRead` constructor call reads, with a decode context (epoch, tick, bodies). None of this is stated, so each implementer will invent it, and the "a new family adds one row and its two functions" (`S6b:113`, `:116`) is false: a new family also adds a schema field, a `WorkshopRead` member, an accumulator member and the constructor argument.
- **Fix:** Add to the Code Map a "Row shape" paragraph: "A row is a private `readonly record struct ReadFamily(EncodeFamily Encode, AddFamily Add, DecodeFamily Decode)` of three `static` method-group delegates; `EncodeFamily` returns `VectorOffset?` (null: field absent); `AddFamily` is the generated `Wire.WorkshopResponse.Add<Field>`; `DecodeFamily(Wire.WorkshopResponse fb, in ReadContext ctx, ref ReadParts parts)` writes one member of the private mutable `ReadParts` struct, where `ReadContext` carries epoch, tick and the decoded bodies and the table lists bodies before motion. `EncodeResponse` holds the offsets in a `stackalloc VectorOffset?[Families.Length]`; no heap allocation is added. `ReadParts` and the `new WorkshopRead(...)` call remain the one place a new family is named besides its row." Replace design note 2 with "a new family adds a schema field, a `WorkshopRead` member, a `ReadParts` member, one row and its two functions; what it no longer adds is a branch to two complex members and a count literal", and note 5 with the same. If the owner of the slice prefers extraction (splitting both members into helper methods, as earlier slices did), say so as an alternative that meets AC1 without the accumulator; either is acceptable, but one must be chosen in the contract.
