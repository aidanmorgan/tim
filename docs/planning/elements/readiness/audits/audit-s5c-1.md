## Findings

### A1-1 (high) A second TypeScript frame check and identifier conversion

Evidence: Code Map keeps `tools/e2e/workshop-wire.ts:12740-12749` "`openFrame` stays as the TypeScript frame check" (a module-private `function openFrame`, not exported, in deferred e2e code the runtime `tsc` does not compile: `tsconfig.runtime.json:24-41`). The Code Map's description of the new script (spec line 131) gives its whole import list and its own check: "It imports the generated entry module and `flatbuffers`; looks up a root class by the `WireRootIdentifier` member name; frame-checks; then decodes". Its imports are only those two modules, so its frame check, and the "one conversion function per language" (Always), are its own and not `workshop-wire.ts`'s. As written there are two TypeScript frame-check paths and the required conformance test proves only the script's, not the one the e2e helpers use. Forward-only gate (AGENTS.md: "a second rule or code path for the same behaviour"); triage grades it high.

Repair: name one hand TypeScript module compiled by the runtime chain (for example `tools/runtime/wire-frame.ts`) that exports the size-prefix/length/identifier check and the `WireRootIdentifier`-to-bytes conversion; the conformance script and `workshop-wire.ts` both import it; delete `openFrame` and `COMMAND_IDENTIFIER`/`RESPONSE_IDENTIFIER`/`SAVE_IDENTIFIER` (`:12734-12736`) from `workshop-wire.ts`. Add the module to the owned scope and to S11's scan (exactly one TypeScript frame check).

### A1-2 (medium) Ruling (a) is not carried in full: no TypeScript-to-C# reason match

Evidence: ruling (a) requires the TypeScript decode to refuse "with a plain error that the test matches to the C# reason for the same buffer". S6 only asserts that TypeScript "refuses the same buffer with an `Error` and decodes nothing". Today's TypeScript check cannot make the match: one message covers both a short and a long buffer (`workshop-wire.ts:12744`, `declared !== bytes.length`), so `Truncated` and `TrailingBytes` are indistinguishable. Owner decision 24p's text of ruling (a) (`owner-decisions-2026-11-22.md:71`) also omits the matching clause.

Repair: the one TypeScript frame check (A1-1) refuses with distinct plain messages for short-of-prefix, truncated, trailing bytes and wrong identifier; S6's C# test asserts, per malformed buffer, that the script's refusal names the same failed check as the C# `WireFaultReason` (a mapping held by the C# test, so no TypeScript mirror of `WireFaultReason`, which the Never list forbids). Add the clause to 24p.

### A1-3 (medium) Harness number reporting cannot work as written; NaN case unjustified

Evidence: the script "holds no field, type or slot name of its own" yet reports "f32 values as their exact IEEE-754 bit pattern in hex". The object API types `float`, `double` and every 8-to-32-bit integer as plain `number` (generated `*T` classes), so without type information the script cannot tell an f32 from an int or a double, and `JSON.stringify(-0)` is `"0"`, so -0 is lost unless every number is encoded. NaN: ECMAScript leaves the NaN bit pattern written by `Float32Array`/`DataView.setFloat32` implementation-defined, so an "exact bit pattern" NaN assertion across a TypeScript re-encode is not guaranteed by the platform; save prevalidation refuses non-finite values (`engine/gpu/WorkshopSavePrevalidation.cs:104`, `:169`, `:189-192`), so a NaN may not be encodable through the production codecs the row requires. The contract itself drops the NaN-payload distinction elsewhere as gameplay-irrelevant (Code Map, `run-reset-snapshot.ts` bullet), which is inconsistent. (S5's "decoded domain value equals the original" is workable: existing round-trip controls already compare decoded commands and responses by value, `TypedTransportCommandTests.cs:191`, `:217`, and saves in `WorkshopFormatTests`.)

Repair: report every JS `number` as its IEEE-754 binary64 bit pattern (exact for every f32, int and double; keeps -0) and `bigint` as decimal; the C# side widens its expected values. For NaN, assert NaN-ness only, on a field whose production encoder admits it (name the field), or drop the NaN boundary.
