# Planning audit: `spec-s6f-shape-pair-tables.md` (S6f, shapes and the shape-pair table), sixth audit (file 6)

Audited 24 November 2026 in the `spec-drafts` checkout at main `0959e883` (code as at that revision), planning phase, read-only; nothing built or run. Contract: 3,295 words (limit 6,000). Binding decisions: `owner-decisions-2026-11-22.md` (22, 24h, 24j, 24k, 3a, 38, 42). Scans: ast-grep 0.51.3 plus a member scan (scripts in the session scratchpad, not committed) over the roots of S6b's switch command, excluding `elements/`, tests, tools and generated code.

## Verdict: Fail

The fifth audit's blocking findings are resolved in substance except where noted below (section "Fifth-audit findings"). The split from S6g is clean, the pair table is now designed, and the capability probe is honest. Seven new blocking defects remain, four of them in planned tests that would fail on the baseline or cannot discriminate: (1) the row shape of the shape tables is undecided, so tasks 2 and 3 are not actionable and no new production file is named; (2) about ten typed refusals in default arms are removed or contradicted by "no default row" with no replacement; (3) most tables have no test that every enum value has a route (owner decision 24h), and the case lists are hard-coded; (4) F4 fails on the baseline (every contact allocates a `ContactPoint` object); (5) F1e's bound is false for a curved static support and has no control for the plane cases; (6) F2 and F5 are under-specified (unnamed parts, "as today" as the oracle); (7) the Code Map contradicts itself on the broadphase ladder, and the intent contract miscounts the contact functions. Each fix below is exact text.

## Blocking findings

### B1. The row shape of the shape tables is undecided; tasks 2 and 3 are not actionable (wrong specified behaviour; Ready for Development "Actionable")

Contract `:24`, `:61-66`, `:92-97`. Siblings S6c to S6e each carry a "Row shape (decided)" paragraph (type, file, key, columns, layer). S6f has none: Approach says "a shape table of geometry functions (bounds, support, material point, containment, passage, surface tangent and witnesses, feature projections) keyed by `ColliderShapeKind`", but those members live in four assemblies and take different parameter types (`HollowPartner`, `HollowSolid`, `SimCollider`, `MaterialSurface`, the placement `Posed`), operate on different subsets of kinds (hollow-only, finite-only, all seven), and a row type that holds all of them cannot sit in Abstractions, which cannot see `HollowSolid` (`engine/gpu`). The Code Map names no new production file, so the owned-scope guard (compare against the baseline) cannot be applied, and AC1/"one table row per chain" (`delivery-batches.md:314`) is undefined. An implementer would have to design the tables, which is exactly what a ready contract must not leave.

Fix: add to the Code Map, after Decisions, a paragraph "Row shape (decided)" that names, per layer, the row type, its file, its key enum, the member it replaces in each column, and which kinds have a refusing function in each column (see B2). Minimum content (the author may refine names, not structure):
- Declaration layer, key `CuriousContraptions.Abstractions.ColliderShapeKind` (9 values): Bundle table in `CuriousContraptions.Bundle/BundleGeometry.cs` (replaces `:57`); the declaration-to-physics mapping in `engine/gpu/DeclaredPhysics.cs` (`:81`, `:101`); the declaration-to-placement mapping in `engine/PlacementPose.cs` (`Pose` `:187`); the `ColliderDescriptor.Hollow` predicate `:52` stays one membership flag in the Bundle table. Each lives in the assembly of its reader; none reads an engine table.
- Physics layer, key `CuriousContraptions.Gpu.ColliderShapeKind` (7 values): Abstractions: `ValidateShape` lane validation (`PhysicsDeclarationValues.cs:218`) as one validating function per kind; `engine/gpu`: one `ShapeRow` type (new file, named, added to `RuntimeSources.props` if under `CuriousContraptions.Core`) with columns surface count, derivative bounds, surface point, support, containment, passage reach, hollow-partner route, rigid-union distance, and (hollow kinds only) the `HollowGeometry` and `HollowContactQuery` row functions; hollow-only columns are refusing functions for the four solid kinds.
- Simulation layer, key `ShapeKind` (7 values): a `SimShapeRow` (new file) with columns collider extent, support point, broadphase bounds, rolling selection and the two conversions to and from the physics enum; and the 4 x 4 pair table of `{ function, swapped }` cells.
- Placement layer, key private `PlacementPose.Shape` (4 values): a row in `PlacementPose.cs` with columns reach, partner, support distance, vertical, overlaps.
Then list every new file in the owned scope and say which are in `RuntimeSources.props`.

State the number of added cases in AC3. Where a refusal is unreachable after ingest (the two "Unsupported hollow partner." defaults), say so and drop it with that reason.

### B3. No test that every enum value has a route for most tables; case lists are hard-coded (test; owner decision 24h, `delivery-batches.md:314`)

Contract `:45`, `:47`, Design Note 5, table `:141-146`. S6 closes when each table has "a test that every enum value has a route". ### B4. F4 fails on the baseline: every contact is a heap allocation (test; brief checks 5 and 7)

### B5. F1e's bound is false for a curved static support and has no control for the plane cases (test)

Contract `:46`, `:137`, `:142`. "The dynamic body's lowest point never goes below the static top by more than 0.01 m while over its footprint" over a `StaticSphere` for a dynamic box, cylinder or sphere: a release centred on a sphere's apex is unstable equilibrium; within the 1 s window a box tips and slides off, its lowest corner legitimately dropping more than 0.01 m below the apex while its centre is still inside the sphere's horizontal footprint. The contract admits the instability ("rest is not asserted") but keeps the bound and does not define the window, so the three StaticSphere cases can fail on the baseline. The control "the same release clear of the static body passes more than 0.1 m below its top" is also undefined for the three plane cases (there is nothing to clear) and for a static whose top is less than 0.1 m above the bench.

Fix: replace row F1e with: "F1e. Through `LawScene`, a dynamic sphere (radius 0.1 m), box (half 0.1 m) and upright cylinder (radius 0.1, half-width 0.1) released with its lowest point 0.05 m above the reference height of each static support: the bench plane, a `StaticBox` (half-extents 0.5 m, top 0.5 m above the bench) and a `StaticSphere` (radius 0.5 m, centre 0.5 m above the bench); the 9 cases; `world.Step(world.TicksPerSecond, observe)` with the per-tick callback. The reference height is the support's top for the plane and the box, and the sphere's centre height for the sphere. While the body's centre is horizontally within the static's footprint (for the sphere, closer to its axis than its radius), the body's lowest point is never below the reference height minus 0.01 m. Control: the same bodies released over the bench in a `LawScene(bench: false)` (plane cases), or laterally clear of the box and sphere (those cases) pass more than 0.1 m below the reference height within the second. Boundary: a box on a `StaticBox` and a plane as the static side. The bound is the contact-slop scale; a missing pair entry lets the body fall through by at least its own size (0.1 m or more) within 0.3 s, so the bound discriminates; no rest is asserted."
Classification: test.
