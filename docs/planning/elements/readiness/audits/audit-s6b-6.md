## Blocking findings

### B1. `S6b:32` promises a refusal order the specified design cannot keep (wrong specified behaviour; inside the intent)

- **Where:** `S6b:32` ("... and each family's decoder runs in today's order ..., so the first refusal for an input with two defects is unchanged"). Code: `WorkshopWireFlatBuffers.cs:693-707`.
- **Defect:** Today the wrapper constructors are not part of the decoders: `new PhysicsCaptureRead(latches)`, `new PhysicsActivationRead`, `new PhysicsTimerRead`, `new PhysicsContactWorkRead`, `new PhysicsElectricalRead`, `new PhysicsMemoryRead`, `new PhysicsPresentationRead(...)`, `new PhysicsDriveTargetRead` and `new PhysicsEnergyStoreRead` are arguments of the one `new WorkshopRead(...)` call (`:700-706`), evaluated left to right and interleaved with the late decoders `DecodeRetentions`, `DecodeChamberRead`, `DecodeFiniteWorkActuatorRead`, `DecodeGasStoreRead`, `DecodeIntegrityRead`, `DecodeAirflowRead`, `DecodeCoordinateTravelRead`. The wrappers validate and throw (`ArgumentException`, mapped at `:571-578` to `WireFaultException(OutOfRange, "Invalid committed response fields.")`, for example `PhysicsCaptureRead.cs:17`, `ActivationValues.cs:77`, `PhysicsGasRead.cs:37`), while decoders throw other types and messages (`Required` `MissingField` at `:729`, "Ready timer retained provenance." at `:797`). A table walk with a `ReadParts` accumulator (the contract's own row shape, `S6b:113`) runs every decoder in table order and then the one constructor call, so a capture-identity defect and a retention-row defect no longer refuse in today's order. No planned test pins this, and no gameplay defect depends on it.
- **Consequence:** The contract promises something the specified design breaks; a reviewer cannot judge it and an implementer either contorts the design or knowingly breaks a sentence of the read-only intent.
- **Fix (classification: wrong specified behaviour):** In `S6b:32` replace everything from ", and each family's decoder runs in today's order" to the end of that sentence with: "; each family's decoder keeps its own refusals (type and message) for an input with one defect. For an input with several defects, which of them the refusal reports may differ from today's; no test pins the order." Keep the validator-order clause and the sentence "No encoder refuses an input (read at planning: none throws)". Delete the decoder-order list from `S6b:32` (move it to the run log if wanted).

### B2. The exclusion premise is false, and an animation-primitive chain is unassigned (wrong specified behaviour; closure under owner decisions 24h and 42)

- **Where:** `S6b:91` ("none has a switch, a ladder or a wide member today (commands 1 to 4, then each use read)"), `S6b:101`, and `docs/planning/invest/delivery-batches.md:317` ("none of which has a switch, ladder or wide member"). Sites: `engine/presentation/AnimationBatch.cs:329-348`, `:430-446`, `:452-473`.
- **Defect:** Measured at `0959e883` by the contract's own command (1) over its own roots (207 switch nodes; 211 enum declarations, 210 names, `ColliderShapeKind` twice: all reproduced), 62 of the 172 excluded names have at least one `switch` whose arms name two or more of their members (for example `WorkshopCommandKind`, `TransmissionEngagementPhase`, `ChamberPhase`, `ClockMappingState`, `ScheduleControlKind`, `SimulationCadence`, `WorkshopSimulationPhase`, `WireFaultReason`, `AnimationKind`). The contract itself names two of them as having a switch (S6e keeps the `PrismaticCommand` switch at `SupplyRoute.cs:381`; `S6b:93` calls out `ui/WorkshopBenchPlacement.cs:48`). The premise is therefore false as written, and it hides one real capability chain: **`AnimationKind`** (`Clip`, `ExponentialFollow`, `Oscillation`, `Impulses`; `engine/presentation/AnimationBatch.cs:13`) is the closed set of the animation evaluator's four primitives (the design guide's own definition of a capability kind includes "animation primitive ... its kind is a closed enum"), and it is dispatched by a three-member ladder (`:329-348`), a four-arm switch (`:439-446`, inside the member at `:430`) and a three-member ladder (`:452-473`) on the per-frame path. The contract excludes it as an "evaluator option of one primitive" (`S6b:95`), which is wrong: the options are `AnimationRepeat`, `AnimationImpulseTiming` and `AnimationImpulseOverlap`; `AnimationKind` is the primitive. A second unowned group: the six discrete-state value maps, one overload per discrete driver, each a switch over that driver's state enum: `CuriousContraptions.Abstractions/ElementPresentation.cs:42-90` (`PresentationStateValues.Map` over `ActuatorObservationState`, `ContactLoadPhase`, `ActivationTimerPhase`; `PresentationFourStateValues.Map` over `TransmissionEngagementPhase`), `PrismaticPhaseValues.cs:11` (`PrismaticDrivePhase`), `PresentationFiniteWorkValues.cs:12` (`FiniteWorkObservationState`); `MapDiscreteState` selects among them (`WorkshopDeclaredPresentation.cs:588`). Replace the clause in `S6b:91` ("and none has a switch, a ladder or a wide member today (commands 1 to 4, then each use read): none gains a path when a capability is added") with: "Many have a switch or ladder over their own members (62 names at the drafting revision; the closing run lists them in the run log without reassigning them): each is a mapping among that enum's own lifecycle, state, result, message or mode members, or to another closed set of the same lifecycle, and none gains a member or a path when a capability is added.
