# Planning audit: `spec-s6c-presentation-route-tables.md` (S6c), fifth pass

## Verdict: Fail

Seven blocking defects. Four are inside `<intent-contract>` (P1 to P6 and the "undefined value" clause), which is read-only after planning. The central one: the driver-keyed chains the story exists to remove are mostly not in the owned scope, so S6 could close with them untouched; and the new route tests repeat the S6 fourth-audit trap (the compiled scene refuses the input before the code under test runs).

## Blocking findings

### B1. The per-driver source-reference ladders in both admission sites are unassigned (scope; wrong specified behaviour)

- **Where:** `S6c:22`, `S6c:57-62` (owned scope), `S6c:29` (Always), Slices table (`delivery-batches.md`: S6c "every `PresentationDriver` route and rule").
- **Defect:** The owned scope names `PresentationBindingValues` (`BundleValidator.cs:205`), `SupplyBundleValidation.cs:183-190` and `InvalidBindingValues` (`WorkshopCompiledScene.cs:341`), which carry only the payload rules. The same files hold the larger, mirrored per-driver chains that decide which source reference a driver requires and checks it exists: bundle `PresentationBindingIdentity :192`, `PresentationBindingSocket :245`, `PresentationBindingCapabilities :258`, `PresentationBindingAirflow :282`, `PresentationBindingGas :292`, `PresentationBindingFiniteWork :303`, `PresentationBindingRetention :315`, `PresentationBindingActuator :323`, `PresentationBindingEvents :343`; compiled scene `InvalidSupplyBinding :231`, `InvalidPhysicalBinding :248`, `InvalidAirflowBinding :251`, `InvalidGasBinding :255`, `InvalidFiniteWorkBinding :267`, `InvalidActuatorBinding :279`, `InvalidMechanicalObservationBinding :299`, `InvalidSignalBinding :313`, `InvalidBindingEvaluation :331`. Each is `driver == X != binding.Y.HasValue` for Socket, Guide, Airflow, GasShape, Integrity, FiniteWork, Store, Retention, Transmission, Actuator, SupplyNode and SignalNode. `BundleValidator.PresentationBindingCapabilities` is the very member the story cites as at 27. `rg -c "PresentationDriver\.\w+"` (production, excluding `elements/`, tests, tools): `WorkshopDeclaredPresentation.cs` 37, `ElementPresentation.cs` 33, `BundleValidator.cs` 22, `WorkshopCompiledScene.cs` 20, `SignalObservationRules.cs` 7, `SupplyBundleValidation.cs` 2. After S6c as drafted, adding a driver that needs a source reference still edits about fifteen members in two files. Also left: five per-driver branches inside the query helpers (`WorkshopDeclaredPresentation.cs:446` CommittedCount, `:447` oscillator pulse, `:468`, `:470` timer, `:499` supply), which the first S6 slice's Never freezes, and the event/oscillator-pulse branches at `:148`, `:189`, `:294`, `:303`, `:322`, `:362`, `:678`.
- **Consequence:** Owner decision 24h's closure ("every per-capability enum chain is a table") is not met for `PresentationDriver`, and the S6f slice, the last, would close S6 anyway. The two admission sites also stay able to drift, which the Always bullet and the Decisions section promise they cannot.
- **Fix:** Add to the intent Approach and to the owned scope: the driver row carries a "source reference" column (a closed set of the reference kinds above, each naming which `PresentationBinding` field it requires, and the rule that field must satisfy), and the two sites read it: the listed members of `BundleValidator.cs:192-359` and `WorkshopCompiledScene.cs:231-339` become one row-driven loop per site, with existence checks (owner, payload member) as static functions on the row. Name in the contract the members left alone, if any, with a reason: the per-driver value computations inside the query bodies (`:446-499`) are S6 first-slice territory and are excluded with that reason, and `PresentationBindingActuator`'s `CoordinateKind` switch (`BundleValidator.cs:330`) is S6f's. Because this enlarges the slice, see D1.

### B2. P1 to P3 reach neither admission site as specified (test; inside the intent)

- **Where:** `S6c:43` to `:45`, `S6c:140-142`.
- **Defect:** "The minimal binding that driver admits" is not a defined input. At the compiled site `ValidatePresentation` (`WorkshopCompiledScene.cs:216-229`) refuses a track in this order: `InvalidSignalBinding`, `InvalidSupplyBinding`, `InvalidPhysicalBinding`, `InvalidTrackFields`, `InvalidBindingEvaluation`, `InvalidBindingValues`, all with the single message "Compiled presentation track is invalid." A track re-targeted to another driver is refused by the driver-specific source checks first (S6 audit F1). At the bundle site `OutOfRange` accumulates errors, so presence of a named error is assertable but a minimal valid entry per driver needs ports, signal nodes, payloads (`PresentationBindingIdentity`, `Socket`, `Capabilities`). `Enum.IsDefined` guards run before the code S6c changes (`BundleValidator.cs:196-197`, `WorkshopCompiledScene.cs:325-328`), so P3 passes on the baseline and after any table, whatever the table does on a miss.
- **Fix:** Replace the P1 to P3 inputs: "For each `PresentationDriver` value taken from `Enum.GetValues`, the first registered part definition (`PartRegistry.Definitions`, ordered by `PartId`) whose presentation binds that driver (26 of 26 are declared by at least one delivered part: `rg -l "PresentationDriver\.<X>\b" elements/`), asserted not null; the bundle site is exercised through `BundleValidator.Validate` on that part's entry (pattern: `ComposableAnimationMappingTests.BundleValidator_ValidatesStateValues`, `:269`) and the compiled site through a real scene of that part (`CompiledSceneFixture.Compile`). P1: the unmodified entry and scene are admitted by both sites. P2: change one payload field only (`StateValues`, `FourStateValues`, `FiniteWorkValues`, `PrismaticValues`) on the real binding of each driver: the bundle site reports `Presentation.StateValues` (named error, `Assert.Contains`), the compiled site refuses with "Compiled presentation track is invalid."; the control for the compiled site is the same track unmodified, which is admitted (a single message cannot identify the validator, so the single-field change plus the unmodified control is the proof). No track's driver or source field is edited." Reword P3 as "the unchanged guard: an undefined driver is refused by both sites at their `IsDefined` check", and say in the Boundary that the table's miss branch for an undefined value is unreachable by design (as AC3 of the first S6 slice states) and is verified by reading.

### B3. The driver table cannot hold the continuous query column (design; wrong specified behaviour)

- **Where:** `S6c:24`, `S6c:61`.
- **Defect:** "The first S6 slice's continuous query table becomes the continuous route's column" of the driver table that "both admission sites ... read". `PresentationDriverRules` is in `CuriousContraptions.Abstractions`; `CuriousContraptions.Bundle` references only Abstractions projects (`CuriousContraptions.Bundle.csproj:11-15`), so the table must live there. The first slice's rows are `Func<Track, WorkshopRead, float>` over `Track`, a private class of `WorkshopDeclaredPresentation` (`CoreRuntimeSource`, `RuntimeSources.props:124`), which Abstractions cannot reference. One table cannot hold both. `MapDiscreteState` (`WorkshopDeclaredPresentation.cs:588`) has the same layering.
- **Fix:** Replace by: "Two tables on the one enum. Abstractions: `PresentationDriverRules`' data table (a `FrozenDictionary<PresentationDriver, DriverRow>`; columns: route class (event, continuous, discrete, none), signal source, normalized, physical, level, mapping set, payload member, source-reference kind (B1), observed signal node kind). Engine: the first slice's query table stays in `WorkshopDeclaredPresentation.cs` unchanged, and `MapDiscreteState` becomes a second engine table keyed by the same enum (rows for the six discrete drivers). The every-value test covers the Abstractions table through the public rules; the engine tables keep their own tests (first slice M3; the discrete theory here)." Remove "becomes the continuous route's column" from `S6c:24`, `:61`.

### B4. Undefined and unlisted-value behaviour is not what "refused as today" says (wrong specified behaviour; inside the intent)

### B6. P5 and P6 are not executable or have the wrong error name (test; inside the intent)

- **Defect:** P5 samples "at the start, the midpoint and the end of its duration" for every curve. `ExponentialFollow` and `IntegratedRate` are admitted only on continuous physical drivers with `Duration == 0` (`Supports`, `ElementPresentation.cs:293-296`), so they have no duration; `Linear` on a physical driver also has zero duration; `CubicSmoothStep` is admitted only on level and event drivers (`:299-306`); `CubicSmoothStep` is declared by no package (`rg -l ... elements/` is empty), nor `LocalZ`. - **Fix:** Replace P5 with a per-curve table in the contract, each case on a real compiled track with the curve re-targeted to one the track's driver admits (`Supports`), and each expectation named: SmoothStep `3t^2 - 2t^3`, CubicSmoothStep `6t^5 - 15t^4 + 10t^3`, Linear `t` (a level driver with duration > 0), SineSquaredPulse `sin^2(pi t)`, LinearDecay `1 - t`, SmoothRiseFall the definition in `AnimationEvaluation.cs`, sampled at t = 0, 0.5, 1 of the duration within 1e-5; `ExponentialFollow` (physical driver, duration 0): after one response time the value has covered `1 - 1/e` of a step within 1e-3 of the step; `IntegratedRate`: after t seconds at constant rate r the angle is `r * t` within 1e-4 rad (state the quantity's gameplay reason: a wheel turning at the committed speed). The theory is over `Enum.GetValues<PresentationCurve>()` with this per-curve input table checked to cover all eight. P6: "Presentation.DriverCurve (bundle) and 'Compiled presentation track is invalid.' (compiled); control: the same curve on an admitting driver is admitted."
