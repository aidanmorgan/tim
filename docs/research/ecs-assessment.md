# ECS assessment for Curious Contraptions

**Owner disposition: deferred research proposal.** This assessment creates no ECS library, prototype or consumer-contract prerequisite. Current numerical authority remains [WGSL f16](../gpu-f16-physics.md); current work follows [TODO](../../TODO.md) and the [owner deferral](../delivery-workflow.md#pipeline-priority). Research date: 1 October 2026. Work ID: ECS-ASSESSMENT. Author: implementation subagent `/root/ecs_research`. This is an architectural recommendation, not an adopted migration or a performance qualification. [Implementation evidence](../verification/ecs-assessment/implementation.md) records the inspected working-tree identity; independent review is a separate gate.

**Deferred proposal: use ECS-style composition for the extracted simulation/gameplay layer, while retaining specialized numerical storage and Godot presentation. Evaluate a C# ECS library against an equally extracted, optimized typed-array implementation before adopting the library. A wholesale engine rewrite is not justified by the evidence.**

Flexibility and reuse are the strongest reasons: capabilities can be assembled independently of a part's scene class. Better performance is plausible where contiguous data, cached queries and less allocation replace expensive work, but ECS itself guarantees neither faster physics nor the required FPS.

## Comparing the choices

| Choice | Flexibility and reuse | Performance and delivery tradeoff | Assessment |
| --- | --- | --- | --- |
| Extract current runtime into pure C# owners, typed capability registries and dense arrays | Good; reusable laws and explicit scheduling need no framework | Least framework overhead; bespoke query/lifecycle maintenance remains | Mandatory fair comparator; potentially sufficient |
| ECS for capability composition/orchestration, specialized solver arrays, separate animation owner, Godot presenter | Strong for many combinations of sensors, sources, constraints and cosmetic behavior | Possible batching/locality gains; entity mapping, queries and structural changes cost time/memory | Preferred architectural direction, conditional library adoption |
| Convert solver internals, animation, scene graph and rendering wholesale into one framework | Uniform vocabulary, but numerical constraints and presentation do not naturally become independent entity updates | Highest migration/proof burden; risks duplicated state and loss of mature algorithms | Do not undertake without measured, specific justification |

An illustrative target composition combines electrical input, finite-supply accounting, shaft/joint binding and an indicator. [MotorPart](../../parts/MotorPart.cs), lines 15–54, currently declares inputs, shaft/joint bindings, ports and animation; lines 91–98 gate torque on a boolean power input and calculate a per-step work limit. Those declarations do not establish a finite electrical reservoir: finite-supply accounting is part of the proposed composition. A shared actuator system could process electrical-to-mechanical demands for a motor and linear pusher using typed capability data. Hinge versus slider kinematics stay explicit; a fan additionally requests airflow transfer. A lamp may reuse supply accounting and indicator presentation without owning a shaft. This is a proposed design example, not a claim these parts have identical laws.

Systems must generate requests to the shared conservation/constraint solver. Independently applying motor, gas and electrical updates can spend the same stored energy twice or introduce order-dependent one-tick delays. Composition is valuable only with validated combinations, explicit phase ordering and one authoritative owner for each state quantity. Avoid a universal component with dozens of optional fields, and avoid scattering one part's rules across undocumented systems.

## Architecture that fits the required workers

| Context | Owns | Exchanges |
| --- | --- | --- |
| Physics worker: fixed 120 Hz, initially four outer substeps | Authoritative capability/entity state; timers, networks and event order; bodies, contacts, coupled solver and transactional checkpoints | Validated commands in; committed timestamped poses, observations and reliable discrete events out |
| Animation worker: initially 60 Hz | Cosmetic clips, phase, easing and animation history; optionally an independent ECS store if it earns its cost | Committed observations/events in; immutable or transferred animation samples out |
| Browser main thread: display-paced rendering | Godot nodes/resources, UI/input, interpolation and final property submission | Typed commands out; bounded histories in; never synchronous worker waits |

This preserves [REQ-01–14](../delivery-workflow.md#standing-requirements), including the permitted main-thread renderer, 60 FPS supported baseline/qualified 90 FPS tier, exclusive mutable ownership, exact Reset and forward-only refactors. It does **not** require a third Web Worker. ECS is a data model; worker hosting, clock policy and transport still need implementation.

The pinned host uses .NET 10, Godot 4.7.2 and 2dog managed/native versions 4.7.2.91/4.7.2.6 ([build pins](../../Directory.Build.props), [web host](../../CuriousContraptions.web/CuriousContraptions.web.csproj)). Current [2dog documentation](https://2dog.dev/hosts/web) says its Godot/.NET host is single-threaded. A library's parallel-query API cannot overcome that. Separate single-threaded C# worker runtimes remain the planned path; successful startup, transfer and memory qualification are still required. The [.NET runtime threading documentation](https://github.com/dotnet/runtime/blob/main/src/mono/wasm/features.md) describes a distinct experimental threaded configuration, cross-origin isolation and interop restrictions; that is not evidence of support in these pinned 2dog binaries.

## Storage, scheduling and package risks

[Unity's archetype documentation](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/concepts-archetypes.html) describes grouping identical component sets into packed arrays. Its [structural-change documentation](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/concepts-structural-changes.html) explains entity moves and reference invalidation. These illustrate mechanisms, not a recommendation to introduce Unity.

For this game's mostly stable Run topology, archetypes are plausible. Numerous uncommon component combinations can waste capacity; adding/removing tags every tick can cause churn. Store frequent state transitions in enum-typed values or qualified enable masks, and batch actual topology changes at deterministic transactional boundaries. [EnTT's sparse-set design](https://skypjack.github.io/entt/md_docs_2md_2entity.html) illustrates the alternative of independent component pools. Such storage can suit varying capability sets, but multi-component joins and relationship traversal have different costs. Benchmark actual combinations and mutation rates.

Packed component arrays are not necessarily field-level structure-of-arrays. Large structs waste bandwidth when a system reads one field; reference-bearing components still chase objects. Prefer small value components or specialized field arrays in measured kernels. Avoid duplicating mutable physics state in both ECS and solver storage: either the solver owns it and components hold typed handles, or one shared owner exposes qualified views.

An ECS scheduler does not establish independence between coupled systems. Explicit dependencies and ownership remain necessary; [Unity's job documentation](https://github.com/Unity-Technologies/EntityComponentSystemSamples/blob/master/EntitiesSamples/Docs/jobs.md) separately defines scheduling/dependency machinery. Start each worker with deterministic sequential phases. Any later intra-worker parallel solver experiment must preserve canonical reduction/contact/event order and demonstrate actual runtime support.

Entity slots/chunk indices must remain internal. Use typed stable construction/body IDs and world generations at worker/save boundaries; rebuild local entity mappings from validated current declarations. Reject stale handles after Reset, deletion or reuse. Preserve full-width identifiers, command application tick/phase/order, queued events, RNG state if introduced, and structural-command queues in replay/rollback. A query's incidental traversal order must not decide physical results.

Two relevant C# candidates:

- [Arch](https://github.com/genaray/Arch) offers archetype/chunk storage, command buffers and optional parallel queries. Its [FAQ](https://arch-ecs.gitbook.io/arch/misc/faq) requires attention to component registration/source generation for AOT and explicitly leaves spatial queries to other structures.
- [Friflo.Engine.ECS](https://github.com/friflo/Friflo.Engine.ECS) advertises managed C#, typed queries, relationships and WASM/Godot/Native AOT support. Its [release documentation](https://friflo.gitbook.io/friflo.engine.ecs/project/package/release-notes) records explicit AOT registration for specialized indexed/relation types.

Neither is qualified for this exact build. Native AOT claims do not prove browser Mono/WASM AOT behavior. Pin an exact package version, license and transitive dependency set before a probe; verify trimming, component discovery, generic instantiations and serializers in the published bundle. The current host already roots reflection-reached assemblies; [Microsoft's trimming guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming) recommends analysis and a published test application. Whole-assembly rooting has download/startup costs; suppressing warnings is not proof. [Browser AOT guidance](https://learn.microsoft.com/en-us/aspnet/core/blazor/webassembly-build-tools-and-aot?view=aspnetcore-10.0) describes a code-size/performance tradeoff, not an assured benefit for this host. No vendor benchmark is used to predict our FPS.

## Bounded decision experiment, before committing to a migration

The owner has deferred this experiment. The following proposal is retained for a future explicit decision; it is not authorized work, completed proof, or a prerequisite to current contracts or P0-035.

1. **Freeze the comparison.** Use one existing motor–supply–load construction and its disconnected/blocked controls, one timer/indicator composition, and sparse/dense/repeated-Reset stress fixtures. Declare exact bodies, contacts, joints, capability combinations, animation bindings, mutation rates and device envelopes before runs. Compare A: current baseline; B: extracted typed-array/registry implementation; C: the same extracted slice using one candidate ECS, retaining identical solver algorithms. B and C must use the same worker topology, serialization and optimization level. Attribute worker separation gains separately from storage gains. Select at most one library for the first probe from a recorded compatibility review; do not turn this into a framework tournament.
2. **Prove semantics and packaging first.** Publish native and exact browser configurations; execute startup/query/serialization/Reset under trimming and each intended AOT mode. Prove canonical typed boundary rejection, stale-generation rejection, structural-change rollback, command/event ordering, energy/contact invariants and deterministic replay at equal ticks. Exercise real Chrome/Playwright construction, connected and negative controls, changed configuration, Run/Reset and Save/Load for every affected part/mode. Compare physics with cosmetics disabled and across independent clock rates. Synthetic large workloads supplement UI proof.
3. **Measure fairly.** Freeze hardware/browser/power/viewport and bundle hashes. For a standalone extracted-kernel harness using identical B/C worker/protocol settings, use randomized pairs: 30 seconds warm-up followed by five 120-second captures per case. This harness does not replace application UI or FPS proof. The current Workshop stops Run after 30 simulated seconds, and goals may end it sooner (lines 723–731). For application B/C comparisons use five paired actual-UI attempts with identical actions and the unchanged timeout/goals; warm through complete preceding attempts. Retain entire Run windows and separately report construction/Reset/startup phases, wall/simulated duration and early termination. Never splice short runs into claimed sustained FPS or silently override the timeout. Predeclare minimum usable observation durations; insufficient samples remain Incomplete. Measure whole-tick and selected-system p50/p95/p99, allocation/GC, solver work, transport/freshness, distinct presentations, startup and per-runtime peak/retained memory; include 20 lifecycle cycles. Repeat controls to estimate variation; do not treat correlated ticks as independent statistical trials.
4. **Decide using predeclared gates.** Suggested comparison thresholds, subject to recorded agreement before measurements: at least 10% lower p95 service for the selected orchestration workload than B, with a paired-run 95% confidence interval excluding zero improvement; no greater than 5% regression in whole-tick/frame tails, startup or peak/retained memory. This 5% tolerance never permits crossing an applicable absolute limit or worsening an existing absolute-budget failure. No additional steady-state scratch allocations. No conclusive interval means Incomplete, not a win. Independently demonstrate one additional existing capability combination requires declarations/bindings rather than a copied per-part update algorithm, without obscuring law ownership.

**Stage distinction:** A valid research comparison may expose existing budget failures and still inform the design; it does not qualify a migration or FPS. Before accepting a scoped implementation, freeze its required-now absolute limits, correctness and non-regression gates, plus named outstanding full-engine obligations. New or worsened failures block that slice; retained baseline failures stay explicitly open under P0-034/035. All applicable standing budgets must pass before the engine release gate and product work. A library may be selected for verified reuse without a speed win only by an explicit architecture decision and passing scoped gates; never label that a performance improvement. If it loses to B, retain the extracted component/system design with specialized arrays. Unmet final budgets keep optimization and release qualification open.

Any adopted slice replaces its old owner and all callers/content/tests together. Remove old callbacks, duplicate state, package experiments, obsolete documentation and superseded supported schemas after cutover; preserve historical evidence only. There is one current implementation: no runtime choice between old/new paths, aliases, fallback modes or format migration. Separate experimental builds are comparison artifacts, not supported compatibility systems. Every implementation increment and its cleanup require a distinct adversarial review subagent and fresh affected behavior/performance evidence.
