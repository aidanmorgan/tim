Forward-only changes, enum typing, evidence integrity and palette preservation apply immediately. The present runtime has not yet proved the target architecture/FPS budgets: its deficits remain explicit failures owned by the P0 migration. **P0-035 must establish every applicable runtime requirement before product work. ### Focused agentic engineering and reusable role prompts

These rules adapt the four principles in the [Karpathy-inspired community guidance](https://github.com/multica-ai/andrej-karpathy-skills) and its [agent instructions](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md). This is a community synthesis, not an official specification authored by Karpathy. The cited original post was inaccessible during this review; no direct verification of that post is claimed. The delivery cadence, retained review pair and progress triggers below are project-specific rules.

- **Make uncertainty explicit.** State assumptions that could change behavior or acceptance, inspect the current owner and callers, and identify material alternatives before coding. Resolve routine choices from current contracts. Ask the user only for a consequential unresolved decision; continue independent authorised work.
- **Choose the simplest complete design.** Implement the required behavior with existing patterns. Add abstractions, configurability or infrastructure only for a current requirement or demonstrated dependency. Simplicity cannot remove required cadence controls, rejection, rollback, lifecycle safety or numerical precision.
- **Keep changes surgical.** Every changed line must serve the selected outcome, its necessary caller/content cutover, verification or documentation. Avoid adjacent cleanup and speculative optimisation. Surgical scope includes the entire affected dependency closure: it cannot leave a retired path, incompatible caller or partial forward migration behind.
- **Define observable success first.** Translate the outcome into independent expected results and named positive/control/boundary checks before implementation. Use a short sequence of action → discriminating check. Investigate a failure with a concrete hypothesis; do not tune the oracle to the observed output. Reuse applicable proof under the existing identity policy.

Use these short role prompts with the slice's existing record and exact source criteria; do not paste the whole backlog or duplicate contracts into each assignment:

| Role | Assignment |
| --- | --- |
| Coordinator | Name the current observable outcome, existing IDs, genuine dependencies, allowed scope, required-now checks and deferred enforcing gates. Resolve conflicting current guidance before dependent work. Retain the pair, make scope decisions and maintain current/next ready outcomes. |
| Implementation owner | State material assumptions and the smallest complete design. Implement one outcome and its affected callers/content; run targeted checks and return exact changes, actual results, unresolved risks and the next check. Retain ownership through fixes. |
| Independent reviewer | Read the actual diff and source criteria, derive independent expectations and challenge affected direct/transitive behavior. Map each blocking finding to a criterion, failure/risk, reason it blocks and smallest resolving check. Independently re-review fixes; preserve the required identity, impact matrix, evidence and verdict. |

**Directed backlog progress:** When the user authorises the full TODO-linked goal, keep only the current slice and the next one or two ready outcomes in the working sequence. After independent acceptance and required publication, advance without routine reconfirmation. Honour engine-first, technical prerequisites and individual element publication; an intermediate runnable checkpoint cannot close the complete contract. For a narrower user request, stop at its authorised boundary.

**Stagnation trigger:** After roughly 45 minutes without newly runnable behavior or a resolved concrete blocker, or two failed attempts at the same setup/check, the coordinator briefly reassesses the current hypothesis, acceptance criterion and next experiment. For documentation/design slices, use a concrete reviewable decision or correction as progress. Continue a longer investigation only with a stated reason and new discriminating evidence; otherwise narrow the experiment or advance genuinely independent authorised work. Record a blocker with owner and retry condition when external change is needed. This is a replanning trigger, never a time limit on required proof or permission to waive a gate.

**Bound supporting work:** Before expanding instrumentation, evidence collection or research, identify the acceptance question and how the result changes the next decision. Smoke-test collection before expensive runs. Reuse existing records and original raw evidence; report runtime delivery separately from tests, plans and captures. Preserve failed attempts and required global audits; unrelated findings retain their owners, while unknown affected coverage remains Incomplete. These rules refine execution within the paired workflow and stage gates above; they do not replace any criterion.

### Evidence identity and hashing

Capture identities once for the scoped frozen candidate, including relevant additions, deletions and generated/untracked inputs. Reuse existing immutable Git/blob or build-manifest identities when they establish the exact bytes; hash only relevant uncommitted inputs, scoped diffs and new artifacts whose identity is not already established. A path or timestamp alone is not byte identity. Reference original evidence instead of copying manifests or hashing reports into their own approval.

The independent reviewer validates identity and applicability when accepting or reusing proof. Recompute only changed or unknown relevant identities, a concrete mutation/mismatch concern, or an applicable acceptance/publication boundary that requires a fresh comparison. An unchanged trusted identity need not be recomputed for every read, turn, status edit or before/after every test. Do not routinely hash the whole bundle, workspace or evidence history, or reconstruct old reports merely to hash them; inspect the scoped changes and retain the original evidence. Unknown relevant identity remains Incomplete; unrelated missing identities and unrelated HEAD changes do not block scoped acceptance. Relevant contract, tool and environment changes still invalidate affected proof.

Actual loaded/deployed build identity remains required for browser and publication proof. Tie the observed runtime to the approved artifact using existing immutable asset/build identities and runtime/network observations; local disk hashes or a later refetch alone do not prove which bytes the running page loaded. Hashing every CDP response body is not a universal requirement. Investigate mismatches within their relevant input scope. These rules preserve all required audits, failed attempts, Anvil checks and publication gates; hashes establish identity, never behavior.
