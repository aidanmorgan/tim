## Findings

**F1 — High, blocking. An over-size scene faults the session, and the admitted capacity range is not representable.**
- **Over-limit path.** `EventRecordProducer.Compile` → `EventRingBuffer.Capacity` throws a bare `ArgumentOutOfRangeException` when slots exceed 2^26. The probe confirms the exception type (`probes/capacity-probe.out`).
  - `Compile` runs inside `WorkshopGpuDevice.Stage`'s try, which rethrows the exception.
  - `WorkshopSimulation.Construct` (and the other `Admit` callers) do not catch it in the typed `GpuAdmissionException` → `Reject(WorkshopRejection.GpuAdmission)` branch, which keeps the Building phase. It reaches the generic `catch (Exception)` → `Failure(owner, InvalidRead)`, which sets `Phase = Faulted`.
  - So an unsupported scene faults the session instead of being refused explicitly and atomically, contrary to the AGENTS refactor rule ("reject unsupported inputs explicitly and atomically").
  - This is shown by the deterministic code path plus the exception-type probe. The over-size scene itself was not built, since it needs about 1.1 M rows.
- **Admitted range not representable.** `Capacity` admits every capacity up to `MaximumCapacity` = 2^26. Every slot count in (2^24, 2^26] rounds to 2^25 or 2^26, and for those `EventRingBuffer.ByteLength` throws `OverflowException`.
  - `ByteLength` is used only by the C# reference writer and consumer, which are test references and not production C#.
  - Production asks `worker.js` for a 2–4 GiB `SharedArrayBuffer`. Node 64-bit allocates both lazily (`probes/sab-allocation-node.out`). Whether Chrome allocates them is unproven and belongs to the pending browser and resource gates, so a fault after commit is **not** claimed here.
- **Reachability.** Free play has no population bound (`WorkbenchCapacityTests`: "memory is the only bound"), and Impact and Passage rows are quadratic. For example, about 750 contact-work owners × 750 dynamic bodies at 240 Hz exceeds 2^26.
- **Why it blocks.** It is a demonstrated untyped fault on an unsupported input inside this slice's new admission path.
- **Smallest resolving check.**
  - Choose a limit whose byte length is representable, for example 2^24 slots (1 GiB), or lower by decision.
  - Refuse `slots > limit` through the typed admission rejection (`GpuAdmissionException` or an equivalent typed reason).
  - Add a native boundary test at the limit and at limit + 1 that drives `Capacity`/`Compile` and the device admission path (or an injected row count). Expect a typed rejection, the Building phase kept, and no fault; `ByteLength(limit)` must be computable.

**F2 — Medium, non-blocking; forward to 9A.23. The consumer contract.**
- **Impact source.** 9A.23's delete list removes "the occurrence arrays in `PhysicsContactWorkRead`", but `EventRecordProducer.Stage` sources Impact from exactly those rows. 9A.23 must keep the device-side occurrence rows, or re-source Impact, before deleting them.
- **Reader fences.** `EventRingConsumer` (`Volatile` acquire/release only) is a reference reader, not a sound cross-thread seqlock: the trailing sequence re-read does not order the preceding copy. The 9A.23 JS reader needs `Atomics.load` on both sides and should get a concurrent stress test.

**F3 — Low, non-blocking. Conformance covers one wiring per package.**

- This mutant only inflates rows and capacity. Indicators never emit transitions, so it publishes no record.
- **Suggested check:** add latch → level-lamp and plate → level-lamp conformance benches.

**F4 — Low, non-blocking; performance gate. The bound is justified but quadratic.**

- **Large sandbox.** 200 balls with 200 bumpers give about 2.4 M slots, so 4 Mi slots (256 MiB).
- **Where it is handled.** Memory qualification belongs to the named performance and resource gate.

**Is 1 record per tick per producer a sound bound?**

## Addendum (append-only, 24 Oct 2026): the writer's torn-record defect is fixed by 9A.23 + 9A.25b

This addendum is recorded by the independent reviewer of 9A.23 + 9A.25b. It leaves the verdicts above unchanged and adds the later finding and fix.

**Defect.** The 9A.22 Simulation worker `writeEventRing` wrote each slot as follows: `Atomics.store(sequence, 0)`, then a plain `target.set(payload)`, then `Atomics.store(sequence, seq)`. Under the JS memory model the plain payload stores race with the sequence words.

- On arm64 they were observed to be reordered past them, so a reader could accept a torn record.
- **The reader's role:** the reader that exposed it was 9A.23's first shared reader, which also copied the payload plainly. In round 1, the shipped stress test failed in 7 of 63 runs on the unmodified code (`evidence-9a-23-25b-review/seqlock-probe.txt`, `cursor-run-16.log`).
- **Why it was missed:** 9A.22's own review could not observe it, because the slice had no concurrent reader, and its F5 accepted the fences by inspection.

**Fix.** It is published at main `f1ad3bd19e27` (merge of `da2de5b3`).

- The ring's shared memory is reached only through `EventRingMemory`, in `event-ring-cursor.js` and its C# reference twin. Its only accessors are per-word `Atomics.load` and `Atomics.store`.
- The writer's seqlock is sequence 0, then each payload word stored atomically, then the sequence. The reader's is sequence, then each payload word loaded atomically, then the sequence.
- `EventRingMemory` has no raw buffer accessor. The ring leaves the writer only through `postTo`, and the cursor's ring is private.
- `EventRingConsumerTests.GuardOnlyTheEventRingMemoryViewsTheRingAndEveryAccessorIsAtomic` checks the encapsulation. The reviewer's one-sided and bypass mutants (G1–G6) are killed.

**Verification.** See `review-9a-23-25b-ring-consumers.md`, rounds 1–5 and the terminal section: CI 40055713865 and deployment 7293319272.

**This closes the 9A.22 hand-off item F2** (reader fences): it is superseded by fully atomic payload access on both sides.
