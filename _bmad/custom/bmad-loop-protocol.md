# BMAD loop protocol

Project customization, effective for the owner's requested loop repair. The workflow overrides load this protocol through supported activation hooks. It replaces only the native branches named below; other installed instructions remain. The checker below enforces only its named structural checks; routing, isolation, repairs and acceptance remain explicit coordinator instructions. Missing inputs or unresolved conflicting instructions block the affected approval.

## Effective configuration preflight

Before routing or dispatch, resolve the installed base → team → user workflow and inspect the effective merged configuration, not just this team's TOML. Compare against the installed route and these required layers: Auto requires six configured IDs — blind-hunter, edge-case-hunter, verification-gap, intent-alignment, forward-only, element-free-engine. [Review tiers](#review-tiers) decides which of them a pass launches; a layer that tier does not launch is skipped by its `when` condition, never removed or emptied. Build review requires blind-hunter, edge-case-hunter, verification-gap and element-free-engine; Build oneshot requires blind-hunter and element-free-engine. Code Review requires blind-hunter, edge-case-hunter, verification-gap and element-free-engine, plus acceptance-auditor in full mode. Preserve other installed/configured applicable layers. Generic Review validates the selected native lens set and requires element-free-engine for project engineering approval; an exact partial request remains partial.

For every required layer/lens, verify presence, nonempty instruction, applicable activation (including its when condition), readable instruction inputs and the protocol/engineering hooks. A user override disabling or replacing a required layer does not waive this gate. Missing, empty or inactive required instructions mean Incomplete before dispatch. The one exception is a layer that its `when` condition leaves inactive solely because of the slice's recorded [review tier](#review-tiers) or pass number: that is the tier working, not a missing layer, and its instruction must still be present and nonempty. Record the effective route and checked IDs in native review notes. Validate fields and commands against the installed customization schema and CLI help; do not invent renderer flags or customization keys. Follow documented resolver recovery; Build/Auto renderer failure halts as installed.

The four review/build entry hooks invoke `dotnet run --file tools/anvil/VerifyPolicy.cs -- --bmad-check --project-root <absolute-root> --route <route>` before dispatch. Use Auto, BuildReview or BuildOneshot, CodeReviewNoSpec or CodeReviewFull, and ReviewEngineering or ReviewPartial with explicit `--lenses` for the latter. The checker consumes the installed resolver's effective JSON and exposed base shape, checks supported fields, required IDs/nonempty instructions, policy-file readability and hook wiring. It does not evaluate prose conditions, enforce agent execution or replace this preflight: inspect each reported condition and the route semantics before approval. A structural failure is Incomplete; a structural Pass alone is not active-layer or semantic approval. Reuse a matching result until relevant customization/schema/tool/policy inputs change.

**Policy is this checkout's policy.** Every policy file, guide, role card and tool the loop loads is read from the checkout being worked on, at a path relative to its root. Do not read one from another checkout by absolute path, and do not record such a path in a contract's `context:` list. The checker refuses a policy reference that resolves outside the project root and reports a required policy file that is not in git's index (`UntrackedPolicy`); either is Incomplete before dispatch. The checker covers the persistent policy files, the role cards and the spec template; paths written inside prompts are the coordinator's to resolve inside the checkout. A policy change is published like any other slice before a later slice relies on it, under the AGENTS.md Stable rules: a slice already in review finishes under the rules it started with.

### Session environment check

Run once when a session starts or resumes, before the first build, and record the result in the run log: the pinned Node version (`test "$(node --version)" = v26.12.1`), `dotnet --version` against `global.json`, `dotnet workload list` showing the wasm tools, and one `dotnet restore CuriousContraptions.slnx --nologo --disable-parallel -noAutoResponse`. A mismatch is fixed before implementation, not discovered by a failed full round. When the same probe or command fails twice with the same output, stop repeating it: diagnose the environment (name resolution, proxy, credentials, a changed toolchain) or record a blocker with owner and retry condition. On macOS run the full local round under `caffeinate -i` so the host cannot sleep inside it. Do not upgrade the agent host or SDK while a slice is in progress.

## Capability probe

**Adds to:** Build/Auto step-02 planning, before the planning verdict; every element slice and any slice that plans to use an engine capability it does not itself deliver.

Before the planning gate, the coordinator dispatches one read-only planning scout with the Planning scout card. The scout returns the capabilities the planned behaviour needs, the direct consumers that must change, the open owner decisions, and the shape and tier inputs, each cited in the current checkout. Record the four lists in the contract's Code Map; they are planning evidence, not a new register.

- A capability is **present** only with a cited symbol and a cited test that exercises it. A type or field name alone is not evidence. A capability with a cited symbol but no exercising test is **present, untested**: the slice adds that test and no split follows.
- A **missing** or **narrower** capability that changes a solver law, the worker ABI, the wire schema or a shared presentation contract is delivered as its own engine slice, published first, and the element slice is replanned from that published revision. Smaller additions (a declaration field, a typed parameter, a validator case) stay inside the consuming slice when the contract names them and their tests. This split rule is the owner's 21 November 2026 decision and amends [REQ-12](../../docs/delivery-workflow.md#standing-requirements); the prerequisite slice is a recorded blocker for roadmap order, bounded to the one capability, not a subsystem programme.
- The planning auditor (the existing engineering-auditor role performing its bounded planning check) verifies the probe as part of its Scoped Pass. A plan with an uncited capability or an unowned missing capability is Incomplete.
- When implementation still discovers a missing capability, the owner stops and returns it to planning; the coordinator applies the same split rule instead of amending the element contract in place. More than one such return in a slice is a stagnation trigger.

**Owner decisions.** The scout's open decisions, and any the planner adds, are put to the owner in one batch before ready-for-dev, each with a recommended default chosen from the game's intent. Planning is not ready while a required-now decision is open. In an unattended run, a decision that has a defensible default from the game's intent is decided, and recorded with its reason in the Code Map. A decision that cuts scope, waives a gate or cannot be inferred uses the native HALT `blocked` outcome, whose blocking condition lists every such open decision together, each with a recommended default, so one owner reply clears them all.

**Carry-forward.** Planning reads the entries of `_bmad-output/implementation-artifacts/deferred-work.md` whose paths or capabilities the slice touches, and the previous slice's run-log close note. An unresolved entry that this slice depends on becomes a prerequisite or an explicit, owned exclusion.

## Slice shapes

**Owner decisions, 21 November 2026 ([AGENTS.md](../../AGENTS.md), Delivery slices).** They apply from the next slice that starts; Bellows 12.4 and the registration-derivation slice, in flight on that date, finish under their starting rules.

- **Family slice.** One slice may deliver several named variants of one family when the capability probe marks every capability they need *present* or *present, untested*, so that none needs a new engine, abstraction, wire or shared-presentation capability. A family is variants of one part (presets, materials, colours, sizes), not unrelated parts that happen to be easy. Each identity keeps its own ledger row, acceptance rows, named discriminating tests and registration entries, and the acceptance-to-test table has its rows per identity. A variant found to need a missing or narrower capability leaves the family slice and follows the split rule above.
- **Duplicate closure.** An identity that duplicates another part gets no package and no catalogue or palette entry of its own. It is closed by executed proof through the part that satisfies it, and its ledger row cites that part and the test. It then counts as implemented for "every named element" and for the start of the post-catalogue browser phase, where the satisfying part's browser cases cover it. An identity with any behaviour, parameter or mode of its own is a variant or an element, not a duplicate.
  - *Duplicate of an undelivered part.* The closure is acceptance rows and named tests inside that part's slice, proving the duplicate's required behaviour through that part. It has no record of its own.
  - *Duplicates of delivered parts.* One closure review per group of related duplicates. It is an ordinary `bmad-build-auto` slice with one record, one candidate commit and one approval, whose owned diff is those tests and the ledger rows. It is data-only tier when it meets that test.
- **Early level proof.** A planned puzzle that uses only delivered parts may be authored and proven natively while an element slice is in flight: the real C# simulation solves it by the intended solution, a meaningful control fails, and Reset and save/load restore it. It is an ordinary slice record, run in its own worktree from published main. It can touch files the element slice also touches (the test project's `Compile` list, `content/puzzles.json`, coverage and impact tables), so publication is serialised: one publisher at a time, and the later publisher merges main once and repeats the full local round on the merged candidate before approval. It is not browser or campaign qualification, and component coverage still precedes exhaustive difficulty sweeps.

## Review tiers

**Owner decision, 21 November 2026.** **Replaces:** for a data-only slice, native step-04's launch of every configured layer; for every slice, Intent Alignment on passes after the slice's first. Applies from the next slice that starts; Bellows 12.4 and the registration-derivation slice finish under their starting rules.

The tier is chosen at planning and recorded in the Code Map with its reason and the location of the capability probe. This section is the only definition of the tiers; other documents refer to it.

A slice is **data-only** when its capability probe marks every capability *present*, each with a cited symbol and exercising test, and every path in its owned diff is on this allow-list:

- an element package's declarations, art, scenes and bindings under `elements/<Name>/`, with no executable logic: no branching, computation or behaviour code. Such logic in a package is engine-kind content under the Mis-tiered rule;
- authored content under `content/` (including `content/puzzles.json`) and `assets/`;
- tests of those packages and that content, added to the existing test projects, with no new or changed shared harness, fixture or helper code;
- a line that only adds the new package, source, content or test file to an existing list (the solution file, a `Compile` or source list, a registration, coverage or impact table), wherever that list lives. A new member, branch, type or parameter is not such a line;
- the slice's own record, run log and ledger rows under `_bmad-output/` and `docs/planning/`.

Everything else is **engine tier**: any other file of an engine, abstraction, wire, tool or test-harness project, anything under `schemas/`, TypeScript, build configuration, policy and workflow files. One *present, untested*, *narrower* or *missing* capability also makes the slice engine tier. When in doubt the slice is engine tier.

| Tier | First pass | Later passes |
|---|---|---|
| Data-only | Verification Gap, Forward-Only Auditor, Element-Free Engine Auditor | the same three on every pass |
| Engine | all six layers | both auditors and Verification Gap on every pass; Blind Hunter and Edge Case Hunter when the repair affects their subject; never Intent Alignment |

Passes are counted as in Re-review scope: the slice's first review pass, restarted by a `bad_spec` re-derivation.

**Confirming the tier.** Before each launch the coordinator compares the paths in `git diff --stat` and the owned untracked paths with the allow-list, and opens the hunks of every path it accepts under the list-line allowance; a path outside the list makes the slice engine tier. The informed header names the tier and the probe's location, and the Element-Free Engine Auditor confirms the tier from the full owned diff and the probe before anything else.

The two auditors and Verification Gap run on every pass of every slice, so the owner's forward-only gate and the engineering rules E1–E9 are audited as before and test adequacy is judged on every repair; the data-only tier drops only the layers whose subject, new branching code and new behaviour, a data-only slice does not contain.

**Mis-tiered slice.** If a path fails the allow-list, if the probe is found wrong, or if any layer reports engine-kind content, the slice is engine tier from that moment: the pass cannot approve, all six layers run on the current candidate as a first pass, and the findings already returned are kept and triaged. A slice never moves from engine tier to data-only after planning.

## Slice record: contract and run log

**Replaces:** in native step-03 and step-04, only the placement of bulk evidence and narrative inside `{spec_file}`. Every native section stays where the workflow writes and re-reads it.

Each slice keeps two files:

- **Contract** — the native spec file, wherever the route places it, with every native section: frontmatter (including `deferred:`), the intent contract, Code Map, Implementation Notes, Verification, Spec Change Log, Review Triage Log and Auto Run Result. Two subsections are added outside the read-only intent contract: **Capability probe** in the Code Map, and the **Acceptance-to-test table** in Verification. The Code Map's file list is the owned scope list. Children read the contract fully. KEEP constraints, unresolved findings, the baseline and the owner identity stay in it in full; every other log row, receipt or identity is one line that states the fact and cites its run-log entry.
- **Run log** — `_bmad-output/implementation-artifacts/run-logs/<spec file name>`, append-only and committed with the candidate: full command lines and raw-output locations, agent and message identity lists, path inventories, superseded plan text, finding detail beyond its triage row, handled owner messages, failed-attempt narratives and the close note. Nobody is told to read it fully; a prompt cites the entry it needs.

Where another section of this protocol says to record something in a native field, the fact goes in that field as one line and its bulk goes in the run log. Baseline, owner identity and scope are recorded once in the contract and referred to, not restated at each handover.

**Contract budget.** The contract stays within 6,000 words when planning passes and 8,000 when the slice closes (`wc -w`), plus 400 words for each additional identity in a Family slice. Each design answer, including anything written under the native Design Notes heading, is at most three lines: the decision, its reason and a citation. Derivations, alternatives considered, numeric working, superseded text and worked examples beyond ten lines go to a run-log entry that the answer cites. When a contract is over budget, the coordinator moves bulk to the run log before the next dispatch or review; this is record-keeping, not a finding against the product. A contract that cannot fit because it has too many acceptance rows is a slice to split. The intent contract, KEEP constraints, unresolved findings and acceptance rows are never cut to meet the budget.

## Entry and candidate identity

**Replaces:** Build/Auto step-01 early-exit routing and VCS sanity check order; step-03 Baseline; review staging and whole-worktree finalization.

Before any blocked, ready, in-progress, in-review, done or oneshot early exit or recovery, inspect the working tree and selected spec without writing status. Establish the bounded candidate and unrelated dirty work. For implementation/publication, use a clean isolated checkout rooted at the intended baseline; never stash, revert, copy wholesale or commit unrelated work to make it clean. Transfer only the explicitly owned candidate when continuing an existing slice. If ownership cannot be established safely, block before mutation.

A review or documentation-only maintenance task may operate in the shared checkout when its explicitly owned file/delta scope is unambiguous and no runtime implementation, rollback or publication is attempted. Record this restriction in the native review/spec record. Prior relevant guidance edits may be adopted explicitly as candidate input; unrelated Conveyor work remains outside scope. This exception does not authorize a whole-worktree diff or commit. If overlapping ownership makes the candidate uncertain, isolate it or block.

In existing spec Code Map/Implementation Notes (or the native review record for review-only work), retain checkout, owned scope, original baseline revision, relevant carried candidate changes, and implementation-owner agent ID. This is native context, not a new manifest. Capture baseline_revision once before first implementation. On resume, follow-up review and every repair loop, retain and validate it; never overwrite it with current HEAD. Include partial commits since that baseline in the candidate. Missing historical identity is Incomplete until reconstructed from actual evidence, not guessed from HEAD.

Alongside that native identity, record the applicable policy revision and explicitly owned uncommitted delta of the loaded custom guides/overrides, using existing VCS revision and owned file/hunk descriptions. A rendered snapshot identifies assembled source/resolved values, not the contents of every external file reference. On resume compare these relevant policy inputs with the recorded ones; apply the owner's stable-rules policy and any explicitly immediate/current instruction, recording the effect on plan and proof. Never reset the original candidate baseline or treat an unrelated HEAD change as evidence invalidation. No additional hashes or manifest.

An implementation owner is fresh per slice, retained for every patch and bad_spec repair. After first launch returns an ID, record it before any subsequent repair dispatch. Resume re-engages that ID. In this host, use collaboration.followup_task to resume a completed/idle owner; send_message only queues information, so verify an active turn or returned result before treating work as resumed. If unavailable, stop implementation with an explicit owner-unavailable blocker; a deliberate replacement is allowed only after reconstructing the current spec, original baseline, changes, KEEP constraints and unresolved findings, naming the replacement in the same record and keeping independent review separate. Never silently fall back to coordinator implementation.

## Planning and repair transitions

**Replaces:** Build/Auto step-02 self-review-only readiness for changed contracts; step-04 bad_spec direct return to implementation; patch coordinator fallback; oneshot inline implementation/fixes.

Before ready-for-dev, record the affected design answers and planned discriminating acceptance in native plan fields. For a new or changed reusable abstraction, schema or ownership boundary, reuse applicable independently reviewed architecture/design evidence, or invoke the existing engineering-auditor role for a bounded planning check. Supply the selected contract, actual prerequisite sources and planned cases. Do not run the full review layer set or require implementation tests at this stage. A recorded planning Scoped Pass is required before dispatch. Documentation/configuration changes use their affected workflow design and consistency cases, not invented runtime evidence.

For patch, re-engage the recorded implementation owner with the findings and affected checks. For bad_spec, amend the offending spec outside immutable intent, preserve known-good behavior and KEEP constraints, and revalidate affected design answers, prerequisites and planned acceptance through the planning gate before reimplementation. An intent conflict stays blocked until resolved; do not rewrite immutable intent to force convergence. Preserve baseline and owner throughout. Revert only proven candidate changes when a reset is necessary; never use blanket worktree cleanup. Do not discard correct work merely because the native branch says re-derive.

Build oneshot uses the configured implementation handoff and retained owner, not coordinator inline implementation. Its small plan may live in Implementation Notes, but the same entry, planning and repair gates apply. A nontrivial design conflict moves back to dispatch planning with the same candidate and owner.

### Blocked recovery and stagnation

A stored blocked status is not a permanent dead end or permission to proceed. Read its owner, reason and retry condition; verify the condition has changed with an actual check and record the resolution evidence in the native spec/review record. Only then resume at the installed status matching the remaining work: draft for unresolved planning, ready-for-dev for approved planning awaiting implementation, in-progress for unfinished implementation, or in-review for a candidate awaiting review. Preserve original baseline, implementation owner, known-good work and unresolved findings. Never infer done from the disappearance of a blocker. If the retry condition is unmet or ownership cannot be recovered, retain blocked/Incomplete with the next check.

Apply docs/delivery-workflow.md#focused-agentic-engineering's existing stagnation trigger inside both patch and bad_spec loops: roughly 45 minutes without newly runnable behavior/resolved blocker (a concrete reviewable correction for documentation), or two failed attempts at the same setup/check. The same confirmed finding surviving two attempted repairs counts as two failed checks, even when tests pass; apply this trigger to re-review as well as command failures. Reassess the hypothesis, acceptance and upstream design/spec or capability contract before another local patch. Record the concrete failure, competing explanation and next discriminating check; route a design defect through planning and bad_spec, preserving immutable intent. Continue longer investigation only with the source rule's stated reason and new evidence. Preserve Auto's native five-attempt bad_spec limit and its terminal blocked outcome; the stagnation trigger acts earlier and never resets that counter or waives proof. Do not add a new time gate.

## Capacity and independence

**Replaces:** workflow Subagents and review launch-all-in-one-message requirements when platform capacity is smaller than the layer count.

Fresh/context-free must be enforced by the host launch option, not just prompt wording. In this host, every first implementation launch and independent reviewer launch uses collaboration.spawn_agent with fork_turns='none'; pass only the role-specific inputs and required policy context explicitly. Implementers, reviewers and auditors run at the inherited model and capability, as native step-04 requires of review subagents. Three mechanical roles may be launched on a smaller, faster model where the host offers one (from the next slice that starts): the planning scout, a check runner (a child that only runs named commands and returns their results and raw-output locations) and status reconciliation (records-only edits that copy established facts into the sprint status or `TODO.md`). They decide nothing. A full-capability agent verifies the scout's citations at the planning gate and reads the runner's raw results, and an error found in a mechanical role's output is redone at the inherited default. Record the actual isolation option with the agent identity in native notes. Another host must use its equivalent no-history option. If unavailable, independent acceptance is Incomplete; do not substitute an inherited-history reviewer or call it fresh. Re-engaging the retained implementation owner for repairs is intentional and does not make that owner an independent reviewer.

Determine available child slots before dispatch. Launch independent reviewers in bounded waves up to that capacity; keep each context independent and never give a later reviewer earlier findings. Collect outputs without triage until every required layer finishes. Tool-level waiting and sequential launch messages are allowed; do not end the unattended turn merely to await background work. No capacity-based layer omission. If no reviewer can run, block with the actual capability failure. Re-engage only implementation owners for fixes; independent reviewers must remain independent.

**Waiting.** The coordinator waits for a child or a long command with the host's blocking tool call in the same turn, not a timed poll, never ends the turn to await a child, and posts no status message while nothing has changed. It edits `TODO.md` and the sprint status only when the slice's outcome, blocker or candidate changes. After a context compaction it re-reads the run log's handled-messages list and does not act again on an owner message recorded there.

## Owned review staging

**Replaces:** Code Review step-01 instruction 3's uncommitted `git diff HEAD` staging branch before its empty-content check.

Establish owned files/deltas first. For uncommitted review, stage their tracked HEAD-to-worktree changes (including index and working-tree changes), then append each owned untracked file as a new-file diff before checking for empty content. Discover untracked paths with `git ls-files --others --exclude-standard -z`, intersect with owned scope, and use `git diff --no-index -- /dev/null <path>` for each (exit 1 means differences, not tool failure). Use argument-safe paths and unique temporary inputs. Preserve deletion/rename content and deliberate hunk ownership. Do not stage into the Git index or include unrelated dirty files.

An explicit staged-only request instead uses owned index-only changes; exclude unstaged and untracked content even when the same path differs in the worktree. Branch/range reviews retain their requested baseline. A genuinely empty owned review stops as empty, never acceptance. Apply the following role split after complete candidate collection; untracked generated narrative stays out of blind inputs while normative new deliverables reach the informed auditor.

## Reviewer inputs

**Replaces:** the single all-changes diff for every lens; Auto's rule reserving the entire spec for edge-case alone; direct whole-worktree inspection in oneshot prompts.

Prepare role-specific inputs from the same bounded candidate using each skill's native input mechanism. Build, Auto and Code Review bind their existing diff_file placeholder separately for each layer; this is per-launch substitution, not a new customization field. Generic bmad-review uses its native content/staged-content path instead: pass the role-specific file as that input, never invent a diff_file variable. A direct document/artifact review retains the entire supplied artifact for every explicitly requested lens, including a requested spec or narrative document; never filter away the selected content as incidental claims. Exact requested lens sets remain exact and cannot grant missing full-gate approval. In such reviews, do not force a VCS diff, create an implementation spec or require runtime proof. Separate accompanying claims only when such claims exist. The role split below describes diff reviews; for artifact reviews, apply the equivalent separation of artifact content from accompanying claims. Build oneshot must stage these scoped temporary diffs before its Review section even though the installed step has no staging section.

- **Blind Hunter / Edge Case Hunter / Verification Gap:** product-change diff, including changed tests, without workflow-generated spec narrative, triage, result receipts or implementation claims. Supply absolute paths only. Keep generated narrative out even when untracked. A changed requirement/design/policy is itself deliverable content: its normative changes must be inspected by the informed auditor, never silently dropped from the review.
- **Edge Case Hunter:** also receives claims_file separately and reads it only after independent tracing. No other blind specialist receives claims.
- **Intent Alignment:** product diff plus verbatim_intent, as its descriptive role requires. It does not grant acceptance.
- **Forward-Only / Engineering / Acceptance auditors:** full owned candidate diff, including changed specs, rules and workflow configuration. The engineering and acceptance auditors also receive the authoritative contract/design sections, source requirements and existing verification receipts from the native spec/review record. They are informed auditors, not blind lenses.

**Blind diffs leave out generated and asset files (from the next slice that starts).** The diff staged for Blind Hunter, Edge Case Hunter, Verification Gap and Intent Alignment excludes these pathspecs: `engine/gpu/WorkshopWireGenerated.cs` and `engine/gpu/WorkshopAuthoringGenerated.cs` (FlatBuffers-compiler output, still committed), and `*.uid`, `*.import`, `*.obj`, `*.png`, `*.bin` and `*.translation` (engine identifiers, import settings, meshes, images and compiled resources). Their sources stay in: `schemas/*.fbs`, the generator under `tools/WorkshopWireGeneration/`, `*.tscn`, `*.svg` and every hand-written file. With git, append `':(exclude)<pathspec>'` for each to the staging `git diff <baseline_revision> -- .` and skip matching untracked files. A one-line header on the staged file lists the excluded paths that changed, so a reviewer can name one it needs; Verification Gap reads an excluded file when a test it judges depends on it. The informed auditors' full owned diff keeps every file. Add a pathspec here when another generated or binary kind enters the tree; never exclude a hand-written file.

For informed auditors, supply a short plain-text header with their role-specific staged input (or direct artifact context) naming the absolute native record/artifact path, relevant sections, phase, candidate/artifact identity and raw command/result evidence paths where required. On the Auto route the header also names the slice's review tier and the location of its capability probe. Implementation acceptance requires the original baseline and current candidate identity; a standalone artifact review identifies the actual artifact and revision when available instead of inventing an implementation baseline. The header references existing evidence rather than duplicating it; a coordinator's success assertion is not a receipt. It explicitly permits reading these inputs and overrides claims-only isolation for this role. Missing contract, current candidate identity or required-now proof means Incomplete; a test's source is not evidence it executed. Planning headers identify tests as planned. Review-only work with no implementation spec uses its native review record; never fabricate a spec or acceptance result.

Before every launch, verify each required path exists and substitute all known project/runtime placeholders to absolute paths. No unresolved token reaches a child. The coordinator checks that the product and informed inputs together cover every owned deliverable and that no excluded narrative is the sole copy of a changed obligation. If a product diff is empty, report that specialist's scope empty, not whole-candidate Pass; the informed review still examines documentation/configuration changes.

### Reviewer duties

Read the assigned role's input and relevant authoritative source sections. The coordinator and engineering auditor load the full project engineering contract and both engine guides. Other specialists receive this duties section plus only applicable policy/source sections; they need not reload three complete guides. Paths alone are not evidence that a rule was applied.

All roles preserve owner policy: no mutants; no browser gate before catalogue closure; no output-hash or unjustified-precision acceptance; no invented finding quotas. Use defined gameplay/interface behavior and source-defined tolerances. Preserve your lens's purpose and required output format. Report unreadable inputs and evidence limits explicitly; do not silently fall back. Engineering audit covers all applicable E1–E9 and D1–D7 obligations, including non-engine changes. Coordinator owns triage and the blocking verdict.

## Implementation handoff and verification ownership

Before requesting independent review or the required full local round, the retained implementer inspects the full owned diff from the original baseline, including carried commits and untracked content, for needless branches/state, duplicate rules, speculative abstractions and unrelated churn. Make justified simplifications now and record a short result in native Implementation Notes. This self-check is not approval, never waives the final post-review scope/simplification analysis, never changes baseline or acceptance, and does not require cosmetic refactoring.

In existing Verification fields assign each command to one executor, naming its matching build/configuration, raw result location and relevant inputs that invalidate reuse. Normally the implementer owns affected builds/checks and one designated executor owns the final required full local round. Independent reviewers inspect matching evidence and run unresolved discriminating checks; they do not duplicate the whole round merely to own a result. Normal hooks remain separately mandatory and do not replace that round. A relevant late repair rebuilds/rechecks its affected closure; reuse still-applicable evidence. Documentation/tool-policy work runs affected checks without claiming runtime qualification.

**Write validation in batches.** Anvil validation runs before each write and its decision is honoured, but it needs no turn of its own per file. An agent with several writes ready sends their validation calls together in one response and, in the next response, makes exactly the writes that returned `allow` or `warn`. A `block` withholds that write until its diagnostics are fixed and it is validated again, and every write in the batch that depends on it is held with it. A `gateUnavailable` result is reported and the write proceeds, as the tool specifies. Do not put a write in the same response as its own validation: the decision would arrive after the write. Anvil has no command-line pre-write entry point (checked at 0.14.3-alpha.6; `anvil check` scans files already on disk), so a host hook cannot replace the call.

### Handoff order and first-pass checks

The implementation owner hands off only after these pass, in this order, and records each in the run log:

1. **Maintainability gate.** Run it as soon as the candidate compiles and again here, so a complexity repair is not discovered after review. Make the matching non-incremental compiler-log builds once per changed candidate, then run the gate, in that order, before any test run that counts as evidence. The gate builds into its own temporary folder and leaves the checkout's build outputs and compiler logs current, so no rebuild follows a completed run. This order applies from the next slice that starts.
2. **New-package registration check.** Whenever the slice adds or renames a package, port, parameter, wire field, test file or tool, run the [registration check](../../docs/delivery-workflow.md#new-package-registration-check). It runs the hand-maintained catalogue, palette, coverage, impact, analyzer and static-gate tests that otherwise fail first in the full round, including the guard that every repository C# file is compiled by a project. A focused result from a test file that guard has not yet accepted is not evidence.
3. **Acceptance-to-test table.** In the contract, one row per matrix and acceptance row: the row, the named test, its control and boundary case, and the run that executed it. A row without an executed discriminating test is not ready for review.
4. **Whitespace.** Run `git add -N` on owned new files, which the check otherwise ignores (intent-to-add records only the path and is the one exception to the no-staging rules here and in native step-04), then `git diff --check <baseline_revision>` is clean, so staging finds nothing after the final scope check.
5. **One full local round** on the handoff candidate: zero failures, `Skipped: 0`.

The handoff round is the round native step-03 Verify requires; the coordinator inspects its matching evidence and does not repeat it. During repair the owner runs the affected checks and, where the repair touches registration, the registration check. A second full round runs only when the candidate changed after handoff, on the final candidate, by the designated executor. This is how AGENTS.md's "once per round, at the end" and E7's full local round apply here: one per candidate that review or acceptance relies on, never one per repair.

## Coordinator reading and the review step

**Replaces:** native step-03 Verify's "read that file into your own context" and "rewrite `{diff_file}` and re-read it"; how native step-03's Matrix Test Audit is performed; the coordinator's own whole-diff reading in step-04 and in the Final diff scope check. Applies from the next slice that starts (loop change approved by the owner, 21 November 2026).

The coordinator does not load the candidate diff into its own context. Independent judgement of the diff belongs to the review layers, which each read it in full. The coordinator reads instead:

- `git diff --stat <baseline_revision>` and the owned untracked paths, compared with the Code Map's owned scope list. A changed path outside that list, or a listed path that did not change, is opened and resolved before review launch.
- The owner's handoff report, the acceptance-to-test table and the raw results of the Verification commands. Native step-03's "judge against the diff, not the report" is kept this way: a claim in the report counts only with its command result or a hunk the coordinator opened.
- For native step-03's Matrix Test Audit, the acceptance-to-test table and the raw test results: every matrix row has a named covering test that ran and passed in the cited run. Whether a covering test is adequate is judged by the Verification Gap layer, not by the coordinator reading test source.
- In Classify, for each finding, the cited file and lines and as much surrounding code, callers and guards as verifying that one finding needs (`git diff <baseline_revision> -- <path>`, or the file itself). Nothing wider.

It still stages `{diff_file}` and the role-specific diffs as files for the layers. The Final diff scope check and simplification analysis are performed from the full owned diff by an informed existing reviewer, re-engaged sequentially after re-review completes; the coordinator records that reviewer's compact result and opens the hunks behind any item it must decide. When no informed reviewer can run, the coordinator performs the check itself and says so in the entry.

### Step-04 as this project runs it

Native step-04 remains the installed step, because the skill's customization offers activation hooks, facts, the handoff and review layers but no way to replace a step file. This list is the one ordered reading of it with the project replacements applied; where a line names a section, that section is the rule.

1. Set `in-review`. Stage the role-specific diffs ([Reviewer inputs](#reviewer-inputs)) without reading them.
2. Confirm the tier from `git diff --stat`, the owned untracked paths and the allow-list, opening only the hunks of a path accepted as a list line ([Review tiers](#review-tiers)). Launch that tier's layers in capacity-bounded waves ([Capacity and independence](#capacity-and-independence)) and wait with a blocking call.
3. When every launched layer has reported, verify each finding at its cited location, render one verdict and write one triage row per finding. The native verdict vocabulary, carried-row rule and triage-log format stay. The native reject-low, out-of-scope, spec-edit and agent-context rules do not ([Triage](#triage-re-review-and-completion)).
4. Route each confirmed finding by Routing by what is wrong, and from the third pass apply Re-review scope.
5. Patch: re-engage the recorded owner, never the coordinator; the owner runs the affected checks; refresh the staged inputs; independently re-review the fix with the layers it affects.
6. `bad_spec`: amend outside the intent contract, pass the planning gate again, return to the same owner. The native five-iteration limit stays.
7. After the last re-review: the [Final diff scope check](#final-diff-scope-check); the maintainability gate on the resulting final candidate, without which that check does not pass; a second full local round by the designated executor on that final candidate when it changed after handoff, including by the scope check; the close note and deferred-work additions; the one candidate commit through the unmodified normal hooks; independent SnapshotApproval of that committed SHA; and only then publication ([Terminal completion](#terminal-completion)). Native Finalize's follow-up thresholds and whole-repository clean check do not apply.

## Triage, re-review and completion

**Replaces:** native reject-low, defer-pre-existing/out-of-scope, reject-spec-edit and defer-agent-context rules; carried-verdict shortcut; optional followup_review_recommended thresholds; immediate done/commit after patch; whole-repository clean check.

Verify each finding against the current contract and candidate. Spec/context locations do not justify rejection or deferral. A carried verdict requires evidence still applicable to current relevant inputs and owner policy. Confirmed applicable violations block approval; element-specific and forward-only violations are high. Required-now uncertainty is Incomplete, not maybe-false then defer/proceed. Every confirmed review defect must be repaired before acceptance, including pre-existing issues or findings outside the initial diff and low-severity defects; the only exception is the Re-review scope rule below. Origin, age, initial scope, severity or context-file location alone never justify rejection or deferral. Reject only with an evidence-backed refutation of the concrete defect. Amend the plan and owned scope for the necessary repair closure, preserve baseline/owner, return the repair to that owner, then independently re-review it and affected dependencies. Do not silently adopt unrelated dirty changes: isolate the repair or record an actual ownership/external blocker as Incomplete/blocked, with owner and retry condition; unresolved work cannot become done. This requires fixing confirmed findings, not a repository-wide hunt. Explicitly deferred browser/performance qualification is not itself a defect or a new required-now gate. A review-only assignment reports findings and blocks acceptance without claiming or performing unauthorized repairs.

**Routing by what is wrong.** **Replaces:** native step-04 Classify's patch and `bad_spec` definitions and its "when in doubt, prefer bad_spec" tie-break. `intent_gap` keeps its native meaning (the intent itself is wrong, ambiguous or contradictory) and its native route. Classify each confirmed finding before routing it:

- A missing, weak, vacuous or over-precise **test**, or a stale document or status line, is a **patch**: return it to the implementation owner with the affected checks. It does not reopen planning, even when the test it adds is listed in the contract; the owner updates the acceptance-to-test table in the same patch.
- A **product defect** against a correct contract is a patch.
- **`bad_spec`** is reserved for a contract whose specified behaviour, design answer or prerequisite is wrong or missing, so that implementing it faithfully cannot pass. Only these return through the planning gate.

Do not label a round's findings `bad_spec` as a group; route each on its own classification.

**Re-review scope (owner decision, 21 November 2026; narrows the 4 November repair policy for re-review only).** A *pass* is one Review Triage Log entry for the current candidate; a `bad_spec` re-derivation restarts the count, because its code has not yet been reviewed. A slice's first two passes are unrestricted in what they may confirm, and every finding they confirm is repaired in the slice. At any pass, every finding confirmed in the repair diff or in what it directly affects, including an unchanged caller the repair broke, is repaired. From the third pass onward, a newly confirmed finding outside the repair diff and what it directly affects is still repaired in this slice when it is any of: Fail or Incomplete under an owner hard rule or a required-now criterion (the no-skip, no-hash, forward-only, element-free, typing, f32, TypeScript and maintainability rules, and required-now proof); an incorrect game outcome, causal order, resting or motion behaviour, or lifecycle restoration; a crash, deadlock or data loss; or an `intent_gap`, which keeps its native route. Only a finding outside all of those, a quality improvement to code or tests that breaks no rule, criterion or behaviour, is deferred. The coordinator uses the native defer route, adds it to the spec's `deferred:` list and to `deferred-work.md` with source, evidence and owner before the candidate commit, and marks its Review Triage Log row as deferred under this rule. It then does not block completion: where this protocol or a route hook requires every confirmed finding to be repaired before completion, a finding deferred under this rule is excluded. On a review-only route the reviewer only reports; the caller that owns the slice applies this rule.

Every relevant repair invalidates affected approval. After the owner returns a fix, refresh the affected staged inputs, run matching required checks and independently re-review the fix and its dependency impacts before approval. Reuse still-applicable evidence for unchanged areas. This mandatory re-review replaces native numerical follow-up thresholds; a false followup_review_recommended value cannot authorize completion. Do not restart all lenses or full tests without changed relevant inputs or an unresolved concern; required local full-round/hook authority still applies to runtime candidates.

### Final diff scope check

After review is complete, every confirmed finding is repaired and affected fixes have passed independent re-review, the coordinator or an informed existing reviewer performs a final diff scope check and required simplification analysis before acceptance, Finalize, done, sprint synchronization or authorized commit/publication. This is a sequential completion step, not another simultaneous lens or a second full review loop.

Inspect the full owned candidate against the original intent, acceptance criteria and justified confirmed-repair closure. Include all candidate commits since the original baseline plus owned staged, unstaged and untracked changes; do not inspect only the last repair or reset the baseline to current HEAD. Establish complete coverage without including unrelated dirty work. Each changed file and meaningful hunk must serve necessary behavior, callers, schema, content, tests, documentation or a confirmed review repair. Identify incidental refactors, formatting churn, speculative abstractions or dependencies, unrelated features and duplicated documentation or ledgers. Judge necessity, not arbitrary line or file counts. Never rewrite intent to legitimize gratuitous work.

Analyse the full owned diff and affected dependency context for simplification opportunities through refactoring, deletion or other measures. Look for unnecessary branches, state, indirection and duplication; speculative abstractions, options or dependencies; opportunities to reuse existing generic laws; and simpler control flow, data flow or ownership. Require a demonstrable benefit to clarity, maintenance or correctness, not cosmetic churn or fewer lines alone. Preserve required behavior, acceptance criteria, typed and data-driven boundaries, validation, lifecycle safety, performance targets, test rigor and forward-only rules. Do not collapse distinct contracts or introduce element-specific engine assumptions in pursuit of simplicity.

Return a bounded, materially beneficial simplification to the same implementation owner for implementation before completion. Reject speculative, risky or unrelated adjacent cleanup with a concise rationale; retain a necessary design with an evidence-backed reason. No finding quota, line-count threshold or refactor is required when analysis finds no justified opportunity. A confirmed defect remains mandatory repair, never an optional simplification.

A controlled, justified expansion to fix a confirmed defect, including a pre-existing defect, is required repair rather than sprawl; do not relabel that defect out of scope. Return unnecessary owned changes to the same implementation owner for removal while preserving necessary repairs, KEEP constraints and unrelated dirty work, including Conveyor. Missing simplification analysis or scope/ownership uncertainty is Incomplete; remaining unnecessary drift is Fail. Either blocks completion. After removal or another relevant edit, run affected checks and independent re-review, then repeat both scope and simplification analysis on the actual revised full candidate before proceeding. Reuse unchanged valid evidence; do not restart all review layers without cause.

Record a compact **Final diff scope** entry in the native triage/result: candidate identity and baseline or artifact scope, coverage inspected, kept/removed rationale, concise simplification result (applied changes, no justified opportunity, or evidence-backed reason to retain the design) and Pass/Fail/Incomplete. No separate ledger or manifest is needed. Review-only receipt additions that accurately record this decision do not recursively require another receipt/check; changes to normative instructions, deliverables or candidate scope invalidate affected approval and require a fresh check.

Exact partial reviews retain their requested lenses and output contracts and do not become implementation approval. A direct artifact review uses the supplied artifact scope and available revision, without inventing a Git baseline. Its caller applies this check to the actual final candidate before using the review for acceptance; findings-only completion does not claim that gate passed.

### Maintainability gate

**Owner rule, 5 November 2026; balanced coupling and the test-project exclusion added 6 November 2026.** It applies to every slice that starts after adoption, under the AGENTS.md Stable rules. 9A.46e, which was in progress at adoption, finishes under its starting rules; every later slice, resumed or new, is gated. Likewise 9A.46g, in progress on 6 November, is not blocked by coupling findings. The [E9 maintainability gate](project-engineering-contract.md#e9--maintainability-gate) is a hard completion gate for every Auto, Build (including oneshot and small-change), Code Review and engineering Review approval. It is not a review layer and does not replace the full local round or normal hooks.

The implementation owner runs `dotnet run --file '{project-root}/tools/anvil/VerifyPolicy.cs' -- --maintainability --project-root '{project-root}'` before review handoff. The executor named in Verification runs it again on the actual final candidate after every relevant repair, before the Final diff scope check passes. Record the command, candidate identity, violation count (metrics and coupling) and raw output location in the existing Verification/Review Triage Log fields. Balanced coupling is mandatory: it runs inside the same command, `--coupling` alone never replaces the gate, and a run whose output lacks the `Coupling dependencies:` summary or either canary `PASS` line is **Incomplete**. The gate scores all production and tool code, not the owned diff: the metrics and balanced coupling between production projects. Test projects are excluded and the run lists them. It is not the native whole-repository clean check that this protocol replaces. The gate compiles every project from scratch with injected analyzer configuration into its own temporary folder (`--artifacts-path`), so the checkout's `bin` and `obj` folders are not written. The one exception is the root game project, whose output path the Godot SDK fixes under `.godot/mono/temp`: the gate builds in the order of the verification capture (playtest, solution, web), which leaves that project as the same variant from the same sources, and its assembly was byte-identical before and after the gate when this was introduced (21 November 2026, on `4f193bb2`). The gate's build is still not verification evidence, but no rebuild follows it: matching builds and compiler logs made from the same sources stay current, and a source change invalidates both as usual. An interrupted, timed-out or refused gate run can leave the root game project partly built or as the playtest variant, which is built first: make the capture builds again before any test run that counts as evidence. This changes where the gate writes, not what it checks. The tool behaves this way in every checkout that has the commit, including an in-flight slice once it merges it; the handoff order above applies from the next slice that starts.

Every type, member or coupling dependency the gate lists is a confirmed high finding, including pre-existing code outside the initial diff. Amend the owned scope to the necessary refactor closure and return it to the same implementation owner. Refactor behaviour-preservingly under the forward-only rule, keep or add behavioural tests for the refactored code, then independently re-review the repair. A gate failure is never rejected, deferred, waived or labelled pre-existing, out of scope or low. A coupling repair integrates through a contract, removes the intrusive path or removes the dependency. Suppressions, exclusions, generated-code markers on hand-written code, threshold changes, reclassified project kinds or volatility, test markers on production projects or edits that weaken the gate are Forward-Only/engineering **Fail** findings. A FAIL is **Fail**. A refused or missing run, including a non-compiling candidate, is **Incomplete**. Either blocks Finalize, done, sprint synchronization and commit/publication. Refactoring needed to clear the gate is required repair, not sprawl, in the Final diff scope check.

### Terminal completion

Before Finalize, sprint synchronization, done or authorized commit/publication, record the phase verdict, owned scope, candidate identity, actual evidence, the passing maintainability gate run and deferred gates in the native triage/result. Fail or Incomplete blocks the transition. Commit only explicitly owned approved changes; unrelated dirty paths do not authorize a commit or make a scoped documentation review fail. Do not claim approval for an unreviewed partial commit. Publication authorization and the owner's no-CI-wait rule govern; record remote/browser qualification unverified unless established.

**One candidate commit, one approval.** The contract's final status, the sprint status and any completion wording are part of the candidate that SnapshotApproval reviews; do not publish them as a second commit with its own hook run and approval. A Family slice is one candidate commit and one approval for all of its identities. Committed prose states what was verified before the commit and names what remains for the approver; it never describes its own approval or publication as done or as pending. The contract's native `status` field takes its native value. The SnapshotApproval verdict and publication receipt, which cannot exist before the commit, are recorded in `TODO.md` and the run log inside the next slice's candidate commit, as named owned scope, or by one records-only commit when no slice follows; they are never a second approved candidate.

**Close note.** The close note and every `deferred-work.md` addition are written before the candidate commit and are part of it, so the next slice finds them on published main. Append a close note to the run log: each confirmed finding class that recurred from an earlier slice, each defect left unresolved or with cause unknown, and each capability found missing late. Add every unresolved or cause-unknown item to `deferred-work.md` with its source, evidence and owner. Add a recurring mistake that a card could have prevented to the relevant [role card](role-cards.md) in the next policy change, in one line.

These controls are reviewable instructions. Resolver/render checks verify their wiring, and scenario walkthroughs inspect intended transitions without executing agents; neither proves future agent adherence or runtime engine compliance.
