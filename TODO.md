## Design candidates — pipes, electronics and optics (subagent research, 27 September 2026)

These are **pending puzzle options**, not implemented features or claims about the original TIM editions. Three research subagents considered transport, complementary mechanisms and beginner-friendly 3D interaction; follow-up research covers timers and optics. Behaviour, priorities and examples below are proposed rules for this game. Reconcile overlaps with the historical backlog rather than creating duplicate parts.

### Ball pipes and controlled delivery

- [ ] First: clear straight tubes, fixed-radius 45°/90° elbows and funnel inlets. Example: catch a bumper launch and route the ball around a wall into a basket. Start with one bore size and length-only straight resizing.
- [ ] First: a visible shutter/gate that holds and releases a ball through mechanical or powered control. Example: wait until a receiving tray arrives before releasing its payload.
- [ ] Next: Y-diverter with a visible selected outlet; introduce a fixed selection before powered or alternating selection. Example: send the first ball to a switch and the second to the basket.
- [ ] Next: hopper with a one-ball escapement, visible queue and one release per trigger. Example: feed two destinations alternately without releasing the whole supply.
- [ ] Later: spiral gravity-delay tube, powered airlift and speed-sensitive trapdoor. Distinguish travel-time delay from an exact electronic timer; uphill transport must visibly consume power.
- [ ] Implement hollow conduit surfaces in the existing custom sphere collision solver, not filled convex tubes or a separate Godot rigid-body world. Preserve gravity, momentum, blockage and visible ball motion; no hidden teleportation or constant-speed path following.
- [ ] Add explicit compatible inlet/outlet port IDs and orientation to connection definitions. Overlapping silhouettes do not establish connectivity. Test seams, fast-ball tunnelling, blocked outlets, queues, simultaneous arrivals and disconnected mouths.
- [ ] Use chunky collars, transparent strips/cutaways and tap-accessible inspection. Snap compatible endpoints; retain the existing move/rotate interaction, three unfilled dashed projections and transparent reference walls. Consider tap-to-route after basic pieces work, with one Undo for the whole route; do not add a CAD spline editor or permanent camera toolbar.
- [ ] Teach almost-planar routing first, then meaningful depth: around a corner → catch and bank → descending delivery → hold/release → powered transfer → stagger two deliveries through a shared crossing.

Research basis: [Minecraft's hopper description](https://www.minecraft.net/en-us/article/hopper) provides a collection/transfer precedent. Factorio's developer reports document both [unpredictable pipe behaviour](https://www.factorio.com/blog/post/fff-416) and [overly unconstrained transport](https://www.factorio.com/blog/post/fff-430). Those are design lessons about clarity and useful constraints, not a proposal to apply Factorio's fluid model to physical balls. Liquids, pressure networks and arbitrary suction remain separate future scope.

### Electronics: delay, duration, memory and counting

- [ ] First: **delay box — wait, then trigger**. A rising-edge event starts an adjustable countdown (prototype default 1 s), then emits one event even if the input has returned off. Ignore retriggers while busy and show that state. Example: release a ball after its catcher arrives.
- [ ] First: **hold timer — on for a duration**. Trigger immediately enables output for an adjustable interval (prototype default 2 s); ignore retriggers while active. Example: keep a pipe gate open long enough for a delivery. Do not conflate this with delayed activation.
- [ ] First: ball-crossing detector emitting one event per forward crossing, distinct from a pressure plate's continuous occupied state. Reuse existing switches where their semantics match.
- [ ] Next: Set/Reset latch, with Reset winning simultaneous inputs. Example: first detector starts a conveyor; the arrival detector stops it.
- [ ] Next: event counter with visible current/target count, saturating at its target and holding output until Reset. Example: collect three balls before unlocking a gate. A held input must not count every tick.
- [ ] Next: a dedicated “Both” gate for two continuous conditions; later “Either” and “Not” only where they earn teaching space. Example: open a hatch only when a ball is waiting and the lift is docked.
- [ ] Later: repeating clock/metronome. First event follows one full interval; disabling resets phase. Example: repeatedly feed an alternating pipe junction.
- [ ] Define power versus control explicitly: a signal commands an actuator but never supplies motor power. Distinguish socket shapes and cable appearance as well as colour. Decide and document logic-module power before implementation; the research suggests self-contained low-power modules, but actuator batteries/solar supplies must remain necessary.
- [ ] Give each module one understandable job, with a small dial, countdown ring, status lamps or on-body count. Use contextual controls and icon-first UI; avoid a breadboard editor, arithmetic combinators or mandatory truth-table configuration.
- [ ] Use simulation-time ticks and deterministic event ordering. Pause freezes timers and physics together; slow motion scales both. Explicit Reset cancels pending events and clears timer/counter/latch state; run Reset restores authored initial state. Prevent zero-delay feedback loops and retain brief events across slow rendered frames.
- [ ] Specify loss-of-power rules: actuator power loss stops action without replaying missed one-shot events when restored. If logic requires external power, losing it clears volatile state/countdowns; restoration samples input without fabricating a rising edge. Test simultaneous Reset/trigger and blocked gates without clipping through balls.
- [ ] Teach wait-before-release → hold-open duration → remembered activation → count arrivals → interlock two conditions before requiring clocks or compound timing.

Research basis: Scrap Mechanic's developer [timer/logic update](https://store.steampowered.com/news/posts/?appids=387990&enddate=1473276913) demonstrates delayed interactions; Microsoft's [Redstone guide](https://learn.microsoft.com/en-us/minecraft/creator/documents/redstoneguide?view=minecraft-bedrock-stable) distinguishes signal timing behaviours. Factorio's [Combinators 2.0](https://www.factorio.com/blog/post/fff-384) motivates visible state and reducing cumbersome circuitry. Exact defaults above are our proposals, not copied behaviours.

### Optics: lasers, mirrors, splitters and lenses

- [ ] First: **laser emitter** with electrical supply and enable input, initially fixed power and one colour. Example: a ball-operated switch enables a beam that starts a powered conveyor.
- [ ] First: **adjustable flat mirror** with reflection determined by its actual surface normal. Example: reflect around a wall and upward onto a receiver. Reuse the three-axis rotation gizmo and offer a selected outgoing-ray preview; do not introduce another permanent rotation toolbar.
- [x] Render torch/flashlight light as a **soft cone widening from the lens**, not a straight line. The C# mesh uses four nested translucent shells and 48 sampled directions per shell, matched to beam angle/range and clipped against physical proxies. Reviewed browser reference and wall-shadow views preserve the palette and readable parts/UI; native tests cover rotated sources and partial obstruction.
- [ ] Extend cone visual checks to moving partial occluders from multiple camera angles and several simultaneous sources. Sampled silhouette clipping is approximate, not full volumetric scattering; measure frame performance and refine visible stepping if needed.
- [ ] First: **light detector / receiver** with a large visible target and threshold indicator, producing a control signal. Example: a passing ball breaks the beam and stops a fan. Teach immediate response before optional sustained-illumination charging.
- [ ] First: **beam shutter**, a visible blade that physically blocks the ray, driven by an electrical actuator or later a rope/weight. Example: hold a flap open while another mechanism charges a receiver.
- [ ] Next: **50:50 beam splitter**, sending half the incoming power straight through and half along the reflected path. Example: illuminate two receivers simultaneously with a limited power budget. Adjustable ratios can wait.
- [ ] Next: **colour filter**, passing selected RGB components and absorbing others rather than recolouring any input. Example: extract red from white; blue input cannot become red.
- [ ] Next: **RGB combiner/mixer**, distinct from a splitter. Combine aligned inputs into one outgoing beam without amplifying their total power. Example: red plus green supplies a yellow receiver; red plus blue gives magenta, all three white. Crossing beams in empty space do not automatically combine.
- [ ] Next: **colour-selective powered plug**, accepting an optical command while switching a separate electrical supply. Example: a yellow beam enables a battery-powered fan. Light is a control signal here, not free electrical energy.
- [ ] Later: **converging lens** and **heat-sensitive latch/target**. Move the focal region onto a target to release a ball. Track beam width and irradiance, not merely a redirected centre ray; focusing increases power per area, not total power. Show a finite focal spot and short/long focal-length presets.
- [ ] Later: **diverging lens**, spreading limited power over a wider footprint. Example: cover two low-threshold detectors, neither receiving the full original power. Implement with finite-width beam coverage and partial occlusion.
- [ ] Later: **prism**, separating components present in white light into RGB paths using an explicit simplified spectral rule. A pure red beam must not create green or blue energy.
- [ ] Optional: **fibre/light pipe**, carrying light between explicit optical endpoints with coupling limits and loss. Keep separate from ball tubes and restrict its inventory where unrestricted routing would bypass the mirror puzzle.
- [ ] Build C# optical tracing against the custom collision world: finite mirror/aperture surfaces, nearest-hit occlusion, moving balls and wall OBBs. Define opaque frames/mounts; do not silently use a conflicting second collision world.
- [ ] Track linear RGB power, beam width, finite range and bounded branch/bounce counts. Passive optics cannot amplify power; stop cycles deterministically and never count circulating light repeatedly as fresh energy. Define finite-width coverage before claiming useful lens physics.
- [ ] Snapshot geometry/control once per fixed tick; trace emitters, aggregate detector contributions, then commit outputs together. Changes caused by those outputs affect the next optical tick, preventing entity-order dependence and recursive same-tick feedback.
- [ ] Reset restores transforms, shutter pose, emitter settings and electrical/charge/heat state; clear traced beams and recompute previews. Test occluded receivers, wrong colours, insufficient split power, loops, moving blockers and power interruption.
- [ ] Keep bright toy housings, chunky stands, clear glass and large target discs. Add original pictograms for each distinct function. Show aim paths/focal envelopes only when relevant; supplement colour with channel symbols/patterns. Visible side-on beams are a readability convention, not a claim of full optical simulation.
- [ ] Teach hit a receiver → interrupt with a ball → reflect around an obstacle → gate a beam → split limited power → filter/mix colours → command a powered machine → focus/spread light → separate colours with a prism.

Research basis: Croteam's official [device reference](https://taloseditor.croteam.com/device_reference/) documents coloured generators, connectors and matching receivers with charge timing. [Edmund Optics](https://www.edmundoptics.com/knowledge-center/application-notes/optics/what-are-beamsplitters/) distinguishes transmitted/reflected splitting from wavelength separation. [Open University](https://www.open.edu/openlearn/body-mind/how-lenses-and-mirrors-work) explains focusing/spreading, and [AMNH](https://www.amnh.org/explore/ology/physics/play-with-color-and-light) explains prism colour separation. These support the concepts; the simplified game rules above are proposals, not edition-specific TIM claims.
